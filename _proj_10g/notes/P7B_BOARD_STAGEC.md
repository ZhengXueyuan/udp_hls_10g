## 3. ⭐ 限速级判定：机制、证据链、不确定度

### 3.1 现象（三台独立仪器同时指同一件事）

1. **板侧账**：`ΔW15(W15 = tx_stat_bytes 含重传)/ΔW51(app 载荷)` = **13.8–19.3**；`ΔW55(tx_stat_retx)` = **6,970–11,449 会话**，
   每次会话重放 `(ΔW20−ΔW52)/ΔW55` = **27.6–34.5 帧** ≈ **在飞窗口上限 33 帧**（`RING_CAP = 0xBFFE = 49150 B / 1460`）。
2. **线上账**（DL1 头段 20,000 帧 pcap，`an_dl.py`）：第一条连接 **10,183 个数据帧 = 667 唯一 + 9516 重复（93.4%）**；
   时间线可见 **重放突发（seq 回退重放）紧跟在对端同 ack 的 dup-ACK 批之后**（例：t=0.000206–0.000244 收 8 个
   `ack=305419897` 的 dup-ACK ⇒ t=0.000261 起板子重放 `seq=305419897…305425736`=前 5 帧）。
3. **对端账**：`TcpInSegs` 逐跑 ≈ 板侧 `ΔW20`（**无线上丢帧**），`TcpExtTCPOFOQueue` 只 +627…+1198
   （**0.16–0.4%** 的乱序到达）；`port_rx_nodesc_drops` 在 DL4（ring 4096）为 **0**。
   ⇒ **初始"洞"是 0.16–0.4% 量级的小事件，被放大成 1400–1900% 的线上重复。**

### 3.2 机制（与读数逐条对齐）

```
板发一整窗（8–16 帧突发，窗口上限 33 帧）
  → 对端栈出现一个洞（0.16–0.4%；ring=4096 时为 0 的 NIC 丢失 ⇒ 洞在栈/软队列一侧）
  → 对端 quickack：洞存在期间**每收一帧回一个 dup-ACK**（pcap: 9815 ACK / 10183 数据帧）
  → 板子把 dup-ACK 当重传触发 ⇒ **重放整个 [snd_una, snd_nxt]（≈29 帧）**
  → 重放帧多数是**对端已收过的重复** ⇒ Linux 对重复段**立即回 ACK** ⇒ 板子看到更多 dup-ACK
  → 回到第二行 ⇒ **自持反馈环**（一次初始洞可自持放大 ~20×：627 个 OFO 事件 vs 36 万重复帧）
```

**这不是"板子发不出去"，也不是"对端收不下"**：帧率只有几何上限的 43–46%（`ΔW43/ΔW20` = 416–461 拍/帧，几何 193 ——
⛔ **2026-10-10 订正（口径）**：原写"TX 线只忙 43–46%"；`W43` 每拍无条件 +1 ⇒ `193/P` 是"fps 未达几何上限"的换算、
非线占空测量），对端在 UDP 洪流下能收 809,578 fps。**是 TCP 的丢包-重放-再丢包的闭环把有效吞吐打到 ~6%。**
（⚠️ 本格的直接证据 = **重复率 13.8–19.3×**（`W15/W51`，板侧实测）+ 首连 pcap 93.4% 帧是重复 —— 不依赖"线占空"。）

### 3.3 ⚠️ 归因的边界（不许读过头）

- **"洞从哪来"没有定到最后一米**：pcap（对端驱动层）显示这些段**到过对端**，但对端 TCP 没前进
  （首连前 21 个 ACK 停在 `ISN+1`）⇒ 洞在**对端栈内部**（软队列/socket 层）。**我没有逐个洞的见证**。
- **"谁先动手"**：第一跳重放**紧跟 dup-ACK 批**（时序上）⇒ 触发键 = dup-ACK；但**板的 dup-ACK 阈值**
  （≥3？）与**重放粒度**（整窗而非单洞）只有行为证据、没有 RTL 级证据（本轮禁读 `rtl/`）。
- **A/B 只证明"Stage C 的两刀（A2 + `TCP_TX_OVL`）把下行打坏了"**，没有拆开是刀 1 还是刀 2 单独触发
  （两者是乘法关系：只有 A2 ⇒ 帧器 379 拍；只有乒乓 ⇒ app 1828 拍 —— 两者都不足以让 TX 线跑到线速突发）。
- **`Δnodesc` 口径**：对端 NIC 的 `port_rx_packets/good_bytes` 在 **~1M fps** 时**虚高 ≈18%**
  （J0 窗：NIC 记 983,201 fps > 该几何上限 809,578 fps，见 §6-②）⇒ **凡是拿对端 NIC 绝对计数做判据的，
  先过"线上时间预算"这一关**。DL4 的 `Δnodesc = 0` 就是在这个有偏的计数器上读到的（**登记，不加重**）。

### 4.3 双向（设计件 §6.3 的预算）—— ✅ 量到"每 ACK 11 拍"

**构型**（登记清楚）：板侧 UDP 泛洪（UDP 数据帧占满 TX 线）+ 对端 TCP 上行 `p7b_tcp_src_fix`（板每收一帧发一纯 ACK
⇒ ACK 插进同一条 TX 线）。**这不是 TCP 数据 + TCP ACK**（演示 app 单会话 ⇒ 两方向 TCP 数据不能并发，§7-③），
但"数据帧 + 纯 ACK 共用 TX 线"这一**结构**同构。

| 窗 | 时长 | UDP fps | 拍/帧 | UDP 载荷 | TX 线组成 |
|---|---:|---:|---:|---:|---|
| UDP-only 基线 | 2.571 s | **809,578** | **193.00** | 9.5336 Gbps | 数据帧 100%（ACK 帧 = −1） |
| 上行进行中（1 s 窗） | 1.070 s | 795,323 | 151.21 | 9.3657 Gbps | 数据帧 + **238.0k ACK/s** |
| 上行进行中（~5 s 窗） | 5.003 s | 795,234 | 149.25 | 9.3652 Gbps（**−1.77%**） | 数据帧 + **251.7k ACK/s** |
| 上行停止后 1 s | 1.073 s | **809,578** | **193.00** | 9.5336 Gbps | 数据帧 100%（ACK 帧 = 1，**fps 逐字回到基线**） |

- **判据**：`ΔW20 − ΔW8`（MAC 帧 − UDP 数据帧）= ACK 帧数；~5 s 窗 = **1,259,061 / 5.003 s = 251.7k ACK/s**，
  UDP 数据帧率损失 = **1.772%**。**模型预测** = `251,666 × 11 拍 / 156.25e6 = 1.772%` ⇒ **逐位吻合**（设计件 §6.3-核的
  "纯 ACK 线时 = 11 拍"**首次拿到板级读数**）。
- ⚠️ 设计件写"204 拍"时假设 **ACK 率 = 数据帧率（809k/s）**；实测此构型 ACK 率 = 252k/s ⇒ 损失 **1.77%**，
  **不是 5.4%**。谁对谁错取决于工作点（上行 4.15 Gbps ≈ 355k ACK/s ⇒ 2.5%）。
- 同窗对端读数：上行在洪流下 **2877.9 Mbps**（vs 无洪流 4042.7–4149.1）⇒ 洪流/ACK 挤占使上行 −30%。

## 5. ⭐ 专节：`0x04` 实测 = **0xA**（BID 提升的**首次板级证据**）

- 读数：`ID_BID 0x0000000a` + `ID_OK`（`/tmp/p7b_biz/p7b_snap.sh id`，rc=0）；
  `final_state.sh` 收尾复读 `BID=0x0000000a`；A/B 期间换 Build 2 后读回 `0x00000009` ⇒ **BID 真的有区分力**（#55 的债还清）。
- ⚠️ **拿到这个读数之前先修了一个台架缺陷**（否则整轮所有身份门都会**假红**）：
  `reg_rw` 打**小写** `0x0000000a`，而 BID_SYNC 轮把期望值写成**大写** `0x0000000A`，原代码是**字符串**比较
  ⇒ BID 世代里第一次出现字母（9→0xA）时**必假红**（8/9/7 全是数字 ⇒ 结构性从未暴露）。
  修法 = 比较前大小写归一（`norm()`），**判据语义零改动**；落点见 §6-①。
- ⚠️ **仍未取得**：`p7b_gate4_accept.sh` 的 G1（它用**数值**比较 `[ $((bd)) -eq $((EXPECT_BID)) ]` ⇒ **免疫**，无需改）。
