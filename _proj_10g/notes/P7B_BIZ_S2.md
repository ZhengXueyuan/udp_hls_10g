### 0.2 ⚠️ **一条方法更正（本轮自己踩到、必须写下来）—— Windows `ping` 的退出码不是可达性判据**

- 本轮最初用 `ping -n 1 -w … 192.168.0.38 >/dev/null 2>&1` **按退出码**判"对端活着没有"，
  于是先后报出 **3 次"PEER_UP"**（20:02:48 / 20:09:47 / 20:37 起多次）。
  **全部是假阳性**：Windows 在收到**本机产生的** `无法访问目标主机`（destination host unreachable）时
  **仍然 `exit 0`，且统计行写"已接收 = 1，丢失 = 0"**（原文留档在本轮 shell 输出里）。
  ⇒ 那个分支的读数**看着完全像"通了"**。
- **实测反例（两种失败形态的退出码）**：
  - `无法访问目标主机`（ARP 失败）⇒ **exit 0**（＝假阳性来源）
  - `请求超时`（ARP 通、无 ICMP 应答）⇒ **exit 1**
- **改用**：`TCP connect`（`socket.connect((ip,22))` / `:3121`）作为可达性判据，并对**扫描器自身**
  做正/负对照（`192.168.0.1:80 == True`）。
- ⚠️ **同族教训（与全局第 28/30/34/35 条同一个坑）**：**"判据/工具本身会安静地给出错的'通过'"**。
  本轮的"PEER_UP ×3"如果被当成真读数，下一步就会去烧板、然后读到一堆
  `PRECHECK_FAIL`/空读，再把它归因成"板子死了"——**归因方向会整个错**。

## 3. ⚠️ **J16 的判据强度订正**（"`W56` 恒 0"**不是**"8 B/帧真修掉了"的正证据）

方案 §5.3-4 写：**`J16` 先跑**，`W56` 恒 0 是"修复到位"的板侧直接证据，**反例 = 未修的位流，它应非 0**。
**这句话对不上 RTL**（本轮逐字读过修复 diff 与 `rtl/fifo_sync.v`）：

| 事实 | 出处 | 后果 |
|---|---|---|
| 修复**前**写口是 `.wr(txf_wr && !txf_full)`（本拍 `full` 做预 AND） | diff 的 `-` 行 | —— |
| `ovf_pulse` 的定义就是 `wr && full` | `rtl/fifo_sync.v:59` | ⇒ 修复前 `ovf_pulse ≡ txf_wr && !full && full ≡ **0**` ⇒ **结构性恒 0** |
| `stat_tx_ovf` 是修复**新增的输出端口**（修复前不存在） | diff 的 `+` 行 | ⇒ **旧位流里这个字根本没有**（旧位流是 51 字，W56 不存在） |

> ### ⇒ **J16 的正确读法**：`ΔW56 == 0` 是**修复后必须成立的"守卫"**（它在生产者判据回归时**会响**，
> ### 所以它是**有牙的回归守卫**），但它**不是**"8 B/帧已修"的**正证据** ——
> ### 在**修复前**的位流上它也**只会读 0**（要么字不存在、要么被预 AND 钉死）。
> ### 方案里"反例 = 未修的位流，它应非 0"这句**作废**。

**⇒ ① 的正证据只能是 §2.3 的几何（四台仪器）+ `ΔW9 == Σ线上载荷`**（后者在缺陷态**必然失败**，
差值恰为 `8 × 帧数`）。J16 与它**互为补充**，不互为替代。

| **W55** | `tcp_tx_frame.stat_retx` | `if (svc_rewind) stat_retx <= stat_retx + 32'd1;` —— **回卷次数**（重传会话启动数） | `rtl/tcp_tx_frame.v:823` |
| **W57** | `tcp_tx_frame.o_retx_hi` = `retx_hi` | 回卷**高水位** = 回卷**前**的 `snd_nxt`（⇒ 本会话重放上界）；**只在 `retx_active=1` 时有效** | `:108`、`:254`、`:815-817` |
| **W58** | `tcp_tx_frame.o_retx_active` = `retx_active` | 重传会话进行中（**瞬态电平**，一次会话 ~数百拍到数万拍） | `:109`、`:255`、`:822` |

### 4.2 ⭐ 关键：**`ΔW55` 与 `3,572` 对不对得上，本身就是一个判别式**

`svc` 的触发源有两个（`rtl/tcp_tx_frame.v:297-298`）：
```verilog
wire svc = (state == S_IDLE) && !ack_pend_r && !retx_active &&
           !flush_pend && (retx_req || rto_pend_any);
```
- `retx_req` = `tcp_rx` 的 **dup-ACK 检测**（电平保持到 `retx_gnt`）
- `rto_pend_any` = **RTO 超时**

一次 `svc` ⇒ **一次回卷**（`stat_retx += 1`），而**一次回卷会重放从 `snd_una` 到 `retx_hi` 的
一整段连续 seq**（ring 会话逐帧重放，`ring_delta = retx_hi - rb_snd_nxt`，`:317`）
⇒ **线上出现的"重复 seq 段数" = Σ(每次回卷重放的段数)**，而 **`ΔW55` = 回卷次数**。

> ### ⇒ **判据**：Stage 1 的 pcap 口径 `dupseq = 3,572`（300 连接）
> - 若 **`ΔW55 ≈ 3,572`** ⇒ **每次回卷只重放 ~1 段**（点状重传）；
> - 若 **`ΔW55 ≈ 300`**（≈11.9/连接 却只有 1 次回卷）⇒ **每次回卷重放 ~11.9 段**（区间重放）；
> - 若 **`ΔW55 ≈ 300×11.9/大块数`** ⇒ 读出"一次回卷重放多少段"的**直接标定**。
>
> **这一条是本轮唯一能"把 11.9 这个数拆开"的判据**，Stage 1 做不到（那时 `W55` 不在窗口）。

### 4.3 ⭐ **dup-ACK vs RTO** —— 能用**参数推理**定掉一半，**但仍有必须上板的缺口**

**能定的（结构性的，本轮从源码算出）**：**在本轮的 300 连接测试里，RTO 触发结构上不可能。**
1. RTO 时长 = `RTO_LIM × 256` 拍；`RTO_LIM = 61035`（156.25 MHz 档）⇒
   `61035 × 256 / 156.25e6` = **≈ 0.1000 s = 100 ms**
   （出处：`rtl/tcp_tx_frame.v:162`、`:171`，`:326-328` 给出 `RTO_LIM × 256 拍` 的口径）。
2. Stage 1 实测**每连接总长 `dur_ms` 均值 = 9.284 ms**（1 MB / 903.7 Mbps），
   而重复段只出现在连接开始后 **0.105–4.16 ms**（`p7b_biz_s1/s1_2_duppos.txt`）。
   ⇒ **100 ms ≫ 9.28 ms ⇒ 一条连接活不到 RTO 点火**。
3. 且新连接**拿满整 100 ms**：`cfg_up` 会把该槽 `rto_timer` 清 **0**（`:769-770`），
   而扫描到 `0` 时是**重装** 而不是触发（`:944-945`：
   `if (rto_timer[scan_id] == 21'd0) rto_timer[scan_id] <= RTO_LIM;`）
   ⇒ **不存在"新连接继承旧会话的过期 RTO"这条捷径**（G4 已修）。

> **⇒ 结论（推理强度）**：本轮所有 rewind **只能是 `retx_req`（dup-ACK）触发**的。
> ⚠️ **但这是参数推理，不是读数**：`W55/W57/W58` **三个字里没有任何一个能区分触发源**
> （`stat_retx` 在 `svc_rewind` 上自增，对两个触发源一视同仁）。

**必须上板才能补的那一格（本轮**定不了**，如实登记）**：
**"对端到底有没有发过 dup-ACK"** —— 这要**前向 pcap 里的 ACK 序列**（同一 ack 号连续出现 ≥3 次）
或 `tcp_rx` 的 dup-ACK 计数器（**不在窗口**）。
⚠️ 而且 Stage 1 的 pcap 口径是 `gaps = 0`、`first_mismatch = -1`（对端**没看到丢段**）
⇒ 与"对端发 dup-ACK"**表面矛盾**，**这个矛盾本轮无法解决**，只能如实登记为
"**板子在无对端丢段证据的情况下自发重传**"（与"RTO 卷回重放是我们的已知家族"一致，
且 §4.2 的 `ΔW55` 会给出重放规模的直接标定）。

### 4.4 `W57/W58` 的**可用性上限**（诚实说明）

- `W58`（`retx_active`）是**瞬态电平**，而快照是**采样**：一次重传会话约**几百拍到几万拍**
  （重放 ~11.9 段 = 11.9×~193 拍 ≈ 2,300 拍 ≈ **15 µs @156.25 MHz**），
  而一次 `full` 快照要**几十毫秒**（61 次 `reg_rw` 进程启动）⇒ **采样命中率极低**。
  ⇒ **要拿 `W57/W58` 必须用高频 `snap` 模式专打这两个字**（每次触发 + 读 2 个字，~几十 ms），
  或者接受"很可能采不到 `retx_active=1`"。
- `W57` 只有配合 `snd_una` 才有意义（重放字节数 = `retx_hi − snd_una`），而 **`snd_una` 不在窗口**
  ⇒ 单看 `W57` 只能读到"回卷前 snd_nxt 的高水位"这一个绝对量，
  与 pcap 的"重复段偏移上界"（Stage 1 实测最大 208,780 B）**可以直接对照**。

## 5. ③ `J12` / `W54` —— **"`W54` 有没有牙"的结论（RTL 层已定；注入器已备好）**

### 5.1 `W54` 的语义（逐字出处）

`rtl/app_pattern.v:531-542`：
```verilog
if (rxs == 2'd0) begin
    if (rx_tvalid) begin rw_data <= rx_tdata; rw_keep <= rx_tkeep;
                       rw_n <= pop8(rx_tkeep); rw_i <= 4'd0; rxs <= (pop8(rx_tkeep)==0)?0:1; end
end else begin
    if (byte_at(rw_data, rw_i) != rx_exp) stat_mismatch <= stat_mismatch + 32'd1;  // ← W54
    rx_lfsr <= xs_next(rx_lfsr);                                                   // ← 无条件推进
    stat_rx_bytes <= stat_rx_bytes + 32'd1;                                        // ← W53
    ...
end
```
⇒ **逐字节比对 + 每个比过的字节都无条件推进 LFSR**。

### 5.2 ⭐ **什么样的错误会让 `W54` 不动**（这就是"牙"的边界，必须写清）

| # | 逃逸形态 | 为什么它不动 | 谁兜住 |
|---|---|---|---|
| **E1** | **一个字节都没到校验器**（app RX 通路死 / `ev_up` 没来过 / `tcp_echo` 空） | 比对循环从未进入 ⇒ `ΔW53 = ΔW54 = 0` | ⭐ **`ΔW53` 的非空前置**：必须同时要求 `ΔW53 == 对端 socket `send()` 字节` |
| **E2** | 丢失发生在**每条连接的尾部**（最后一个被比对的字节之后、`ev_up` 重锁之前） | 下一连接的 `ev_up` 把 `rx_lfsr` 复位到 `SEED`（`rtl/app_pattern.v:333-335`），而对端**也**按连接从偏移 0 重发（`p7b_tcp_src.cpp:80` `P7bPat tx(0)`）⇒ **自动重新对齐**，失配一次都不产生 | ⭐ **`ΔW53 == 对端 send()`** —— 尾部丢字节会让 `W53` 短少（它是**逐字节累加**，不看对齐） |
| **E3** | 板侧**多算了**字节（重复投递同一段） | 重复投递的字节**仍然匹配**图案流（因为 LFSR 也照常推进） | `ΔW53 == 对端 send()`（多了就是多了） |
| **E4** | 载荷**整体位移 8 字节**（正是组①缺陷的形态） | **不会**逃逸：位移后第一个字节就失配 ⇒ 之后**永久失配**（LFSR 与流错位） | 它**有牙** |

⇒ **本轮结论**：
- **`W54` 对"内容错/位移/重排"有牙**（E4 那类正是它要抓的）；
- **`W54` 对"丢字节"只有在丢点之后还有可比字节时才响**；**尾段丢失要靠 `W53` 兜**。
- ⇒ **`J12` 必须成对判**：`ΔW54 == 0` **且** `ΔW53 == 对端 socket send() 字节`。**单判 `ΔW54 == 0` 无意义。**

### 5.3 ⭐ 牙的**证明**计划（注入器已实现、已自检；**未跑板**）

`_proj_10g/notes/p7b_biz_s2/p7b_tcp_badbyte.py`：
往 8080 灌 **N 字节真图案流**，**只在偏移 K 翻转 1 bit**（其余逐字节正确）。
由 5.1 的"无条件推进"⇒ **期望 `ΔW54 == 1`（精确），`ΔW53 == N`**。
- **精确的 1** 是关键：它同时排除"压根没在比对"（得 0）、"整帧否决/粘滞"（得大数）、
  "位移"（得 N−K）。
- **同时跑一条 `--flip-at -1`（不翻）的对照** ⇒ 期望 `ΔW54 == 0`、`ΔW53 == N`。
  **两条一起才叫有牙**（正例会响 + 负例不响）。
- ⚠️ 独立性的诚实说明：这个注入器**只**验证"校验器会数失配"，
  **不**验证"失配数 == 真实错字节数"（那要靠 E4 那种整段位移的离线复算）。

### 10.1.1 ⭐ **PCIe 恢复配方的扩展**（`P7B_PCIE_RESCAN_RECOVERY.md` 的场景 B 不够用）

本轮开机时 FPGA 跑的是 **QSPI 里的厂商设计**（POST 时枚举，`1 BARs: config 0, user -1`）。
烧上我们的位流（`2 BARs: config 1, user 0`）后做**设备级** `remove`+`rescan` ⇒ xdma probe **失败**：

```
pci 0000:02:00.0: BAR 0 [mem 0xf7a00000-0xf7afffff]: assigned
pci 0000:02:00.0: BAR 1 [mem size 0x00010000]: can't assign; no space
xdma:map_bars: Failed to detect XDMA config BAR ; probe err -22
```

**根因**：父桥 `0000:00:1c.0` 的内存窗在 POST 时按**厂商设计**（1 个 BAR）定为 **1M**，
装不下我们的 BAR0(1M) + BAR1(64K)。
**修法（已实测）**：**连根端口一起 remove + rescan** ⇒ 内核重算桥窗（`df200000-df3fffff [size=2M]`）
⇒ probe 成功、`/dev/xdma*` 重建、BAR 读回 `0x50360001`：

```bash
echo 1 > /sys/bus/pci/devices/0000:00:1c.0/remove; sleep 2; echo 1 > /sys/bus/pci/rescan
```

⚠️ **同一会话内后续重烧只需设备级 `remove`+`rescan`**（BAR 布局已在缓存里正确）—— 本轮后 3 次都是这样过的。
⛔ **不要**用 `0xffffffff` 判"是场景 A 还是 B"（两种都读 `0xffffffff`）；判据仍是 `lspci` 的 `LnkSta`。

### 10.5.1 ⛔ **新发现（高优先级）：TCP 上行从 1,073 Mbps 塌到 4.8–6.2 Mbps**

**读数**（4 次独立跑，含**重烧后第一个连接**）：`SRC_SUM tx_Mbps = 5.680 / 5.173 / 4.806 / 6.226`。
Stage 1 在**同一台对端、同一端口、同一工具**上是 **1,073.043 Mbps**（差约 200×）。
⚠️ **2026-10-07 加限定（`P7B_BIZ_TCPREG.md` §1.3）**：**1,073.043 = `2^30 bps`（1,073.741824 Mbps）的 99.94%**，
而 Stage 1 的原始件里**没有任何 pace 参数记录** ⇒ **可能含 `--pace-bps` 限速帽** ⇒ 这"200×"里
**至少有一个分量是"测试参数差异"**（不是任何硬件/代码变化）；**真实可持续率未定**。

**取证**：

1. **不是链路**：同一时刻 `ping 192.168.100.2` = **0.094/0.112/0.135 ms**；下行仍 ~897 Mbps。
2. **不是 app**：`ΔW53`（app 校验字节）**跟着 `ΔW22`（交付给 fast path 的帧）走** —— app 把到达的全都消费了。
3. **是"板通告的接收窗"**：对端 `ss`：`rwnd_limited:6ms(100.0%)`、`snd_wnd:3640`、`cwnd:44`。
   逐包看板的纯 ACK：**窗从 47,408 单调降到 9,440…，不恢复**（app 消费了也不把窗开回去）。
   ⛔ **现象订正（2026-10-07，`P7B_BIZ_TCPREG.md` §2.1）**：**不是"单调下降不恢复"，是 ~208 ms 的周期循环** ——
   窗**重开到 49152** → 被对端一个 GSO 大突发（29 KB 超级段）压到 **< 1 个 MSS** → **双向零包静默 ~208 ms**

   且 **`ΔW53 = 3,538,940 ≈ 对端 tx_bytes = 3,538,944`（差 4 B）、`ΔW54 = 0`**
   ⇒ **消费与回收都正常，缺陷在"通告"**（板从不主动通告窗口重开 —— 机理见 TCPREG §2.2）。
4. **不是状态泄漏**：**重烧后第一个连接**也是 4.8 Mbps；重烧前（跑过 300 连接 + 注入）也一样。
5. ⚠️ **无法做"换回 RATE 位流"的判决性 A/B**：RATE 位流文件已被 BIZ 构建覆盖
   （全仓 41 个 `.bit` 无 `4eeb0f5f…`）。
   ⛔ **订正（2026-10-07）**：**该 A/B 已在 `P7B_BIZ_TCPREG.md` §1 完成** —— 用 `git worktree` 从

   `6475c3ba…`），**同会话测出 4.544 Mbps** ⇒ 两臂同病（不是"位流文件没了"就没法判）。

> **判决：`J6`（上行速率）在 BIZ 位流上 FAIL。** 归因**未完成**：
> 证据指向"**板侧通告窗口的信用/回收通路不工作**"（`app_ctrl` 的 `winq/occ/redge` 闭环，
> `rtl/app_ctrl.v`），但**未读到 `winq/occ` 实值**（`dbg_redge0` 未接出、`dbg_winq0` 只进状态行）。

> 1. **"信用/回收通路不工作"改为"通告不工作"**：信用**在回收**（`ack+win` 右沿与交付量 1:1 前进；
>    `ΔW53`/`ΔW54` 见上文第 3 条的订正）；缺陷在 **`rtl/app_ctrl.v:1109-1122` 的 `wu`（窗口重开通告）**
>    —— 两个触发条件**结构性不可达 / 不触零** ⇒ **板从不主动通告窗口重开**，对端只能靠 persist/RTO
>    探回（实测 ~208 ms）。**这是"一直存在"的潜伏设计弱点**。
> 2. **对端侧假设被排除**（TCPREG §3 基线）：对端 TCP loopback **48.3 Gbps**、对端→本机真实路径
>    **327.9 Mbps**、对端 UDP TX → 板 **8.35 Gbps**、NIC 无实质错误 ⇒ **对端健康**。
> 3. **A/B 判决**：RATE 重建臂 **4.544 Mbps** / BIZ 臂 **4.719 Mbps** ⇒ **与 BIZ 四组改动无关**。
>    收口方向 = `P7B_BIZ_TCPREG.md` §6-#1（`wu_zero` 按"危险区"武装 + `wu_mark` 改基）。
