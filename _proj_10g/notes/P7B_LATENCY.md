# P7b 分段延迟实测 —— 一个以太网帧从 SFP 进来, 到整帧交给应用侧

> 施工目录 `_proj_10g/p7b_lat/` · 位流工程 `p7b_lat_prj` (**独立于 `p7b_ku5p_prj`**,
> 遵守"构建期间不得从被构建的工程烧位流") · 4 轮板级取数 (每轮都重烧)
> 读数组件: `board_scratch/run{1,2,3}_stdout.txt` (run1 在 `p7b_lat_probe_stdout.txt` 的副本) +
> `board_scratch/analysis.txt` (换算输出) + `scripts/pinmap.tcl` (探针位表)
> 标记: **【读得】**=板上直接测得 · **【推导】**=由已证事实算出 · **【未核实】**=没有证据

## 0. 一句话结论

**158 B 的以太网帧 (TCP 载荷 100 B 的那种口径), 从 (a) 点——即 PCS 把帧首 `/S/`
呈现在 XGMII 上的那一拍——到整帧交付给应用侧适配器入口: `217.57 ± 0.02 ns`
(11 个样本, 4 轮独立取数)。** 100 B 帧 `170.0 ns`(166.4 / 172.8 两个相位),
1514 B 帧 `1301.5 ns`。**硬下限校验全部通过**: 三者都 ≥ 线上串行化
(83.8 / 128.8 / 1180.7 ns), 64/64 个 `ack=1` 样本无一例外。

⚠️ **口径必须写清 (用户问的是 (B))**:
* **(A) 末字节传输延迟 = 各段拍数相加 = `95.98 ns`**, 与帧长无关;
* **(B) 首字节 → 整帧交付 = 166.4~172.8 / 217.57 / 1299.1~1305.5 ns** (含串行化)。
* ⚠️ **`(B) ≠ (A) + 线上串行化`** —— 因为适配器内部是**逐字播放**
  (0.800 ns/byte), 比 10.3125 Gbit/s 的线上速率 (0.7758 ns/byte) **慢 3.1%**,
  大帧的尾延迟由**适配器放字速率**决定而不是线速。这是本轮最有价值的副产品
  (证据 = §5 的 `(B) = 95.98 + N字 × 6.3997 ns` 模型在三种帧长上**逐 ns 命中**)。
* ⚠️ **(a) 点在 PCS 输出之后**: PHY 内部 (CDR/解串/gearbox/RX 弹性缓冲/PCS RX)
  的延迟落在 (a) **之前**, **本探针结构性地看不见** ⇒ 用户口径里的"第一个 bit
  出 SFP"还要再加 `前导串行化 6.21 ns + PCS 内部延迟(未测)`。见 §7。

## 1. ① GT DRP (`RXGBOX_FIFO_LATENCY` / 0x269): **读不通**

### 1.1 结论

**本轮 `0x269` 一个数都没读到。** 不是"读到 0"、也不是"忘了读", 而是这条路径
在**当前 IP 配置下不存在**; 而**把 IP 参数打开之后, 构建会在 `opt_design` 硬失败**。
下面是我**试过什么**、**卡在哪**、以及**下一轮怎么走**。

### 1.2 现役 P7b 位流**没有** DRP 端口 (证据)

| 环节 | 读数 | 出处 |
|---|---|---|
| `pcs64` 顶层端口总数 | **100 个, 无一个 DRP** | `…/ip/pcs64/pcs64.veo` 全文; `pcs64.v:68-328` 端口表 |
| 关掉它的参数 | `C_ADD_GT_CNTRL_STS_PORTS = 0` (GUI 名 **"Enable Additional GT Control/Status and DRP Ports"**) | `pcs64.xci:51`; `pcs64.xml:133293-133295`, 取值域 `choice_pairs_4873554b = {false,true}` |
| 核内 DRP 去哪了 | 被**钉成常量**、回读悬空 | `pcs64_wrapper.v:429-434`(ch0)/`:951-956`(ch1): `drpaddr_in_N = 10'd0; drpen_in_N = 1'b0; drpwe_in_N = 1'b0; drpclk_in_N = dclk;` —— 而 `drpdo_out_N`/`drprdy_out_N` **没有消费者** |

`opt_design` 直接报错退出 (与现役 wrapper 注释里记的 `Opt 31-67` 同族:

**为什么我没有把它们接 0 硬扛过去 (取舍, 写明理由)**:
* 在 `=0` 那版里这些量由**核内参数**驱动 (不在顶层); 要让"接 0"等价于"接原值"
  必须证明原值就是 0 —— 而 **TX 均衡/摆幅 (`txdiffctrl`/`txprecursor`/

* 本仓**没有**这些值的权威来源: XCI 的 `model_parameters` 里没有
  (`C_GT_SETTINGS = internal`), 明文的 `pcs64_gt_gtwizard_gtye4.v` 里它们走
  `localparam → *_int[…]` 层层派生; 本地也没有 UG578。
* 一旦接错, 受损的是 **TX 眼图** ⇒ 会污染本轮**唯一的主判据** (接收延迟)。
  用一个地址身份都未核实的 DRP 读数去换主判据, 不划算。

**下一轮要读 DRP 的正确做法** (留三条):
1. `generate_target example` 后**照抄官方 example 顶层**的连接值 (唯一权威来源),
   再按 `p7b_lat/rtl/p7b_lat_drp.v` 的时序接 DRP —— 该模块**本轮已写好并过了
   xvlog/xelab**, 只是被 `ifdef P7B_LAT_DRP` 关着 (接线留作施工入口);
2. 或改读 GT 之外的同族量 (但**给不出 gearbox FIFO 深度**);
3. 或接受"只用时间戳测" —— **本轮走的正是这条**, 代价是 (a) 之前的 PCS 内部延迟看不见。

> ⚠️ **`0x269 = RXGBOX_FIFO_LATENCY` 这个"已知"本身未被本仓任何文档证实**:
> 全仓只有一处 `P7B_PHY_IFACE.md:663` 把它登记成**未核实项 U9**, 且**没有任何实现**。
> 本地没有 UG578 ⇒ 即便下一轮读通了, 那个值也应先做**两通道对照 + 与
> "33 拍 @156.25MHz = 211 ns" 的量级核对**, 才谈得上字段身份。

## 2. ② 时间戳探针的设计与跨域标定

### 2.1 分段与观测点 (逐个带出处)

探针本体 `_proj_10g/p7b_lat/rtl/p7b_lat_top.v`; 接线在 `board/wrapper_p4.v` 的
**`ifdef P7B_LAT`** 块 (三层嵌套 `P7B_10G`/`P7B_LAT`/`APP_MODE`)。
**不带 `P7B_LAT` 的构建 (含现役 P7b 构建) 端口表与网表逐位不变。**

| 段 | 观测点 | 判式 (= **被接收**的拍: tvalid && tready) | 域 |
|---|---|---|---|
| **(a)** | PCS 边界 = 帧的第一个 XGMII 字 | 任一 lane `l`: `rx_mii_c_1[l] && rx_mii_d_1[8l +: 8] == 8'hFB` (`/S/`) | FE (`gmii_clk` = `rx_clk_out_1`) |
| **(b)** | MAC RX 输出 SOP 字 | `rxsrc_tvalid && rxsrc_tready && rxsrc_tuser` | FE |
| **(c1)** | `vlan_strip` 输出 SOP | `vs_tvalid && vs_tready && vs_tuser` | DP (`dp_clk`) |
| **(c)** | `rx_classify` **slow** 输出 SOP | `s_tvalid && s_tready && s_tuser` | DP |
| (cf) | `rx_classify` **fast** 输出 SOP | `f_tvalid && f_tready && f_tuser` | DP |
| **(e)** | 慢路径应用侧适配器入口 SOP | `srx_tvalid && srx_tready && srx_tuser` | DP |
| **(e2)** | 同上 **TLAST** = **整帧交付** | `srx_tvalid && srx_tready && srx_tlast` | DP |
| (d) | app UDP 帧缓冲末字提交 | `u_udp_split.uf_commit_word` (`rtl/udp_split.v:491`) | DP |
| (d2) | app UDP RX 口 SOP 可见 | `app_udp_rx_tvalid && app_udp_rx_sof` | DP |

时间基 = 工程**已有**的两个自由计数器, 不新造: FE = `gmii_free` (wrapper `:3056`),
DP = `dp_free` (wrapper `:3080`)。帧长由 `mac_rx_10g.dbg_rx_last_len` 独立锁存。

### 2.2 跨域标定 (本设计最关键的一步)

FE 与 DP 是**物理无关**的两个 156.25 MHz 域 (P7a 实测 ~5 ppm 差;
`board/ku5p_p7b_cdc.xdc:36-39` 整组 `set_clock_groups -asynchronous`)。

后台标定乒乓 (DP→FE→DP), 每 256 个 `dp_clk` 一轮: DP 翻请求 → FE 2FF 收到后把
**本域 `fe_free`** 锁进 `cal_fe_r` → DP 2FF 收到 ack 后把 **本域 `dp_free`** 锁进 `cal_dp_r`。
⇒ 一次标定给出**同一时刻**的一对数。换算:

```
Δ(跨域段) = (dp_c − cal_dp_c)·T_DP − (fe_b − cal_fe_b)·T_FE  (+ 固定偏置 β, 见下)
```

⚠️ **`cal_fe_b`/`cal_dp_c` 是"帧时刻"的锚点, 不是"快照时刻"的标定** (前者在 (b) 拍
锁 `cal_fe_r`, 后者在 (c) 拍锁 `cal_dp_r`)。这是本轮最关键的设计决定:

* 用**快照时刻**的标定对, 帧与标定相隔 ~0.1 s ⇒ 计数差 ~1.6e7 拍 ⇒ 即便按 P7a
  实测到 6e-6 的频率换算, 误差 ≈ `1.6e7 × 6.4ns × 6e-6` ≈ **300 ns** ——
  比要测的段还大, 量出来的会是"频率误差"而不是延迟。
* 用**帧时刻**锚点, 两者相隔 ≤ 1 个标定周期 (1.64 µs ≤ 256 拍) ⇒ 放大因子 ≤ 256 拍
  ⇒ 误差 ≈ **1e-8 ns**, 可忽略。

频率用**实测**而非标称: `T_FE` ← P7a 实测 `1.000025×10¹⁰ bit/s /64` =
**156.253906 MHz** (`P7A_RESULT.md:210`); `T_DP` ← P6b 实测 **156.2585 MHz**
(`P6B_ACCEPT.md` B2b)。

### 2.3 一条**已知的固定偏置 β** (如实登记)

乒乓的 FE 侧锁存与 DP 侧锁存之间隔着 `2FF` 同步链 ⇒ 两者是**同一时刻的近似**,
相差 `β ≈ 2~4 个 dp_clk`。代入推算可得 **`Δ测量 = Δ真 − β`** ⇒
**(b)→(c) 的读数偏小 β**, 即真值 ≈ `25.58 + (2~4)×6.4 = 38.4 ~ 51.2 ns`。
⇒ 该段在报告里标 **±26 ns**, 其余各段都是**单域内**计数差, 没有这个偏置。

> 为什么消不掉: 任何单比特 CDC 都自带一个"未知但恒定"的同步延迟; 要把它拆出来
> 需要一条**已知延迟**的参考路径, 本设计没有。

### 2.4 读数怎么取 (防真空零)

* VIO over JTAG (`vio_lat`, **6×128 位输入 / 6 个控制输出**), `.ltx` 随位流下载。
* **快照协议**: 主机**翻电平** `snap_req` (不是"1 再 0"!) → RTL 边沿检测 → DP 锁
  本域 + 向 FE 要一份 → FE 回执 → DP 装配 24 字并翻 `snap_ack`。
  **主机轮询到 `snap_ack` 变化才算取数成功**; 超时标 `ack=0` 且**不当读数用**。
  ⚠️ 施工实测: 用"1 再 0"会做**两次快照** ⇒ ack 翻两次回到原值 ⇒ 主机永远等不到,
  超时 3 s (**那 3 秒空窗会把背景帧放进来污染读数**)。这一条是本轮踩过的坑。
* 每代同时锁 **8 个事件计数器** ⇒ 判据"所有 tap 计数相等"才证明**锁下来的时间戳
  属于同一帧** (本轮的 `pair` 列)。
* ⚠️ Tcl 是 32 位 (`format %d/%X` 对 >2³¹ 静默输出 0) ⇒ **一个数都不在 Tcl 里转换**,
  输出十六进制字符串, 换算全在 Python (`scripts/analyze_lat.py`)。
* ⚠️ Vivado 会把宽探针网**按常量位切碎** (实测 `probe_in0` 变成 4 片、`probe_in4` 变
  32 片) ⇒ 必须按 `.ltx` 的引脚位表拼回去 (`scripts/gen_pinmap.py` → `pinmap.tcl`,
  逐位覆盖自检 128/128 无空洞)。
* 换算器的**自检**: `scripts/selftest_analyze.py` 用合成真值反推打包, 断言
  `(a→b)/(b→c)/(a→e2)` 三段逐位等于期望 (通过)。

### 2.5 激励 (不接线, 零改动)

链路 = 全系统**唯一一根** AOC: FPGA **J8 = SFP B = GTY X0Y5** ↔ 网卡 **`enp1s0f1np1`**
(闸 2 实测; J7 空着)。**本轮没有动任何线。**

* 激励 = 对端机上 **`ping6 -c 1 -s N ff02::1%enp1s0f1np1`** (全节点组播, 无需 ND,
  **普通用户即可**)。以太网帧长 (含 FCS) = `14+40+8+N+4 = 66+N` ⇒
  **N=34 → 100 B; N=92 → 158 B; N=1448 → 1514 B**。帧长由板侧
  `dbg_rx_last_len` **独立对账** (不靠我们自己声明)。
* **对端机的改动 = 零**: 没有加地址、没有改配置、没有 reboot、没有 raw socket
  (raw socket 实测 `PermissionError: Operation not permitted`, 且 `sudo` 需要密码 ⇒
  **本次施工没有 root**)。用完无需复原。
* 由 Vivado 的 Tcl `exec` 直接 ssh 过去发 (实测可行), 免掉两个进程交错。
* ⚠️ **一个真实的前置坑**: 烧板会复位 GT ⇒ 网卡 carrier 下/上 ⇒ Linux **重新给该口
  加 IPv6 link-local 地址**。地址不在时内核在 IPv6 输出路径就丢包
  (socket 层仍报 "transmitted", 而 `port_tx_packets` 一动不动)。
  ⇒ 脚本里加了"编程后轮询对端地址恢复"的前置检查 (实测 0 ms 恢复)。
  **这条是根因级的**: 没有它, 整个激励会静默失效。

## 3. ③ 分段延迟表

样本 = **4 轮独立板级取数** (每轮都重烧位流), 只取 `ack=1` + **8 个 tap 计数全等** +
**`fe_len` 等于请求帧长** 的样本。第 4 列是**本轮实测的拍数**(1 拍 = 域内一个时钟)。

| 段 | 拍数 | 换算 (ns) | 证据 | 读得/推导 |
|---|---|---|---|---|
| **(a)→(b)** XGMII `/S/` → MAC RX 输出 SOP 被接收 | **4 FE 拍** | **25.60** (跨 26 样本零离散) | `run*/LAT_HEX * pi0` 的 `ro_fe_b`−`ro_fe_a`; `T_FE`=6.39989 ns | **【读得】** FE 域内, 精确 |
| **(b)→(c)** MAC 输出 → `rx_classify` slow SOP | **4 DP 拍** | **25.58** (跨 26 样本零离散) | 帧时刻锚点对 (W21/W22) 换算; `T_DP`=6.39967 ns | **【读得】** 跨域, **±26 ns 偏置** (§2.3) |
| **(c1)** `vlan_strip` SOP → 在 (b)→(c1) 之中 | 包含在内 | — | `dp_vs_r` (W2) | **【读得】** |
| **(c)→(e)** classify → 慢路径适配器入口 SOP | **7 DP 拍** | **44.80** (跨 26 样本零离散) | W18−W3 | **【读得】** DP 域内, 精确 |
| **(e)SOP→(e)TLAST)** 适配器内部逐字播放 | **N字 × 1 DP 拍** | **6.3997 ns/字** | (B) 的仿射模型 (§5) | **【读得】** DP 域内, 精确 |
| (d) app UDP 帧缓冲末字提交 | **恒 0 次** | — | `evt_d = 0` 于**全部 64 个样本** | **【读得】** 但**本轮不可达**, 见 §7 |
| (d2) app UDP RX 口 SOP | **恒 0 次** | — | `evt_d2 = 0` 于全部样本 | 同上 |
| (cf) fast 支 | **恒 0 次** | — | `dp_cf_r = 0` 于全部样本 (IPv6 → slow) | **【读得】** 负对照 |

**SOP→SOP 流水和 = 25.60 + 25.58 + 44.80 = `95.98 ns`** —— 在**三种帧长、27 个干净样本**
上落在 **95.95 ~ 96.00 ns (跨度 0.05 ns)**, 这就是 **(A) 口径的"各段拍数相加"**。

> ⚠️ (b)→(c) 的偏置方向: `Δ测量 = Δ真 − β` ⇒ 真值 ≈ `38.4 ~ 51.2 ns`。
> 但**总和 (A) 与 (B) 不受影响**(它们由 (a)→(b) 与 (c)→(e) 两个单域段 +
> 同一套模型钉死); 只有"流水在跨域那一刀怎么切"有 ±26 ns 的不确定。

## 4. ④ 两个口径 (用户问的是 (B))

### 4.1 实测读数 (均值 / [min,max] / 样本数)

| 帧长 (含 FCS) | **(B) 首字节(a) → 整帧交付(e2)** | **(A) = (B) − 线上串行化** | n |
|---|---|---|---|
| **100 B** | **170.03** [166.37, 172.78] | 86.24 [82.59, 89.00] | 7 |
| **158 B** (TCP 载荷 100 B 的口径) | **217.57 ± 0.02** [217.55, 217.59] | **88.79** [88.78, 88.81] | 11 |
| **1514 B** | **1301.51** [1299.10, 1305.51] | 120.81 [118.39, 124.81] | 8 |

> **(A) 有两个口径, 两个都给**:
> * **(A)₁ = 各段拍数相加 = `95.98 ns`** (任务书的主定义) —— 在三种帧长、27 个样本上
>   落在 **95.95 ~ 96.00 ns (跨度 0.05 ns)**, 这才是"与帧长无关"的那个量;
> * **(A)₂ = (B) − 线上串行化**(上表右列) —— **随帧长增长** (86.2 → 88.8 → 120.8),
>   原因见 §5.3 (适配器播放速率 3.1% 慢于线速)。

* 158 B 那一行是本轮最硬的读数: **11 个样本、4 轮独立取数 (每轮重烧), 离散 0.04 ns**。
* 100 B / 1514 B 的区间厚度 = **恰好 1 个 DP 拍 (6.4 ns)** —— 是适配器逐字播放的
  **相位量化**, 不是噪声 (见 §5 模型: 两种值分别对应 N字 与 N字−1 拍)。

### 4.2 硬下限校验 (**必过项**)

硬下限 = `(8 + L) × 8 / 10.3125e9` (标称线速率; 实测线速率 +0.0025% ⇒ 真下限略小,
用标称是**保守**的)。

| 帧长 | 硬下限 | (B) 实测 | 通过? | 余量 |
|---|---|---|---|---|
| 100 B | 83.78 ns | ≥ 166.37 | ✅ | ≥ 82.6 ns |
| 158 B | 128.78 ns | ≥ 217.55 | ✅ | ≥ 88.8 ns |
| 1514 B | 1180.70 ns | ≥ 1299.10 | ✅ | ≥ 118.4 ns |

**64/64 个 `ack=1` 样本全部通过** (换算器里的 `硬下限校验` 段)。
⇒ **口径没有搞混**: 读数**总是大于**线上串行化时间, 说明量的是"首字节→整帧交付"
而不是"末字节的传输延迟"。

### 4.3 如果要"第一个 bit 出 SFP"这个口径

(a) 点已经在 PCS 输出**之后**了。从"帧的第一个 bit 离开对端 SFP"算起, 还要加:

```
t(首个bit出SFP → 整帧交付) = (B) + 8 × 0.77576 ns + L_PCS
                            = (B) + 6.21 ns + L_PCS
```

| 帧长 | (B) | + 前导串行化 | **= 读数 (不含 L_PCS)** |
|---|---|---|---|
| 100 B | 170.03 | +6.21 | **176.2 ns + L_PCS** |
| 158 B | 217.57 | +6.21 | **223.8 ns + L_PCS** |
| 1514 B | 1301.51 | +6.21 | **1307.7 ns + L_PCS** |

**`L_PCS` = CDR + 解串 + gearbox + RX 弹性缓冲 + PCS RX 到 XGMII 的延迟 = 本轮没测**
(见 §7)。这正是 §1 想要 DRP 的原因 —— 也是本轮唯一的实质口径缺口。

## 5. ⑤ 总预算表

### 5.1 (B) 的**逐 ns 精确模型** (三种帧长同时命中)

```
(B) = 95.98 ns            [流水: (a)->(b) 25.60 + (b)->(c) 25.58 + (c)->(e)SOP 44.80]
    + N字 × 6.39967 ns    [适配器内部逐字播放, N字 = ceil((L−4)/8); 相位决定 恰好 N字 或 N字−1]
```

| 帧长 | 内容字节 (去 FCS) | N字 | `95.98 + N字×6.3997` | 实测 (B) | 差 |
|---|---|---|---|---|---|
| 100 B | 96 | 12 | 166.38 **或** 172.78 (11 拍) | 166.37 / 172.78 | **0.01 ns** |
| 158 B | 154 | 20 | 217.57 (19 拍) | **217.57** | **0.00 ns** |
| 1514 B | 1510 | 189 | 1299.11 (188 拍) **或** 1305.51 | 1299.10 / 1305.51 | **0.01 ns** |

⇒ 模型在三种帧长上**同时命中到 0.01 ns**。这不是"拟合得好", 是**同一批整数拍数**。

### 5.2 预算表

**158 B 帧 (= TCP 载荷 100 B):**

| 项 | ns | 占比 | 来源 |
|---|---|---|---|
| 线上串行化 `(8+158)×8/10.3125e9` | **128.78** | 59.2% | **【推导】** 硬下限 |
| (a)→(b) | 25.60 | 11.8% | **【读得】** |
| (b)→(c) | 25.58 | 11.8% | **【读得】** (含 ±26 偏置) |
| (c)→(e) SOP | 44.80 | 20.6% | **【读得】** |
| 适配器播放 19 拍 (与串行化**重叠**) | — | — | 见下 |
| **合计 (B)** | **217.57** | — | **【读得】** |

⚠️ 注意: 上表**不能**简单相加 (`128.78+25.60+25.58+44.80 = 224.76 ≠ 217.57`) ⇒
**占比列之和 > 100% 是正常的**: 串行化那 128.78 ns 与适配器播放是**并行**发生的,
其中约 7.2 ns (即 §5.3 的 0.0242 ns/byte × 158 + 量化) 被重叠吸收掉了。
⇒ (B) **不是** "(8+L)串行化 + 各段" 的简单和, 而是
**"流水 + max(串行化, 适配器播放)"** 的形式 = §5.1 的模型。

**100 B 帧:**

| 项 | ns | 来源 |
|---|---|---|
| 线上串行化 `(8+100)×8/10.3125e9` | 83.78 | **【推导】** 硬下限 |
| 流水 (a→b + b→c + c→e) | 95.98 | **【读得】** |
| 适配器播放 11 或 12 拍 (相位量化) | 70.40 / 76.80 | **【读得】** |
| **合计 (B)** | **170.03** [166.37, 172.78] | **【读得】** |
| **(A) = (B) − 硬下限** | **86.24** [82.59, 89.00] | **【推导】** |

**1514 B 帧:**

| 项 | ns | 来源 |
|---|---|---|
| 线上串行化 `(8+1514)×8/10.3125e9` | 1180.70 | **【推导】** 硬下限 |
| 流水 | 95.98 | **【读得】** |
| 适配器播放 188 或 189 拍 | 1203.13 / 1209.53 | **【读得】** |
| **合计 (B)** | **1301.51** [1299.10, 1305.51] | **【读得】** |
| **(A) = (B) − 硬下限** | **120.81** [118.39, 124.81] | **【推导】** |

> `(A)` **不是常数**: 86.2 → 88.8 → 120.8 (随 L 增长)。这正是 §5.3 的机制 ——
> 适配器播放 (0.800 ns/byte) 比线上 (0.7758 ns/byte) 快得少, 差值
> `0.0242 ns/byte` 会随帧长累积。**(A) 的"与帧长无关"只对流水部分成立**
> (`95.98 ns` 在三种帧长、27 个样本上跨 0.05 ns)。

### 5.3 ⭐ 一条设计级发现 (顺带量出来的)

**适配器的放字速率 = 1 字/DP 拍 = 8 B / 6.39967 ns = 1.25008 GB/s = 10.0006 Gbit/s,
比 10.3125 Gbit/s 的线上速率慢 3.1%** ⇒ 大帧的尾延迟由**适配器播放**而不是线速决定。
证据: §5.1 模型里 (B) 对 L 的斜率 = `8×0.77576…` 不对 —— 实测斜率 ≈ 0.800 ns/byte =
`1/6.39967×8`, 与 `udp_split` 的播放器一字一拍**逐位吻合**。
⇒ 若要 10G 线速下的尾延迟贴线速, **`udp_split` 的播放器需要加宽到 2 字/拍**
(否则每帧仅播放就要多花 `L×(0.800−0.7758)` ≈ `0.024·L` ns, 1514 B 帧上就是 36.6 ns)。

## 6. ⑥ 变异结果 (观测链上的可编程延迟)

RTL 里有 `mut_sel`(选哪一段) / `mut_n`(延迟几拍) 两个 VIO 控制, 把**被选中的那一拍的
观测脉冲**推迟 `mut_n` 拍。⚠️ **它证明的是"锁存 + 换算链是忠实的拍计数",
不是"数据面里真有这么多拍"** —— 后者由 §4.2 的物理下界与 §5.1 的模型来证。
参考 = L=158 的 11 个无变异样本均值 (a→b=25.60, b→c=25.58)。

| 变异 | 选中的段 | 期望 | 实测 Δ(a→b) | 实测 Δ(b→c) | 结论 |
|---|---|---|---|---|---|
| `mut_sel=1 n=10` | (b) 拍 | 该段 +10 拍 | **+64.00** (=10×6.3999) | −63.99 (b→c 相应缩短) | ✅ **精确** |
| `mut_sel=3 n=10` | (c) 拍 | 该段 +10 拍 | +0.00 | **+64.00** | ✅ **精确** |
| `mut_sel=5 n=10` | (a) 拍 | 该段 +10 拍 | **−64.00** (a 后移 ⇒ a→b 缩短) | −0.01 | ✅ **精确** |
| `mut_sel=1 n=30` | (b) 拍 | +30 拍 | **+192.00** (=30×6.3999) | −192.01 | ✅ **精确 + 成比例** |
| `mut_sel=1 n=0` | — (禁用) | 与基线相同 | +0.00 | +0.01 | ✅ **直通** |
| `mut_sel=4 n=10` | (d) app 队列 | 该段 +10 拍 | +0.00 | −0.02 | ⚠️ **没抓到 —— (d) 恒不触发**, 等价变异, 如实报 |

* 每条都在 **4 轮独立取数里逐字复现** (r0/r1/r2/r3 全同), 离散 ≤ 0.02 ns。
* **`mut_sel=4` 没抓到是"等价变异"**: (d) = `u_udp_split.uf_commit_word` 在**全部
  64 个样本上恒 0** (IPv6 帧永远到不了 UDP app 队列) ⇒ 给它加延迟当然量不出任何变化。
  这一条**必须如实报成"没抓到"**, 不能算作"通过"。

## 8. ⑧ 需要用户做什么

**本轮不需要任何接线改动, 也不需要 root** —— 全部读数已经拿到 (线保持
`J8 ↔ enp1s0f1np1`, J7 空着)。

**要补上 §7 的 U1 (PCS 内部延迟) 的话, 需要你二选一:**

1. ⭐ **首选 · 不插拔**: 允许我做**第二轮构建时打开 IP 的
   `CONFIG.ADD_GT_CNTRL_STS_PORTS`**, 并且**先 `generate_target example` 抄官方
   example 顶层的连接值**来驱动那 45×2 个 GT 控制输入 —— 这样 DRP 才能读,
   `0x269` 才有值。代价: 一次 ~45 min 构建 + 一次烧板;
   风险: 那些值若抄错会动 TX 眼图 (本轮就是因为**没有权威来源**才放弃的)。
2. **可选 · 更贵**: 把线接回 `J7↔J8` 做板内自环, 再给我加一个板内 TX 发生器
   (需另一次构建)。这条**只有在你还想要"自己发、自己收"的确定尺寸激励时才有价值** ——
   本轮已证明**网卡侧 `ping6 -s N` 就能给出任意尺寸的帧**, 所以我不建议为了尺寸可控去动线。

**若还想让 (B) 的终点推到 app UDP/TCP 队列 (U4/U5)**, 需要**对端机的 root**
(配一个临时 IPv4 地址, 或给 `python3` 加 `cap_net_raw` 以便 raw-socket 注入) ——
本次施工**没有 root** (`sudo` 要密码, raw socket 被拒), 所以那一刀停在了慢路径适配器入口。

**建议的下一步里最便宜的一条**: §5.3 的 `udp_split` 播放器加宽到 2 字/拍 ——
它能把 1514 B 帧的尾延迟砍掉约 36 ns, 且是**纯数据面改动、判据现成**。
