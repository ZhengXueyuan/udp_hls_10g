## 1. `T_RUN` —— 退出码 1 的**真实来源**（要证据，不要猜）

### 1.1 退出码的来源（源码级）
`_proj_pcie/p6e_udp_pattern.cpp`（= 对端机上的同一份，md5 已核对）**只有两条 `return 1` 的路径**：

```
:178  if (frames == 0) { printf("  [FAIL] 一个包都没收到 ⇒ peer 没学到 / 板子没发 / 网段不对\n"); return 1; }
:179  if (bad)         { printf("  [FAIL] %llu/%llu 帧图案真失配\n", ...); return 1; }
```
本轮的原始日志（`p7b_gate4_2/accept/traffic_cmd.txt`）显示：**`收 1665 帧`、`[FAIL] 4/1665 帧图案真失配`、`TRAFFIC_RC=1`**
⇒ **来源是 `bad>0`（真失配计数），不是零帧**。

### 1.2 证据链：为什么 `bad` 出在**激励侧**
1. **收包率 0.091%**：工具 `收 1665 帧 / 17.17 s = 97 fps`，而同期板子在发 **106,000 fps**
   （板侧 `W20`(mac_tx_frames) × 网卡计数 × pcap 时间戳三口径一致）。**工具运行窗**（= `nic_B→nic_C`
   之间，含教学前的静默期）内**主机侧 NIC 数到 1,885,735 帧**（1,059,813,444 − 1,057,927,709 / 19.96 s
   = **94,466 fps**；扣掉静默期即 106k fps 的瞬时率）
   ⇒ **丢失发生在 socket 层之上/之内，不在线上**。
2. **它收到的帧是"连续"的**：1660 次"重对齐"**全部恰好 1472 B**（`2443520 = 1660 × 1472` 逐字）。
   ⇒ 每次重对齐只是**它的锚点落后一帧**（`p6e_udp_pattern.cpp:130-155`：匹配成功时 **`pat` 不推进**，
   所以每一帧都要走 resync，且每次都被记成"少了一帧"）⇒ 工具自报的 **"掉包 49.92%" 是它自己的
   记账产物**；真实接收侧丢失 ~99.9%（报告里引用的 49.92% **应作废**，它低估了 ~1000×）。
3. **首次失配点 = 缓冲容量**：第一个 `bad` 落在第 **1662** 帧 ≈ `8 MB ÷ (1518 B 帧的 skb truesize)`
   ≈ 1662 帧 —— 即"第一个队列容量装得下的连续块"正好用完的地方。
4. **之后是级联，不是 4 个独立事件**：`bad` 每收一帧 **+1**（1→2→3→4），帧号 1662/1663/1664/1665
   的时刻是 **6.6 / 10.1 / 13.6 / 17.2 s（Δ = 3.5 s）** —— 与 `resync` 失败时每次要走满
   `Σ_{k=32}^{65536}(k+32) ≈ 2.1×10⁹` 步（`:59-68` 的 O(win²)）的代价同量级。
5. **重同步窗只有 0.419 ms 的线上流量**：`65536 B ÷ (106,148 fps × 1472 B)` = **0.419 ms**
   ⇒ 该工具在 10G app 速率下**结构性地**不能承受任何 >0.4 ms 的接收停顿。
6. **板侧内容清白由独立口径给出**：F3 的 pcap 逐字节 **2999/2999**、偏移 0 起连续、覆盖 100%
   （`p7b_gate4_2/content_verified.txt`）。

### 1.3 ⚠️ 严格边界（如实说，不许拔高）
**工具运行的那 17 s 窗内，板侧流并没有被独立口径覆盖**（两次 pcap 分别在 12:41:56 与 12:52，
都在工具退出之后）。因此 log 里的 `bad` 在**形式上有两种解释**：① 工具接收侧失对齐（本单采纳）；
② 板侧流在那 17 s 内出现过 >64 KB 的跳变。判给**激励侧**的依据是 §1.2 的 1–5（量化吻合：0.091%
收包率 + 1662 ≈ 缓冲容量 + 级联/3.5 s 的形态 + 64 KB = 0.42 ms），**不是"已证否板侧"**。
⇒ 这条登记进 §6 的**残余未知**（要闭合它，需要"工具运行时同时抓包"的一次实验）。

## 2. `N_SELF` —— ±1 偏置的机理（判据的算术错？还是物理事实？）

**都不是**：它是**判据的前提不成立** —— 判据假定 `port_rx_good / port_rx_bad / port_rx_packets`
是**同一次原子快照**，而实测**单个 dump 内部**就不自洽：

| dump（本轮原件 `p7b_gate4_2/accept/*.txt`） | good + bad − packets |
|---|---|
| `nic_A` | **0** |
| `nic_B` | **0** |
| `nic_C` | **0** |
| **`nic_D`** | **+1**（39,603,532 + 1,020,633,510 = 1,060,237,042 = packets 1,060,237,041 **+1**） |

⇒ 三个字段**不是同一时刻读出来的**（NIC 的 RX 通路上有两个计数点，一次快照至多落在一帧"在飞"
之间 ⇒ 残差 ±1；顺序打印 + 一次 dump ~2.5 ms 的耗时也支持这一点）。**`N_SELF` 的 FAIL 与设计无关**：
板侧自己的记账自洽到**半帧以内**（`ΔW8 = 535,141 == ΔW20`；`ΔW9 = 787,727,056`，比 `535,141 × 1472`
少 **496 B = 半帧在飞** —— 快照锁存时刻的正常截断，不是丢字节）。
**它不是"第一帧必然如此"的物理事实**，而是**读侧的非原子性** ⇒ 判据必须带容差。

**修法（已落地）**：`|端点内残差| ≤ 1` 且 `|Δ残差| ≤ 2`，并把**两端点的残差打在判据行上**。
判别力不受影响：真缺陷（有一类帧记进 packets 却既不算 good 也不算 bad）会让残差**随帧数增长**
——4 s 窗 @106k fps 下 1% 就是 4000 帧，与 ±2 差三个数量级。

**反例实测**：
- `ns_self_plus1`（**真实形态**：`resid_D = +1`）⇒ 必须 PASS：`实测=2120001 + 0 - 2120000 = 1 (端点内残差 A=0 B=1)` ✅
- `ns_self_classgap`（1% 分类缺口，`resid_D = −21200`）⇒ 必须 FAIL：`实测=2098800 + 0 - 2120000 = -21200` ✅ 退出 1

## 3. `N_XCHK` —— 它现在在图什么？正确的参考源是什么？

### 3.1 判据写错了：它**结构性从未评估过**（不是 SKIP，是根本没打印）
旧守卫（`p7b_gate4_accept.sh` 原 `:550`）：
```bash
if [ -n "${NQ_NC+x}" ] && [ -n "${NB_NC+x}" ]; then     # NB_NC/NQ_NC 是 declare -A 关联数组
```
bash 语义：**`${assoc+x}` 只测下标 `0`**，而键是 `port_rx_good` 这类非数字串 ⇒ **恒为空** ⇒ `if` 永远为假。
本机 bash 实测（本轮真跑，输出原样）：
```
关联数组, 键=foo:  [${A+x}] = []            ← 恒空
关联数组, 键=bar:  [${C+x}] = []
普通数组, 下标=0:  [${D+x}] = [x]           ← 只有普通数组才成立
按真实键存在性判:     [${E[port_rx_good]:-}] = [42]   ← 修法
```
旁证：`grep -c XCHK _proj_10g/notes/p7b_gate4_2/accept_run1.txt` = **0**（两轮验收的日志里**从来没有**这一行）
⇒ 上一轮报告写的 "N_XCHK SKIP（ΔW20=0）" **也不成立**（当时同样从未评估）。
**修法**：按真实键存在性判 `[ -n "${NQ_NC[port_rx_packets]:-}" ]`（现 `:674`），并加"未评估"的显式打印（`:685`）。

### 3.2 前提不成立之一：**主机侧不是独立的硬件计数**
`p7b_gate4_2/kernel_vs_hw_counters.txt` 两次采样**逐字相同**：

⇒ `ethtool -S` 的 `port_rx_*` **就是内核 netdev 计数的镜像**（与上一轮对 `port_tx_*` 的发现同族）

### 3.3 前提不成立之二：参考侧的**更新量子 ≈ 1 s**

⇒ 同一台机、同样长的 4 s 窗，参考侧给出的"走过的流量"与墙钟**差 ±0.7~1.0 s 的整档**

## 4. F4 的**独立口径** = pcap 时间戳（本轮读数）

- **为什么它独立**：抓包点在**驱动队列**（不在 socket），与"板侧 RTL 计数""激励工具的 socket"
  是**三条不同的消费者路径**；而且**逐帧时间戳**，没有 §3.3 那种刷新量子。
- **本轮两次实测**（都在同一位流、同一会话）：
  - `p7b_gate4_2/rate_probe.txt`（12:41:56）：3000 包 / 0.028306 s ⇒ **105,949 fps**
  - `p7b_gate4_2/content_verified.txt`（12:52）：2999 帧 / 0.028298 s ⇒ **105,944 fps**
  - 板侧自报（`W20`）同期 **106,000 fps**（±0.002%）⇒ **偏差 0.05% < 1%** ⇒ **F4 PASS**

### 5.1 B 组的口径注（**不许照抄算式的坑**）
`wrapper_p4.v:3708` 的注释写 `51 = 14+22 (snap_seq) + 3+12+4 (P7b 三束)` —— 这个算式**按"槽位空间"算**
（p7bdp 声明 12 个槽，其中**槽 2..5 留给 tx 束**在装配处填 `W41..W44`），**字数是 15 不是 19**：
`14+22+3+8+4 = 51`（装配项数已逐项数过：`fe/dp` 36 + `p7bfe` 3 + `p7bdp` 8 + `txsnap` 4）。
⇒ 谁要改这三束，**别把这个算式"修正"成 55 再加 4 项**（那会静默截断）。这是**读数注记**，
不影响 B1/B8 的判定（板级读回 51 字一致）。
