## 0. 一句话 + 推荐速览

> **单连接长流 = 只改一个常量**（`board/wrapper_p4.v:1170` 的 `.TX_BYTES(32'd1048576)` → `32'h7FFFFFFF` 或 `32'hFFFFFFFF`），
> **逻辑零改动**（参数只进常量比较/常量装载，`[读码]` 见 §2）；构建 1 次、BID `0x11→0x12`、烧回易失、跑老台架（**对端只需换参数**）。
> 长流下的**理论单连速率 = `1460×8×156.25e6/193 = 9.456 Gbps`**（= 线上载荷天花板 `1460/1538×10 = 9.4935 Gbps` 的 **99.61%**），
> 即 **RTL 层面没有"每帧气泡"可挤** —— 帧周期 `193 拍` = 线速几何本身（`[读码]` 逐拍预算见 §3）。
> 因此本刀的成败**不在 RTL 加速**，而在三件事：① 台架**别先撞自己的帽子**（`--check=seq` 逐字节复算封顶 **5.13 Gbps**，`[读码]` `p7b_pattern.h` 头注）；
> ② 窗口/BDP **别成帽**（`WIN_CAP = 49150 B` ⇒ 需 `RTT ≤ 41.6 µs`，`[读码]` 见 §4）；③ 速率判据**别写成空判据/环路恒等式**（见 §6）。

| 问题 | 答案（一行） |
|---|---|
| **Q1 怎么表达长流** | **推荐 (a)+(b 可选)**：把 `TX_BYTES` 常量调大（零逻辑改动、纯常量）；`AUTO_CLOSE` 默认保持 1。**(c) 运行时可写寄存器：本轮不推荐**（要新逻辑 + 跨域 + 当前 app 寄存器总线在板级被钉死）。**(d) 无界流**要新逻辑，留作条件性 Step 2。 |

| **Q3 窗口/BDP** | 硬帽 = **发送侧 `49150 B`**（`WIN_CAP=RING_CAP=0xBFFE`）/ **接收侧 `49152 B`**（`WIN_POOL`/`0x0C` 默认）。⇒ `RTT ≤ 41.6 µs`（9.456 Gbps）。**RTT 见证 = 长流内现取 `ss -ti` 原始行**（⚠️ 单位未回内核源码核过）；⛔ **禁止**用 `窗口/速率` 反推 RTT（环路恒等式）。 |

| **Q5 判据** | 板侧主判据 = **内窗** `ΔW51×8/(ΔW5/156.25e6)` + **帧周期** `P=ΔW43/ΔW20`；对端双口径 = sink 字节/NIC 硬件计数；**全 32 位计数器一律 mod 2³² 且记 raw 与 k**；⛔ 两条**空判据警告**见 §6.4。 |
| **Q6 风险/回退** | 回退三路：① 改回常量重建；② **直接重烧归档件** `p7b_retxfix_salvage/bits/8c8b6126__wrapper_p4.bit`（零构建）；③ 不加新宏（`ifdef APP_MODE` 已隔离默认构建）。时序核 = `check_p6e_timing.py` + WNS/WHS + 三类失败端点 0/0/0 + ⛔ **订正（必改 1）"零逻辑改动"的证据 = 最差路径同族性 + Routed 端资源逐数**（**不是**"综合资源计数与 r6-fix 逐数相同" —— r6-fix 的 synth 报告**全盘不存在**；见 §7.2-4）。 |

## 2. Q1 —— 「长流」怎么表达（四选项逐项评估）

> 硬约束先摆上：**WNS `+0.014` = 周期 6.400 ns 的 0.22%**（`[实测]`），且本流程**同输入重跑的重排幅度 ±0.4–1.3 ns**
> ⇒ **任何"新增逻辑"都可能把时序翻负**。所以选型的第一优先级 = **"这一刀动不动逻辑"**。

### 2.1 事实（先钉死"参数从哪来"）

`[读码]` `board/wrapper_p4.v:1170`：`app_pattern #(.TX_BYTES(32'd1048576), .TX_SEGSZ(12'd1460)) u_app (`
`[读码]` `.AUTO_CLOSE` **未被覆盖** ⇒ 取默认 `1'b1`（`rtl/app_pattern.v:31`）；`i_bad_frame` 板上恒 `0`（`:1182`）。
`[读码]` TX_BYTES 的全部使用点（`rtl/app_pattern.v`）：`:599`（`remain <= TX_BYTES`）、`:619-620`（`seg_len` 首帧长度选择）、`:402`（`seg_len!=0` 判据）。
⇒ **它是模块参数、只在例化点被覆盖；改它 = 改 `wrapper_p4.v` 一行常量。**

### 2.2 四选项对照

| 选项 | 怎么改 | **动逻辑？**（依据） | 代价 | 风险 |
|---|---|---|---|---|
| **(a) `TX_BYTES` 调大**（推荐） | `wrapper_p4.v:1170` 常量 `32'd1048576` → `32'h7FFFFFFF`（L1）/ `32'hFFFFFFFF`（L2） | **零新增逻辑**。`:599` 是常量装载；`:619` 的比较两端都是**常量**（`TX_BYTES > TX_SEGSZ`）⇒ 综合期常量折叠；`:402` 的 `seg_len != 0` 与本次改动无关 | 1 行 + **1 次重建**（≈20 min）+ 烧录；长度**不可运行时改** | 低。⚠️ 但"零逻辑改动"**必须用读数证明**（§7.2-4 的 **(a) 最差路径同族性 + (b) Routed 资源逐数**；⛔ **不是**综合资源计数 —— 那个基线不存在），不许只靠注释 |
| **(b) `AUTO_CLOSE = 1'b0`** | 例化点加 `.AUTO_CLOSE(1'b0)` | **零新增逻辑**（`if (AUTO_CLOSE) begin close_req<=1; end` 被常量折叠掉 ⇒ 是**删逻辑**不是加） | 同上 | ⚠️ **行为代价**：发满后 app 静默（`active<=0`、不发 FIN）⇒ 对端只能等超时 ⇒ sink 会走 **STALL 分支（RC=1）**，把"正常结束"误报成停流。**只适合当"半开/停流"专项的第二臂**，不适合主速率臂 |
| **(c) 新增"流长度"寄存器**（经 `app_ctrl` / 快照窗写） | 新寄存器 + 跨域 + app 的 `remain` 装载 mux | **动逻辑（DP 域）**。`[读码]` `wrapper_p4.v:1280-1282`：**app 寄存器总线在板级被钉死**（`app_reg_addr=0 / app_reg_wr=0 / app_reg_wdata=0`，注释逐字"P5 寄存器总线默认静止（板级无 CPU/AXI; 将来接 AXI-Lite 桥）"）⇒ 要做还得**先把 AXI-Lite 桥接出来**（跨域 + 地址译码） | **大**：桥 + 寄存器 + CDC + `remain` 装载 mux；**吃 DP 域时序** | 高。⚠️ `[实测]` DP 域最差终点 = **`u_app/stg_reg[33]/CE`**（r6-fix）—— 恰好是 app 的装配控制锥；往 `app_pattern` 里加 mux = 往最差族上加。**在 0.22% 余量上不划算** |
| **(d) 无界流（`STREAM` 参数：`remain==0` 时重装而不是 `active<=0`）** | 新参数 + 收帧分支一处 mux（`:676-683`） | **动逻辑（DP 域，小量）**：`remain` 多一个装载源 + 收帧分支多一个条件 | 小-中（1 次构建收口 + 时序复读） | 中。**它是唯一能突破 32 位上限的路子**（单次会话 > 4 GiB 或永不结束）⇒ 只在 §2.4 的判据下才做 |

**⚠️ 一个必须点名的坑（同名参数、相反语义）**：`app_udp_pattern` 的 `TX_BYTES == 0` = **连续不停**（`rtl/app_udp_pattern.v:36/:529-537`，板级例化点 `wrapper_p4.v:2508` 就用的 `32'd0`）；而 **`app_pattern` 的 `TX_BYTES == 0` = 一帧都不发**（`rtl/app_pattern.v:402` 注释与 `:403` 的 `seg_len != 0` 门）。
⇒ **不许"照抄 UDP app 的约定"把 TCP app 的 0 改成"连续"** —— 那会静默改变 `tb/tb_app_rx8_equiv.v:144/154/164/174/184/256`（6 处把 `TX_BYTES=0` 当"纯 RX 实例"用）的语义。要无界流就用**新参数名**。

### 2.3 推荐（本轮）

**主推 (a)：`TX_BYTES = 32'h7FFFFFFF`（L1 臂）**，理由：
1. **零逻辑改动 ⇒ 不碰 0.22% 余量**（唯一在硬约束下"免费"的选项）；
2. 单次会话连续流时长 = `2,147,483,647×8 / 9.456e9 ≈ **1.82 s**`（对比现状 **0.88 ms** ⇒ **×2070**），足够在**一个内窗**里把帧周期量到 ±0.01%（§6.3）；
3. 帧/字节几何**可整除核对**：`2,147,483,647 = 1,470,879×1460 + 307` ⇒ 每连 **1,470,880 帧**（尾帧 307 B），板侧 `ΔW51 ≡ 0x7FFFFFFF`（mod 2³²，**逐字节可判**，§6.3-C4b）。

**第二臂 L2：`TX_BYTES = 32'hFFFFFFFF`**（4 GiB−1，3.63 s）—— 它的**唯一增量价值 = 跨两次 32 位序列边界**（2³¹ 与 2³²，见 §7.3），
⇒ **建议 L1 先跑（速率），L2 单独一轮并提前声明"本臂会在 1.56 s / 3.38 s 处跨 2³¹ / 2³²"**，这样异常**可归因**（是"长流速率"还是"边界角"）。

**不推荐**：(c)（代价/风险比最差）；(b) 单独当主臂（会把台架判成 STALL）；(d) 留作条件性 Step 2。

### 2.4 什么时候才需要 (d)（判据，供用户裁）

只有当 L1/L2 读数**明确指向"流时长不够"**（例如：1.82 s 内速率稳住了、但更长的窗里出现与时间相关的劣化 —— 如 32 位回卷、对端窗口收缩、慢路径扫描/超时类事件的长时间尺度行为）时，才值得动 (d)。
⛔ **不许**在 L1 之前就上 (d)：那会**同时**动逻辑（时序风险）与动语义，把"长流速率"和"无界流语义"两件事搅在一起（本工程明令：一次只切一刀）。

## 3. Q2 —— 长流下会不会有"每帧气泡"？（RTL 逐拍预算）

### 3.1 先回答"TCP 的帧周期是多少"

**结论：`193 拍/帧`，与 UDP 构型**逐数相同**（因为两者线上帧长完全一样：1514 B MAC 帧 + 4 B FCS = 1518 B）**。

- `[实测]` 线几何：`1(前导) + 190(内容) + 2(IFG) = 193` 拍（1518 B 帧），UDP 构型实测 `ΔW43/ΔW20 = 193.0000`（J0）。
- `[读码]` `mac_tx_10g.v`：`stat_tx_words` **每拍 +1**（`:329-330`）⇒ `W43` 在时间上就是"拍时钟"；**线饱和时** `ΔW43/ΔW20` 恰 = 帧周期；线不饱和时它是"周期的倒数形式"（= 1/线占空 × 193 的关系）。⚠️ `p7b_bench` 轮已登记"**本构型下这个数易被读成几何（差 5.5×）**"——本件沿用其口径：**主判据用 `P = ΔW43/ΔW20`，并同时打"线占空 = 193×ΔW20/ΔW43"**。
- **TCP 线上载荷天花板** = `1460/1538×10 = 9.4935 Gbps`；按 193 拍/帧 ⇒ **`1460×8×156.25e6/193 = 9.4560 Gbps = 天花板的 99.61%`**（拍量化吃掉 0.39%）。

### 3.2 逐拍预算（`[读码]`，`P7B_10G` + `TCP_TX_OVL` 构建；相对时间轴，`cycle 0` = 上一帧尾字被 app 消费的拍）

| cycle | 事件 | 依据 |
|---|---|---|
| 0 | 尾字被 app 消费（本帧终点 = 上一帧的 cycle 193） | `app_pattern.v:764-774` |
| 1 | **收帧**（`need==0` ⇒ `frames++`、`op_pend<=1`、装下一帧长度） | `:669-703`（`:676-683` 是 `remain==0` 分支） |
| 2 | **opener**（0 载荷占位字，`tkeep=8'h00`）呈交并被 pipe 收下 | `:403, :541-544, :748-751`。⚠️ 它**不是线上的一个帧**（帧器只按 `pop8(keep)` 计长 ⇒ 不入 FIFO/不推 seq）——`[实测]` pcap 侧"每连 1 个 0 载荷 opener"**在线上不存在**（`P7B_BENCH/ACCEPT_FIRST_RUN.md` §2a-1） |
| 3 | **首载荷字装载**（`asm_go` 被 `!op_pend` 挡了一拍；`a2_ldw` 整字 1 拍） | `:449-453, :705-719` |

**独立的第二条账**：`app` 每帧呈交 **184 拍**（1 opener + 182 满字 + 1 尾字），非呈交拍 **9 拍** ⇒ `184+9 = 193` ✓ 占空 `184/193 = 95.3%`；
RX 引擎每帧接受同样 184 拍、`RX_FIN` 5 拍完全藏在 app 的 193 拍周期内 ⇒ **两侧同拍锁死，谁也快不过谁**。

### 3.3 交叉核对与误差带

- `[实测]` 唯一的**锚点**：r6-fix `--nocheck` 臂 **1 MB / 0.883 ms**（719 帧：`718×1460+296`）⇒ 反推 **P ≈ 192.0 拍**。
  本件推值 `193` 与它差 **1 拍（0.5%）**，落在"0.883 ms 短窗"的测量误差带内（该读数由 sink 的墙钟给出，µs 级分辨率 + 起止定义不明）。
- `[读码]` `stc_dl.sh` 的 `GEOM_NOPCAP_BOARD` 行会在长流里**直接给出** `cpf = ΔW43/ΔW20` 与 `fps` ⇒ **P 的精确值是长流的第一号产物**（我方的模型值 `193` 与实测的差距 = "模型对错的判据"）。
- ⇒ 本件口径：**P ∈ {192, 193, 194} 内，理论速率 `9.407–9.500 Gbps`；取 193 为工作点（9.456 Gbps）**。

### 3.4 瓶颈在哪一级（长流稳态）

| 级 | 每帧预算 | 折算 | 备注 |
|---|---|---|---|
| **app（A2 生成 + 呈交）** | **193 拍** | 9.456 Gbps | 含 **9 拍非呈交拍**（收帧 1 / 首装载 1 / RX_FIN 净 3 / 尾字处理净 4〔含装载拍〕） |
| **RX 引擎（收帧进 FIFO + 校验和）** | **193 拍** | 同上 | 与 app 同步（pipe 1 深，无旁路） |
| **TX 引擎（乒乓双 bank 发帧）** | **191 拍**（`T_HDR 6 + T_PAY 183 + T_TAIL 1 + T_DONE 1`） | 9.555 Gbps | `tcp_tx_frame.v:941-1061`；**比线快 2 拍 ⇒ 不是瓶颈** |
| **线（XGMII）** | **193 拍** | 9.456 Gbps（载荷） | `mac_tx_10g.v`；**与 app 同级 ⇒ 并列瓶颈** |
| **对端 ACK 回流**（下行必要） | 每 2 段 1 个 54 B 纯 ACK | RX 侧负载 ≈ 5% | `[读码]` 板侧对纯 ACK **不应答**（`P7B_BENCH/ACCEPT_FIRST_RUN.md` §2a-1 pcap 逐帧：板→对端无 ACK）；⚠️ 上行数据另计（`tcp_rx` 190 拍/段 = 9.605 Gbps，`[读码]` 出处 `P7B_STAGEB_RX8_REVIEW.md`） |

**⇒ 结论（Q2）**：**单连接理论可达 9.456 Gbps = 天花板的 99.61%，瓶颈 = 线本身（并列 app）**。
**"每帧气泡"在当前 RTL 里已经没有了**（A2 + `TCP_TX_OVL` 两刀吃掉了）；**但帧内余量为 0** ⇒ 长流实测若低于 9.456，扣分点**只可能来自**：
① 帧间额外的控制帧（ACK/wu/FIN —— 下行单流情形下板侧只有收尾 FIN）；
② 帧边界被窗门停拍（`win_open=0` = 在飞 ≥ 49150 ⇒ 见 §4）；
③ 台架/对端反压（sink 跟不上 ⇒ 对端窗收缩 ⇒ 板停）；
④ 32 位边界（§7.3）；
⑤ ⭐ **RTO 全窗重放（必改 2 新增；`[读码]` 结论，⛔ 板级读数 = 直到本轮为止从未有过）** ——
   `rtl/tcp_tx_frame.v` 的 `rto_timer` **没有任何 ACK 复位点**（全部写点 = `:735`(复位) / `:749`/`:1651`(cfg_up 清) /
   `:783`/`:1710`(svc 装载) / `:840-848`/`:1825-1833`(扫描递减+装载) —— **无一是 ACK**）；
   扫描装表门 = `:1823` `scan_estab && ((rb_snd_wnd != 16'd0 && rb_snd_nxt != rb_snd_una) || fin_retx_pend[scan_id])`
   ⇒ **饱和流里 `snd_nxt - snd_una` 长期非零 ⇒ 定时器常装** ⇒ `RTO_LIM = 12207`（`:183`，`ifdef DP_156MHZ`）
   ≈ **20 ms @156.25 MHz** ⇒ 每 20 ms 一次 `svc_rewind` + **`replay_full`**（`:780` = RTO 触发时 `!retx_req` ⇒ 全窗；
   `:389`/`:539`/`:542`/`:544` 逐字"**不受预算约束**"，`RETX_SPAN=4'd3`（`:234`）那点预算**绕过了**）⇒ 整窗 ~33 帧重放。
   **量级（`[推值]`）**：L1 流 1.82 s ⇒ **~90 次 RTO** ⇒ 冗余率 `ΔW15/ΔW51 ≈ 1.002`（~0.21% 速率损失）、`ΔW55 ≈ 90`。
   ⛔ **本条的强度 = 读码（"待证/未测"）**：**没有一条板级读数** —— 原因见 §8-9（已入库的长流全都 ≤ 20 ms/连接，
   这个时间尺度是本轮的**第一次覆盖**）。⇒ 判据侧同步改写 = **C6**（§6.1）。
**这五条正是长流要量/要排除的东西。**

### 3.5 已考虑并**否决**的"再快一点"

- **`TX_SEGSZ` 改 1456（8 的倍数，消掉 4 拍逐字节填充）**：app 侧 `193→189` 拍，但**线侧仍是 193**（`1510+4+12+8 = 1534 → ceil(1514/8)=190` 内容字 ⇒ 1+190+2 = 193）⇒ **净收益 ≈ 0**（甚至因为载荷变小：`1456/193` vs `1460/193` ⇒ **−0.27%**）。⛔ **不改**。
- **缩短 `RX_FIN` / 让 opener 穿过 `RX_FIN`**：动 `tcp_tx_frame` 的状态机或加第二个 `checksum16` ⇒ **新逻辑 + 新面积**，收益 ≤ 3 拍/帧（1.5%）。**只在长流实测确认"帧周期 >193"之后**才值得议。

### 4.3 怎么在长流实测里**现取 RTT**（见证配方）

**主见证 = 长流窗内的 `ss -ti` 原始行**（台架**已经**逐 0.5 s 采 `ss -tinma`，落 `/tmp/ss_<TAG>.log`，见 `stc_dl.sh` 的 `SS_T` 行）：
1. 取**传输窗内**（`t0_snapshot` 与 `t1_snapshot` 之间）的 `SS_T` 行，抄 `rtt:` / `rttvar:` / `rto:` / `ato:` **整行原文**（不许只抄数字）；
2. ⛔ **单位必须先钉死**：本工程登记过"`minrtt 6–8 / srtt 16–27` **单位未回内核源码核**"（`P7B_HANDOFF.md`）。**钉法**（任选其一，都要落盘）：① 同窗内 `rto:` 与内核 `TCP_RTO_MIN`（200 ms）比对 ⇒ 反推单位；② 同窗内做一次**已知量级**的对照（如 `ping` 的 95–140 µs，见下）。
3. **旁证（独立、但不是 RTT）**：板侧 ping 实测 `0.095–0.140 ms`（对端→板，**含板慢路径处理**）⇒ 链路 RTT 的**上界**；
4. ⛔⛔ **禁止**用 `在飞字节 / 速率`（或 `窗口 / 速率`）反推 RTT —— 那是**环路恒等式**（`credit ≈ win − rate×RTT`，本工程 2026-10-07 已把这条证据降级为"**不携带余量信息**"）。它只能当**形态描述**，不能当 RTT 见证。
5. **判定用法**：`RTT_witness ≤ 41.6 µs` ⇒ **窗不是帽**（本次读数可用来判"逼近线速"）；
   若 `> 41.6 µs` ⇒ **本次读数被窗帽限住**，读数只能写"**窗帽下的速率**"，并把它当"要解决窗口"的证据（而不是"板子不行"）。

### 6.2 回卷规则（`[读码]`，逐条钉死）

- 板侧计数器**全 32 位**；**任何两时刻差值一律 mod 2³²，且同时落 raw 与回绕次数 k**。
- **本刀相关计数器的回卷门槛**（@9.456 Gbps 载荷 / 156.25 MHz）：

| 字 | 含 | 速率 | 2³² 回卷窗 | 本刀注意 |
|---|---|---|---|---|
| `W5`（gmii 自由计数） | 时钟 | 156.25 M/s | **27.487 s** | **时基**；内窗 ≤ 2 s ⇒ 安全 |
| `W43`（TX 域每拍 +1） | 时钟 | 156.25 M/s | **27.487 s** | 同上 |
| `W51`（app 发字节） | 载荷 | 1.182 G/s | **3.63 s** | ⚠️ **L2 臂（4 GiB）会在这条上回卷一次** ⇒ 必须记 k |
| `W15`（TCP fast path 发字节） | 载荷 | ≈1.182 G/s | **3.63 s** | 同上 |
| `W20` / `W52`（帧） | 帧 | ≈0.81 M/s | ~88 min | 安全 |
| `W53` / `W54`（上行） | 载荷 | — | — | 下行单流里恒 0（**空判据**，见 C4） |

**两条"窗口纪律"**：① **速率（C1/C2/C3）一律取内窗**（两次快照都落在流内），**不要**用 pre/post 包围整个流算速率（`t0/t1` 与流边界之间有 ≈80–90 ms 的脚本开销 —— `[实测]` N1 跑 ΔW5 = 149.6 ms 而 sink 墙钟只有 68 ms ⇒ 包围窗会**系统性低估**）；
