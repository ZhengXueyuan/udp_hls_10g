## 2. 甲：pace 单位 / Stage 1 稳态 / app 天花板

### 2.1 单位 = **bytes/s** —— 四重独立证据（全部逐字）

**① 内核头**（对端**自己的** headers，两份内核版本都在）：
```
$ grep -n "sk_pacing_rate" /usr/src/linux-headers-7.0.0-34-generic/include/net/sock.h
   266:  *	@sk_pacing_rate: Pacing rate (if supported by transport/packet scheduler)
   493:	unsigned long		sk_pacing_rate; /* bytes per second */
$ grep -rn "SO_MAX_PACING_RATE" /usr/src/linux-headers-*/include/uapi/asm-generic/socket.h
   include/uapi/asm-generic/socket.h:76:#define SO_MAX_PACING_RATE	47
```
（`7.0.0-38-generic` 逐字相同 —— 即**运行中的那个内核**。）

**② 内核源码的 setsockopt 分支**（`linux-source-6.8.0`；⚠️ 版本低于运行内核，见 §6 的限度登记）
`net/core/sock.c`：`SO_MAX_PACING_RATE` 把**字面值直接写进 `sk_pacing_rate`**，无任何换算：
```c
		/* Pairs with READ_ONCE() from sk_getsockopt() */
		WRITE_ONCE(sk->sk_max_pacing_rate, ulval);
		pacing_rate = READ_ONCE(sk->sk_pacing_rate);
		if (ulval < pacing_rate)
			WRITE_ONCE(sk->sk_pacing_rate, ulval);
```
配套：`net/ipv4/tcp_output.c` 的 `tcp_small_queue_check()` 用
`limit = max_t(unsigned long, 2 * skb->truesize, READ_ONCE(sk->sk_pacing_rate) >> READ_ONCE(sk->sk_pacing_shift));`
（**字节**记账）；执行侧 `tcp_pacing_check()`（`:2574`）/ `:2756`/`:3475`。

**③ 运行期自证：`ss` 的 `pacing_rate` = 8 × 传入值（三档 pace、两次会话）**
我在对端**自己**读了这 5 份日志（逐字，非转述）：
| 日志 | 传入 `--pace-bps` | `ss` 逐字片段 |
|---|---|---|
| `/tmp/ss_WU_BASE_P100.log` | 100000000 | `… send 7535483871bps pacing_rate 800000000bps/800000000bps …` |
| `/tmp/ss_PACED_J6.log` | 100000000 | `… pacing_rate 800000000bps/800000000bps …` |
| `/tmp/ss_WU_BASE_P160.log` | 160000000 | `… pacing_rate 1280000000bps/1280000000bps …` |
| `/tmp/ss_PACED160_J6.log` | 160000000 | `… pacing_rate 1280000000bps/1280000000bps …` |
| `/tmp/ss_PACED230_J6.log` | **1073741824** | `… pacing_rate 8589934592bps/8589934592bps …` |

`8589934592 = 2^33 = 8 × 2^30` ⇒ `1073741824 B/s = 8.59 Gbps` 的帽，**不是** 1.07 Gbps。
（`ss` 打 bits/s、内核存 bytes/s ⇒ 8× 是纯单位换算。若 setsockopt 收 bits/s，`ss` 应打 `100000000bps` —— 与实测矛盾。）

**④ 达成率反证（不依赖 `ss` 的单位约定）**：`wuloop_p100_j6_run1.txt:8,:88` 逐字 `--pace-bps 100000000` ⇒
`SRC_SUM tx_bytes=600139784 … dur_s=6.000 tx_Mbps=800.186` ⇒ 达成 **100,023,297 B/s / 100,000,000 = 1.00023**。
**若单位是 bits/s（帽 = 100 Mbps），不可能达成 800.186 Mbps（8×）** ⇒ 单位只能是 bytes/s。

### 2.4 `app_pattern` 的 RX 天花板（RTL 逐行）

- `rtl/app_pattern.v:280`：`assign rx_tready = (rxs == 2'd0);`
- `:524-544` 状态机：`rxs==0` **1 拍**装载一个字（`rw_data/rw_n/rw_i`），`rxs==1` **每拍比 1 字节**；
  末字节那拍 `rxs <= 2'd0` ⇒ 满字 **1 + 8 = 9 拍**。
- ⇒ **8 B / 9 拍 = 0.8889 B/拍**；`8/9 × 156.25e6 = 138,888,888.9 B/s = 138.89 MB/s = 1111.1 Mbps`。
- 时钟域成立：`board/build_p7b_ku5p.tcl:145` 逐字
  `set_property verilog_define {APP_MODE=1 DEV_USP=1 PCIE_OBS=1 DP_156MHZ=1 P7B_10G=1 UDP_TX_OVL=1} [current_fileset]`
  ⇒ `dp_clk = 156.25 MHz`；`board/wrapper_p4.v:1170` 的 `app_pattern` 例化 `.clk(dp_clk)`。
- **该文件的唯一 `ifdef` 是 `DP_156MHZ`（`:291-295`），只改一个 LED 计时器常量 `ACT_TMR_INIT`，与 RX 通路无关。**

**⇒ 稳态/天花板 = 138,846,236 / 138,888,889 = 99.97%（审计写 99.97%，成立）。**
更利落的口径：理论 `8/9 × 156.25e6 / 1048576 = ` **132.4123 MiB/s**，实测逐秒 `132.406 / 132.407 / 132.437 / 132.406`
—— 四个数**逐个落在 5×10⁻⁵ 以内**。**没有任何 pace 值会被设成 `138,842,000 B/s`**；能解释 8/9 这个比值的只有 RTL 结构。

### 2.5 `1,073.043` 的缺口：**缺口成立，归因不能判**（🟡）

- 缺口：`132.414 − 105.188 = 27.226 MiB = 28.55 MB` ⇒ 按稳态速率折算 **0.2056 s**。（审计写"28.3 MB / 0.204 s"，同量级。）
- **但**：归因给「工具 `poll(&p,1,200)` 的一次 200 ms 超时 ⇒ 台架粒度、**不是板子**」**不成立为"已证明"**：
  该循环是 `POLLIN|POLLOUT` 双事件、`poll` 返回即 `send()`，**发送是 ACK 钟控的**（`send 7535483871bps` / `notsent:154104` 表明发送缓冲常态满载）。
  要发生 200 ms 超时，必须**连续 200 ms 既不可读也不可写** —— 那本身就是**板/链路侧 200 ms 无 ACK** 的事件，
  而不是"台架自己吞掉 28 MB"。对端 `ss` 的 `rto:201` ⇒ **201 ms 的 persist/RTO 与这 0.2056 s 同样吻合**。
- 原始件只有 1 s 粒度的 `SRC_T`（`:115-120`），**没有 sub-second 时间戳** ⇒ 我用现有材料**无法**把两者分开。
  **如实登记为"无法判定"**（审计把它写成"就是 poll 超时、不是板子"是**过度声称**）。**不承重**：甲的结论只需要 §2.3+§2.4。

### 2.6 「`2^30 bps` 帽子」叙事 = **证伪**（两条互相独立的路径）

1. **只读 Stage 1 原始件就能判死（与单位无关）**：秒 2–5 的增量是 1110.7–1110.9 Mbps。
   若帽是 `2^30 bps = 1073.74 Mbps`（bits/s 读法），**这 4 秒每秒都超帽 3.4%**，持续 5 秒的令牌桶不可能这样。
2. **单位是 bytes/s 时 `2^30` = 8.59 Gbps 的帽，且该值今天实测会塌**：

   `SRC_SUM tx_bytes=3538944 … dur_s=6.000 tx_Mbps=4.719`（**4.719 Mbps**），`ss` 打 `8589934592bps`。
   ⇒ 用 `2^30` 的帽子解释 `1,073.043` **算术上不可能**。

## 3. 我**证伪 / 修正**审计自身的地方

### 3.1 ⛔ 「头 9 ms 突发 = 137–144 MB/s = 天花板直接读数」复现不出来（口径错）

审计 §2.1/§2.3 写：`p0` = `1,232,704 B / 9 ms = 137.0 MB/s`；`p160` = `1,149,632 B / 8 ms = 143.7 MB/s`，
并据此说"板子能跑 ≥1.10 Gbps，800.186 只是这一刻的帽子"。

**我自写解析器逐包算（对端 `/tmp/wuloop_p0.pcap`、`/tmp/wuloop_p160.pcap`）：**

| 窗口（自主连接起见点 = 首个上行数据包） | p0 累计 | p0 速率 | p160 累计 | p160 速率 |
|---|---|---|---|---|
| +1 ms | 185,192 B | **185.19 MB/s** | 175,200 B | **175.20 MB/s** |
| +2 ms | 324,280 B | 162.14 | 322,468 B | 161.23 |
| +5 ms | 740,788 B | 148.16 | 739,888 B | 147.98 |
| +8 ms | 1,154,284 B | 144.29 | 1,155,096 B | 144.39 |
| **+9 ms** | **1,232,704 B** | **136.97** | **1,240,500 B** | **137.83** |
| +10 ms | 1,232,704 B（已停） | 123.27 | 1,240,500 B（已停） | 124.05 |

1. 审计的两个分子确有其数，但**分母不一致**：`p0` 用 `t≤9 ms` 的累计 ÷ **9 ms**，`p160` 用 `t≤9 ms` 的累计 ÷ **8 ms**
   （从**另一个**基线起算的桶）。⇒ 同一口径下应是 **136.97 / 127.74 MB/s**，不是 `137 / 143.7`。
2. 更根本的：**首毫秒 175–185 MB/s > 结构天花板 138.89 MB/s** ⇒ 这段"速率"里**含缓冲吸收**，
   **它按定义就不是"app 消费率"**。审计 §7-6 自己也把"+3.7% 超结构值"登记为未解释 —— 根因就是这个口径。
3. **结论方向仍成立**（这一格我给它留）：突发期确实跑过 100 MB/s（= 800 Mbps）以上 ⇒
   「800 Mbps 就是板子容量」仍被证伪。**但精度不能引用**：可用的说法是"**≥128 MB/s**"，
   不是"137–144 = 1.10–1.15 Gbps（±4%）"。

### 3.2 🟡 §1.5 的「不是板子」是过度声称 —— 见 §2.5（缺口成立、归因不可判）。

### 3.3 ⛔ §2.1 表里「上界（结构）≤ 1111 Mbps」与「天花板直接读数 137–144 MB/s（= 1100–1150 Mbps）」
**互相矛盾**（后者超前者 +3.7%）。§3.1 给出了仲裁：**直接读数那一格错**，结构上界（1111 Mbps）对。

### 3.4 （次要）`2^30 bps` 的比值：审计沿用了台账的"99.94%"，精确值为 **99.935%**（`1073.043/1073.741824`）。不影响任何结论。

## 5. 丙：`P100` 窗没关 + 跨会话复现（我逐 ACK 自算，未采信审计）

方法：在对端用 `python3 -`（stdin，不落盘）自写 pcap 解析器，只取 **`192.168.100.2:8080 → 对端` 的纯 ACK（`payload==0`）**，
统计其 window 字段与 >100 ms 到达间隔。**窗口未做缩放**（板侧 SYN-ACK 的选项逐字 `6012c0003baf0000020405b4` ⇒ 只有 MSS 1460，**无 wscale**）。

| `wuloop_p100.pcap`（本轮测, pace=100e6） | **411,058** | **29,584** | **0** | **0** | **1**（在 t=6.002 s，**传输已停**） |

| `wuloop_p0.pcap`（未 pacing） | **2,860** | **120** | **92** | 0 | **31** |
| `wuloop_p160.pcap`（160e6） | **7,278** | **288** | **38** | 0 | **30** |
| `paced2_j6.pcap`（arm D, 160e6） | **7,293** | **352** | **55** | 0 | **30** |

## 6. 我**没能**证明的部分（如实登记）
