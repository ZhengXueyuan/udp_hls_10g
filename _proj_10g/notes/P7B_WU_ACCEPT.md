  只有 `1076e50e`（= 修复臂，且 `mtime` 与烧录日志一致）。⇒ 他"无法现核"是**事实**（我复核了），不是托词。

#### 2.5 ⚠️ F1 详证：`W54` 失配 = **工具打洞**，不是板子缺陷

推理链（全部来自原始件）：
1. **判据**：`dW54 > 0` ⟺ `tx_bytes mod 65536 ≠ 0` —— **24/24 完美相关，无例外**（见 §1.1/1.2 两表）。
   `tx_bytes` 是 `send()` 实际收下的字节数；`chunk = 65536`（工具默认，`SRC_CMD` 未传 `--chunk`）。
2. **工具源码**（跑阶梯的那版 = `_proj_pcie/p7b_biz/p7b_tcp_src.cpp`）：
   `tx.fill(sbuf, chunk)`（**推进图案 LFSR 满一个 chunk**）→ `send(fd, sbuf, chunk)`；
   若 `send` 只收下 `n < chunk`（非阻塞部分写），**剩下 `chunk−n` 字节的图案被直接丢弃**，
   下一轮又从**新 chunk** 续 ⇒ **线上图案流里出现一个 (chunk−n) 字节的洞**。
   板侧校验器（`app_pattern` RX）无重同步 ⇒ **洞之后每个字节都算失配**（这正是 99.6%/99.4% 的形态）。
3. **直接物证**（另一轮、同一位流、同 pace 的原始 stdout `p7b_biz_tcpreg/wuloop_diag_p100.txt`）：
   `partial_sends=1326 skip_bytes=5718136 first_partial_at=327680`，同窗 `ΔW54 = 596 978 799`
   （≈ 该跑 rx 字节的 99.6%）—— 工具**自己数出了被丢的图案字节**。
4. **确定性旁证**：P50 四跑 `dW54 = 597 423 923` **逐位相同**、`tx_bytes` 亦逐位相同
   ⇒ 这是**可复现的工具行为**，不是板子的随机丢字节（板侧 `W3/W4/W19/W32/W35/W46/W47/W59/W60` 全 0，
   我核过）。
5. **后果**：`pace=100e6`、`160e6` 档的**图案内容**证据无效（两臂同等失效 ⇒ 不影响 A/B 的**速率**结论）；
   `0 / 50e6 / 134e6 / 1000e6` 档没有打洞（`dW54 = 0`）⇒ 那几个档的**内容**证据仍然干净。
   ⚠️ 这条**他一个字没写**；而它正好能解释"为什么板子在 1.19e9 字节上'失配'"这种**极易被误读成板子缺陷**的读数。
