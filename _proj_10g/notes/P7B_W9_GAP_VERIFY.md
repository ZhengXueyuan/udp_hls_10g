## 3. 问 3：`udpapp_mismatch`（`W13`）为什么没报警？—— **`W13==0` 是空判据**

### 3.1 读数：RX 方向**整个测量窗都没给 app 送过帧**

我从两块的 51 字重算（不是引用汇总表）：

| 窗 | ΔW10 (app 收帧) | ΔW11 (app 收字节) | ΔW12 (空帧) | ΔW13 (失配) |
|---|---|---|---|---|
| r1 / r2 / r3 / l20 | **0** | **0** | **0** | **0** |

而同窗**MAC 级**其实收到了 2 帧：`ΔW0 = +2`、`ΔW1 = +1188`、`W2 = 594`（线上长度判别器）、
`ΔW16 (srx_hls_bytes) = +1196` ⇒ 那 2 帧（594 B 各一）**走的是 HLS 慢路径**（ARP/其它），
**不是** app UDP 口（`ΔW10 = 0` 也证明它们没到 app）。
⇒ **`W13` 在速率窗内是"压根没在做校验"**，不是"校验通过"。

### 3.2 校验器本身**有没有牙**？—— **有牙**（所以这条才扎手）

`rtl/app_udp_pattern.v`（HEAD）RX 侧：比对是**连续图案流逐字节**（`rx_lfsr` =
`SEED` 起算的 xorshift），**帧边界不参与判据**（头注释原话），`stat_mismatch` 是
**粘滞字节数**；`i_en` 只在静止时翻转。⇒ 一旦流里少/多 1 字节，**永久失步**，
其后每个字节都算失配。
- 正证据：**教学期** `W13` 从 0 涨到 **1991**（工具把同一个 100 B 前缀重发 20 次 ⇒
  板侧 LFSR 只走一次 ⇒ 后 19 帧整段失配）⇒ **它确实对"图案流对不上"报警**。
- 对本缺陷的判别力（我给的数量级）：TX 每帧推进 LFSR **1472** 步，而线上载荷只有
  **1464** B ⇒ RX 每帧落后 8 字节 ⇒ 一旦喂给它，`W13` 会以 **≈ +1464/帧** 的量级涨
  （不是"只涨几个字节"）。⇒ 这条判据**本来能抓住本缺陷，而且抓得非常响**，
  **只是这一轮它没被喂**（RX 无流量）。

### 3.3 问 3 小结

| 子问 | 裁定 |
|---|---|
| RX 校验器的锚定 | 连续 LFSR、**不按帧重锚**、粘滞计数（失步后不会自愈） |
| RATE 轮 RX 在收吗 | **没有**（ΔW10=ΔW11=W12=0；MAC 级的 2 帧走了 HLS 慢路径） |
| `W13 == 0` 能证明载荷没坏吗 | **不能**（结构性空判据：测量窗内它一次也没比过） |

## 4. 问 4：修法对不对、够不够？—— **对；且我已在同台上验证"修后即好"**

### 4.1 合同原文（`rtl/fifo_sync.v:7-17`，逐字）

> `full` 是本拍的组合值, 不是"下拍还能不能写" … 若生产者的 `wr` 是**寄存器**
> (本轮决定、下拍落笔), 用本拍的 `full` 做空间门会有**一拍错位** … **空间门必须用 `full_next`**:
> `full_next` = **下一拍 `full` 的精确值** … 生产者判据: "本轮决定的推入下拍一定落笔" ⇔ `!full_next`。
> `ovf_pulse = wr && full`: 本拍有一次写**被拒** … 恒 0 才叫"无静默丢失"。

**修法（工作区版）与之逐条相符**：`gen_ok` / `nul_push` 的空间门换成 `txf_full_n`、
把 `.wr(txf_wr && !txf_full)` 的**预 AND 去掉**（否则 FIFO 内部 `ovf_pulse` 被结构性钉成 0，
= 工程坑 24「哑门」）、把 `ovf_pulse` 接成 `stat_tx_ovf` 计数器。
⚠️ 我的独立验证还补一条**合同没写、但结论依赖它**的推理：
`txf_wr(T) ⇒ !txf_full(T)` 之所以在修后成立，是因为**判据取的是 `full_next(T-1) == full(T)`**
（`full_next` 与 `full` 是同一组指针寄存器的两种组合式，恒等）—— 修后 FIFO 内部的
`ovf_pulse` 仍然恒 0，但**这次是生产者判据正确导致的恒 0，而不是被预 AND 杀掉的恒 0**。

### 4.2 会不会引入新问题？—— 逐条查过，**没有**

| 担心 | 结论 |
|---|---|
| 同一拍两笔写 | **不会**：每拍至多一个 `txf_wr` 脉冲；FIFO 仍自带 `wr && !full` 内部门 |
| 与 `nx_v`（RX 前瞻）冲突 | **无关**：`nx_v` 在 RX 侧，两码事；RX 侧不经过 `u_txf` |
| 时序/面积 | `full_next` 是**既有**端口（P6b F4 就加好了，`mac_rx_64` / `mac_rx_10g` 已在用）⇒ 无新逻辑 |

## 5. 问 5：同类缺陷普查（**只报不改**）—— 生产者写门用"本拍"空间信号

**判据**（两类分开，这不是同一件事）：
- **(甲) 真缺陷形态**：`wr` 是**寄存器脉冲**（本轮决定、下拍落笔）**且** 空间门用**本拍**的
  `full` **且** 被拒时生产者自己的账（计数/指针/状态）已经前进 ⇒ **静默丢字**。
- **(乙) 安全形态**：`wr` 是**组合**握手（`wr = tvalid && tready`，而 `tready` 里含 `!full`）
  ⇒ 被拒 = 握手不成立 = 数据仍在生产者手里 ⇒ **不丢**（FIFO 内部 `wr && !full` 与
  生产者的 accept 条件**逐字同式**）。
