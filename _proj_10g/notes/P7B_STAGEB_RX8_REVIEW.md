## 1. 逐条攻击

### 1.1 ⚠️ "逐字节等价"的表面有多大（#1）—— **挡不住（作为无条件陈述）**

**反例已跑出来**（新门：`sim/p7b_stageb_rx8_review/run_evphase.bat`，两次构建各 1 跑）：

| 实例 | 刺激 | A（默认）| B（`P7B_10G`）| 判据 |
|---|---|---|---|---|
| `u_ctrl` | `ev_up` **压在握手拍**（作者门同款）| rxb=48 mm=0 | rxb=48 mm=0 | **A ≡ B**（控制组）|
| `u_mid` | `ev_up` 在握手后**第 4 拍**（默认构建此刻 `rxs==1`，正在逐字节比）| **rxb=44 mm=28** | **rxb=48 mm=32** | ⚠️ **A ≢ B** |

机理（TB 自己打印的运行期证据，不是推断）：

```
EVID mid ev_cycle: tready_mid=0   <- 默认构建: ev_up 那一拍 rx_tready=0 ⇒ rxs==1 ⇒ 撞在比较窗里
EVID mid ev_cycle: tready_mid=1   <- P7B_10G : ev_up 那一拍空闲
```

逐行核实（`rtl/app_pattern.v`）：`ev_up` 块在 `:530-532` 写 `rx_lfsr <= SEED; rxs <= 0`；
串行比较分支在 `:736-743` **无条件**写 `rx_lfsr <= xs_next(rx_lfsr)`（`:739`）⇒ **同拍后写覆盖前写**
⇒ 复位被**丢掉**。作者笔记 §1 那句"串行路径在该拍**不写** `rx_lfsr`（只写 `rxs<=1`）"**只对握手拍成立**：
握手拍走的是 `:732-733` 的 `else rxs <= 1`（确实不写 lfsr），但**比较窗内**走的是 `:736` 的 else 分支（写 lfsr）。

**后果**：同一逻辑刺激（同一字序 + 同一"事件相对相位"）下，两构建的
`stat_rx_bytes`/`stat_mismatch` 不同 —— 而这两个计数**就是快照字 W53/W54**（板级判据的读数面）。
**方向**：B **应用**每连接复位（= 文档意图 "RX 图案流每连接重置"），A **静默丢弃**复位（既有 quirk）。
⇒ 这不是"B 变坏了"，而是**"逐字节等价"这句话在相位维度上不成立**，而作者的门只覆盖了相位空间的一格。
（该窗在 DEL→ADD 背靠背/同槽重连时真实可达：`ev_up` 由 `app_ctrl.o_ev_up` 单拍脉冲驱动，
与 RX 字流**无对齐关系**；旧连接的残余字可能仍在 frame_fifo 里排出。）

**逐数对账**（证明这不是"两构建速率不同"的伪差异，而是**每 1 个字节都能被复位丢失解释**；
队列 = `word0,1 = SEED[0..15]`，`word2 起 = 从 SEED 重开`，`wd[k]=SEED[8(k-2)..]`（k≥2））：

| 构建 | word0/1 | word2 | word3/4/5 | 合计 |
|---|---|---|---|---|
| **A**（复位被丢） | 8+8 字节，mm 0 | 逐字节 4 拍后**被弃**（`:736` 分支的 `ev_up` 撞车）⇒ 记 **4 字节 / mm 4** | 期望序列**继续走旧位置**（`M^20·SEED` 起）⇒ 3×8 字节全失配 | **rxb 8+8+4+24=44 / mm 4+24=28** ✅ |
| **B**（复位生效） | 8+8，mm 0 | 宽拍比完（旧期望）⇒ 8 字节 / **mm 8** | 期望被重置到 SEED **起点** ⇒ 3×8 全失配 | **rxb 48 / mm 8+24=32** ✅ |

（两列都逐字对上实测：`A=44/28`、`B=48/32`。）

**不能靠加固修掉**：B 里根本不存在"满字的比较窗"这个状态 ⇒ 无法复现 A 的丢弃行为。
唯一彻底同行为 = 让**默认路径**也别丢复位（= 改默认构建，另立项）；否则**必须收窄口径并登记**。

**最小反例**：见上表（3 个字+3 个字的 6 字队列 + 12 拍字间隙 + 单发 ev_up；
`runA/stats.txt` vs `runB/stats.txt` 只差 `MID` 那一行）。三次重跑逐字相同。

### 1.2 `rx_tready` 一字未动 / 背压相位（#2）—— **挡得住**

- `rx_tready = (rxs == 2'd0)`（`:437`）**逐字节确认未改**（`git diff` 里该行不在改动集）。
- ⚠️ 任务里点名要拆的 **`rx_ld`/前瞻寄存器在 TCP 版不存在**：`grep -n "rx_ld\|nx_v" rtl/app_pattern.v` = 0 命中
  （`nx_v` 只在 `rtl/app_udp_pattern.v:577,613,635,658`）。TCP 版 RX 是"取值拍锁存 `rw_*` + 比较态 `rxs==1`"，
  **没有第二个消费者、没有前瞻装载** ⇒ UDP 版必须改 `rx_tready` 的那条理由在这里没有对应物（作者笔记 §… 的这句成立）。
- **会不会采到不同的上游字？** 不会：两构建的消费都**只**由 `d && ready` 握手推进
  （反例门的队列驱动、作者门 5 个实例的驱动都是"只在真握手推进"），且 `rx_tready` 是**同一表达式**
  ⇒ 同一字序。作者门的"8 文件逐字节相同"里 5 个 `acc_w*.txt` 正是这条判据（丢/重/乱序会显形）。
- **上游真的能在 1 拍/字下工作吗**：真上游链 = `tcp_echo`（`fwd_rd = S_FWD && tvalid && tready`，
  `frame_fifo` 组合读）→ `rds` 的组合读 FIFO 本身支持 1 字/拍；写侧 `snap/rollback` 与读侧无关。
  ⇒ **无新增危害**；唯一新增**要求**是"上游需能持续 1 字/拍"（见 §1.8/#8 与 §3-③）。

### 1.3 ⭐ `&& !ev_up` 硬化（#3）—— **挡得住（针对握手拍那一格）；但覆盖有界**

- **逐行核实为真**：`ev_up` 撞车那一拍如果走 `:720` 的宽分支，会写 `rx_lfsr <= rx_lfsr_8`（`:725`），
  它在 `ev_up` 块（`:530-532`）**之后** ⇒ 后写胜 ⇒ 复位被盖掉；而串行路径在该拍写的是 `rxs <= 1`（`:733`），
  不碰 `rx_lfsr` ⇒ 复位生效。**两语句块的先后（块序 = 优先级）+ NBA 后写胜**，作者的因果链成立。
- **变异 F（去掉让位）恰 1 红且红的是 EV 判据**：我在自己的副本里复跑，**逐字复现**
  （`[PASS] negctl-F: exactly 1 red` + `[PASS] negctl-F: the red is the EV judge`，
  红行 = `[FAIL] EV zero mismatch`）⇒ 该硬化**有牙**，不是装饰。
- **EV 判据的覆盖够吗**：**不够**。EV 判据只验"`ev_up` 落在握手拍"这一格；#1 的反例证明**另一格**
  （落在比较窗内）两构建分叉且**没有任何判据看得见**（作者门里没有这一格；我补的门才有）。
- **`ev_down` 呢？** 逐行核：`ev_down` 在 RX 侧**只**写 `closing`（`:589-591`，纯 TX 侧收尾标志），
  不碰 `rx_lfsr`/`rxs`/`rw_*`/计数器 ⇒ **对 RX 无作用**，作者笔记这句正确。
  **DEL→ADD 背靠背（坑 9/14）**：其 RX 侧唯一事件就是 `ev_up` ⇒ 归入 #1 的相位洞（已在反例门里复现）。

### 1.4 `xs_next8`/`xs_word8` 与 UDP 版"逐字节相同"（#4）—— **挡得住（已独立证明）**

**是同一份代码**（不是巧合）：我解析两文件的函数体并逐位比对 ⇒ `IDENTICAL`。
⇒ **两份相同 ⇒ 会一起错**，所以"两边抄的一样"零证据力。**我做了独立证明**（`sim/p7b_stageb_rx8_review/verify_xor_net.py`）：

```
V1 xs_next8 vs 8x xs_next on 64 basis vectors + 0 : OK (complete for linear maps)
V2 xs_word8 lane k == (xs_next^k(s))[31:24], 8 lanes x 64 basis : OK
V3 xs_next8 / xs_word8 vs app_udp_pattern.v : IDENTICAL
V4 XOR terms: xs_next8=1392, xs_word8=891, total=2283
V5 100000-byte trajectory, word+advance both nets : OK
```

- **V1/V2 是完备证明，不是采样**：两个函数都是"若干 `s[j]` 的 XOR" ⇒ 对输入位**线性**；
  线性映射只需在 **64 个基向量**上相等即处处相等。我对 64 个 `e_j` **全部**核过（+ 0 向量必须为 0）。
  这比"跑一条 SEED 轨迹"强：SEED 轨迹只是 2⁶⁴−1 个状态里的一小段，**线性网的误差完全可能在这段上不显形**。
- **"2283 这个数能证明什么"**：**什么也证明不了** —— 它只是项数统计（我复算 = 1392+891 = 2283 一致）。
  它证明的是"生成器两次输出一致"，不是"网是对的"。**能证明正确的是 V1/V2（基向量完备）**。
- 结论：RTL 里那 2283 项 XOR 网**逐位正确**；`rx_exp_word` = 逐字节路径第 k 拍期望字节，
  `rx_lfsr_8` = 8 步推进，**数学上恒等**。

### 1.6 X 态（#6）—— **挡得住（硬件）/ 有界（仿真）**

- 宽路径 `!==`（`:460-467`），串行 `!=`（`:737`）；**二值数据下逐位等价**（作者门已证 + 我的代数证明）。
- **有 X 时**：`!==` 返回确定 1（记失配）；`!=` 返回 X ⇒ `if (X)` **不执行**（不记失配）⇒ 分叉。
- **方向**：10G 构建**只会多报**失配（把 X 当失配），**永远不会漏报** ⇒ 不会掩盖真缺陷，
  只可能在仿真里制造**假红**。硬件（位流）无 X/Z ⇒ **对板级无作用**。
- 结论：作者的登记（§5.5）**准确**；我另记一条**使用约定**：未来任何"10G 构建 `stat_mismatch == 0`"
  类的仿真判据，若上游有 X 污染，红的原因可能是这条**而不是**真缺陷（查 X 前先查上游复位/未初始化读）。

### 1.7 算式与 `tcp_rx` 190（#7）—— **挡得住**

**自己数一遍 RTL**（`rtl/app_pattern.v:712-743`）：

```
满字 (pop8(tkeep)==8): 宽路径 1 拍/字 (接受拍即比较完，rxs 保持 0) ⇒ 1
尾字 (n=B, 1..7)     : 1 拍接受 (rxs<=1) + B 拍逐字节 ⇒ 1+B
0 长字              : 1 拍
⇒ 段 = 1460B = 182 满字 + 1 个 4B 尾字 ⇒ 宽 182×1 + (1+4) = 187 ；默认 182×9 + 5 = 1643
```
实测复跑（两构建各 1 跑）：`runA/rate.txt = 1643.000 cyc/seg`、`runB/rate.txt = 187.000 cyc/seg` ✅ 与算式逐项吻合。
**"5" 的来源**：尾字 = 1 拍取值 + 4 拍逐字节（不是 5 拍比较）——作者的写法正确。

**`tcp_rx` 的 190**（任务点名核）：读 `rtl/tcp_rx.v` —— `localparam S_HDR/S_PAY/...`（`:167`）、
`s_axis_tready = (S_PAY) ? (m_axis_tready || !emit_v) : (S_TAIL) ? 0 : ((S_HDR && wcnt==6) ? (m_axis_tready || !emit_v) : 1'b1)`（`:381-385`）。
结构 = **w0..w6 七个头字**（S_HDR 收：w0..w5 **无条件 1 字/拍**，**w6 要等下游空**——那条"跨帧角例"）
+ **183 个载荷字**（S_PAY，下游 ready 时 1 字/拍）⇒ **190 拍/1460B 段**成立（**稳态**，下游恒 ready）。
⚠️ 但这条链上**唯一的"条件拍"就在 w6**：若下游在那拍忙，段周期就 >190 ⇒ 这正是"读 RTL 推的、未实测"的
那条边（`P7B_RATE_DATAPATH.md` §3/§5-item-4 自己标了）。与 app 的 187 关系：**二者在同一条流水上串接**
（不是竞争同一拍），段周期按 `max(187, 190)` 计 ⇒ **app 只余 3 拍（1.6%）**，这 3 拍余量**全靠那个 190 成立**。

### 1.8 实际收益 / 值不值得建（#8）—— **挡得住（有条件）**

- **改前**：RX 单流被 **app 校验器**钉死 = `1460/1643 = 0.8887 B/拍 = 1.1109 Gbps`；
  板级实测 `1,110.8 Mbps` = 该结构值的 **99.97%**（BIZ Stage 1）⇒ **这是一个实测的、贴死的限速级**。
- **改后**：app = `1460/187 = 7.807 B/拍 = 9.759 Gbps` ⇒ 限速级换成 **`tcp_rx` 的 190 拍**
  （`1460/190 = 7.684 B/拍 = 9.605 Gbps`，**未实测**）。
- ⇒ **这一刀的收益 = 移走一个实测限速级（×8.7 的结构跃迁）**，**不是**"RX 到 10G"：
  ① 新限速级 `tcp_rx` 190 只有 3 拍余量且**从未实测**；② 本刀不碰 TX（设计件说 TX 侧要 A2+乒乓才到 193 拍）；
  ③ 没有板级读数。**"RX 单路 10G 这一刀到不了" —— 这个结论作者写得对**。
- **值得建吗**：**值得**，但正确的最小包是 **`R1 + tcp_rx 拍数实测`**（同一个构建/同一次 xsim 就能把两件事一起收口），
  理由：`tcp_rx` 的 190 是**设计判据自己要求先测出来**的量（`P7B_SINGLE_FLOW_10G_DESIGN.md` §2.3 + 审查 B5），
  而 R1 恰好把"app 不再是限速级"变成"必须知道 tcp_rx 是多少"。**只建 R1 不测 tcp_rx = 收益不可判**。

## 2. "挡得住"各条的**反例构造失败说明**（全局纪律）

- #2（背压相位）：我尝试的构造 = "让上游在**相位 X** 送字、看两构建是否采到不同字"。
