## 1. 逐条攻击与结论（含证据）

### 1.1 【攻击点 1】镜像方向 —— 独立重推 ✅ 证实

**我不看它的结论，自己从板上读数推**：

1. 板上读数 `S3_FINAL_SWORD hi 3579139413 lo 1431655931`（`P7B_GATE1.md:549`，任务书亦给
   `c1_sword = 0xD5555555555555FB`）⇒ 拼成 64 位 `0xD5555555555555FB`。
2. 这个寄存器是**探针直接观察的 `rx_mii_d` 总线**（`P7B_GATE1.md:1025` 起的检查器把
   `mii_d==64'hD5555555555555FB && c==8'h01` 当帧首）。总线约定 `mii_d[l*8+:8]` = lane `l`。
   ⇒ 由该常量得 **`mii_d[7:0] = 0xFB`（lane0）、`mii_d[63:56] = 0xD5`（lane7）**。
3. 独立前提（不来自本文档）：官方例程 `pcs64_pkt_gen_mon.v:995`
   `preamble = 64'hFB_55_55_55_55_55_55_D5`，`:1148` `tx_mii_d <= swapn(tx_datain)`，
   `:1240` `swapn[i+:8] = d[(63-i)-:8]` ⇒ lane0 = 内部字最高字节 = `0xFB` = 帧**首发字节**。
   （[S1] 46.2.2 同向：`/S/` 在 lane0。）
4. 本仓冻结合同：`tdata[63:56]` = 帧首发字节（`rtl/mac_rx_64.v:2-8`）。
5. ⇒ **必须 `tdata[63:56] ← mii_d[7:0]`**，一般式 `tdata[(7-l)*8+:8] = mii_d[l*8+:8]`。

**与 RTL 对照**：
- TX：`mac_tx_10g.v:134-140` `bswap64[i*8 +: 8] = d[(7-i)*8 +: 8]`，`:246` `tx_d = bswap64(cw_data)`
  ⇒ `xgmii_txd[8*0+:8] = cw_data[56+:8]` = 合同首字节 ⇒ lane0 = 首发字节 ✓ **一致**。
- RX：`mac_rx_10g.v:186-197` `align8`（lo=0 分支）`= {w[7:0],w[15:8],…,w[63:56]}`
  ⇒ `a_data[63:56] = ld[7:0]` = lane0 ⇒ ✓ **一致**。
- 两者互为逆：对任意 `d`，`bswap64(bswap64(d))[b*8+:8] = d[b*8+:8]` ⇒ TX∘RX = I（我逐位验过）。
- 交付的 §2.2 交叉复算（板级 3 个字 vs 手算）**我也独立重算过**：第 2 字
  `FE 14 FF…FF`、第 3 字 `00 00 00 06 82 9A DD B5` 均与板上读数一致（注意方向：lane0 是最低字节）
  ⇒ **约定 + 镜像 + lane 编号三者自洽**。

**结论：证实**（文档推导与 RTL 实现一致，我的独立重推也一致）。

### 1.2 【攻击点 2】字节序判据的判别力 ⚠️ 部分证伪（缺陷 D2）

**判据源码**（`tb_mac_10g.v:497-498`）：

```verilog
chk(drv_d[0] === 64'hD5555555555555FB, "XGMII 帧首字 == 0xD5555555555555FB (/S/ 在 lane0)");
chk(drv_c[0] === 8'h01,               "帧首字只有 lane0 是控制字符");
```

`drv_d[]/drv_c[]` 是 **TB 自己的激励数组**（`pack_words` 在 `:267-282` 按 `gb/gc` 组装，`drv_run` 在
`:251-265` 把它喂给 `rx_d/rx_c`）。所以这两条是**对 TB 自身激励生成器的自检**：
`gb[0]=0xFB, gb[1..6]=0x55, gb[7]=0xD5` ⇒ `drv_d[0] = {D5,55,…,FB}` 是**构造性恒真**，
与 DUT 无关 —— **它无法区分"镜像对了"和"镜像反了"**（对 DUT 判别力 = 0）。
这把设计文档 §0 的"判据 = 组 2"+§8.2 的"首字常量只证明我们没引入 lane 旋转"两句话都变成了**不准确的自述**。

**但同一属性在别处有牙**（所以这不是"整条属性没测"）：
- 组 8（TX，`:703`）`chk(xcap_d[wi] === 64'hD5555555555555FB)` —— `xcap_d` 是 **DUT 的输出**，独立常量 ✓；
- 组 8（TX，`:712`）`expb[k] === cbuf[k]`（`cbuf[i]=i^0xA5`，非回文图案）⇒ 验证"合同首字节落在 lane0"，
  **独立于 DUT** ✓；
- 组 2（RX，`:501-503`）`rx_got[fs+0] === 0xA5` = `cbuf[0]` ⇒ 验证 RX 的 lane0→`[63:56]` ✓。
- **实证**（我重跑变异）：M1（TX bswap 直通）被 8 条组 8 的内容/FCS 判据抓住；
  M1b（RX align8 直通）被 `交付首字节 == 内容[0]` 等判据抓住。⇒ 镜像属性**有**判别力，
  **只是不是文档点名的那一条**。

**结论：部分证伪** —— 属性被覆盖（有实证），但**文档点名的判据是自证式（tautology）**。

### 1.3 【攻击点 3】`/T/` 的八种落位与"帧长为 8 的倍数"

- **RX：8 种全有**（证实）。组 3 扫 `k=60..68`（`:512`），`/T/` lane = `(k+4)%8`：
  k=60→0, 61→1, 62→2, 63→3, 64→4, 65→5, 66→6, 67→7, 68→0 ⇒ **lane 0..7 全覆盖**，
  且判据 `rx_dbg_last_tlane === ((k+4)%8)`（`:524`）是 DUT 输出比对独立期望 ✓。
  其中 `k=64`（lane4）正好是"末字整字都是 FCS"⇒ `emit_n=0`、tlast 落回前一字的分支（`:214-223`），
  交付 64 字节的判据 `:518` 能证伪该分支写错 ✓。
- **TX：缺 lane4 / lane5 两个用例**（存疑→已补测）。交付门的 TX 用例只有
  clen ∈ {60, 20(→64), 61, 62, 63, 67, 1514, 200(环回)} ⇒ `/T/` lane = `L mod 8` ∈ **{0,1,2,3,4(环回),6,7}**，
  **lane 5 无用例**（lane4 只在环回里出现，且那里不做 TX 格式判据）。
  我把组 8.3 的循环从 `61..63` 扩到 `61..65`（clen=64 → lane4、clen=65 → lane5，都是"末字与尾块合并"分支），
  **在原 RTL 上 241 checks / 0 fail** ⇒ 实现正确，缺的只是用例。
- **"末字与尾块合并"（帧长为 8 的倍数 / 差 1）**：我逐值验了 clen=60..68 的合并字构造
  （`merge_d`/`merge_c`/`t1_idle` 手推 + 实测周期）⇒ 正确（见 §1.10 的周期表）。
- **"只发合规 8 种 T 型块"**（对照例程的 `T0 D1..D7` 非标角落）：**证实**。
  `merge_c`（`:176-184`）把所有 `lane >= tstart+4` 的位标成控制字符、`merge_d` 把 `l-tstart>4`
  的 lane 填 `XGMII_I`；`tail_c`（`:195-202`）同理 ⇒ `/T/` 之后**只可能是 /I/**。
  且**每条** TX 判据都带 `tx_decode` 的 `ndata_after_t === 0`（`:707, 751, 769` 等），
  `badctrl === 0` 也会抓"帧内出现非法控制码" ⇒ 这条**有牙** ✓。

### 1.4 【攻击点 4】一拍内混合 / T+S 同拍 / IFG 判据

- **`/T/` + `/S/` 同拍**：有用例（`:620-640`），但它只判"不卡死 + 不污染其后规范帧"，
  这是**非规范输入**（[S1] Figure 49-7：T 与 S 不可能同块），声明是诚实的 ✓。
- **数据 + `/I/` 混合**：由组 3 的 `/T/` 字天然覆盖（`/T/` 前数据、后 `/I/`），全 8 lane 都跑到 ✓。
  帧中窗内出现控制字符（含 `/I/`）⇒ `win_ctrl`⇒`terr` 由组 5 的 `/E/`+保留控制码用例覆盖（`:575-589`）✓。
- **全 `/I/` 空闲**：`drv_idle_all` + 每处 24 拍 settle 覆盖 ✓。
- **背靠背 / IFG**：组 6 第一例用 7 个 `/I/` 的 IPG 连发两帧、两帧都判（`:600-611`）✓。
- **M6 的教训（单帧里 S_IDLE 空闲字与 IFG 空闲字不可区分）**：文档说的对，而且 **8.3c 真的在门里**
  （`:775-793`，两帧连发判 `s2-s1 === 12`）。**我用变异独立复核了这条**：M6（IFG 12→4）
  跑出来**只有一条 FAIL**，且正是 `TX 周期: /S/→/S/ == 12 拍`。⇒ "8.3c 是唯一判别面"**证实**
  （8.3b 的 `nidle>=12` 确实抓不到：单帧尾后 S_IDLE 也会补空闲字，被 `q > t_word+2` 的窗口吃进去）。
- ⚠️ **缺陷 D3**：`chk(rx_dbg_state !== 2'bx, "T/S 同拍: 状态机未进 X (不卡死)")`（`:628`）是**恒真**：
  `dbg_rx_state` 是每拍都有确定赋值的 2 位寄存器（`:382`），复位后即 0，**永远不会是 `2'bx`**。
  它既不能判"卡死"也不能判"没卡死"，对 DUT 零判别力（真正的"不卡死"证据是同组后面那几条）。

  `frd` 组合化是**语义等价且必要**的改动（FWFT 下"同拍捕获+同拍弹出"），我推过时序 ✓。

### 1.6 【攻击点 6】X 乐观陷阱 ✅ 未发现漏

全 RTL 搜 `if (!`：`crc32_64.v:393`、`mac_rx_10g.v:266/321/332`、`mac_tx_10g.v:258/273/277/311`，
共 **8 处**。逐一判：
- `!rst_n`（3 处）= 复位，与既有模块同式；
- `!fempty`（TX 3 处）= 流程控制，X 时走"当空"（安全方向：不起帧、不弹字）；
- `!res_ok` / `!push_ok`（RX 2 处）= **计数器自增**，X 时会静默不计数（方向偏乐观）。
  这两处的输入是寄存器上的等式比较（`crc == 常量` / `full_next` 组合），要出 X 得先有大面积 X。
- **判据侧无漏**：本工程那条铁律（`!== 1'b1`）**只适用于 TB 判据**——全仓 `rtl/*.v` 里
  `!== 1'b1` 命中数 = **0**，说明 RTL 从来不用这个写法；而 TB 的 `chk` 就是
  `if (cond !== 1'b1)`（`:25`）⇒ **X 一律判 FAIL**，方向正确 ✓。TB 内部比较也都用 `===`/`!==` ✓。
- **结论：本案没有可供攻击的遗漏**（8 处均为既有风格，且真正的判据侧是 X-pessimistic）。

### 1.9 【攻击点 9】CRC ✅ 证实（强）

我用 Python **直接解析 `crc32_64.v` 的常量块文本**（`pad_r` 的 32 条 bit 行 + `nv1..nv8` 各 32 条），
把它们当作线性函数求值，与参考模型（反射 `0xEDB88320` / init `0xFFFFFFFF` / 无终值取反）比对：

```
1) crc32('123456789') = 0xCBF43926  expect 0xCBF43926  OK
2) 60B 内容+4B FCS 残留 = 0xDEBB20E3  expect 0xDEBB20E3  OK   (0xC704DD7B? False)
3) RTL 常量块 vs 参考模型: 20000 组, 失配 0  OK      (9 种 keep 全覆盖: 00/80/C0/E0/F0/F8/FC/FE/FF)
4) 两整字 == 16 字节连续 ref: DC7199A2 vs DC7199A2  OK
```

- 三条语义逐条对：反射多项式 ✓ / 初值 `0xFFFFFFFF` ✓ / **无终值取反**（寄存器里就是原值，
  终值取反只在写 FCS 字段时 `crc_nxt ^ 32'hFFFFFFFF`，TX `:222`）✓ / 残留魔数 `0xDEBB20E3`
  **不是** `0xC704DD7B` ✓。
- `en` 与 `d/keep` 同拍：`crc_nxt` 是**纯组合**（`:390`），调用方（RX `:236` / TX `:211`）把
  `d/keep/en` 与同拍发射的字直接连上 ⇒ 满足工程坑 1 ✓。
- `init` 优先于 `en` ✓（`:390` 的 `init ? … : (en ? … : crc_r)`）；RX 用 `init=s_v`
  在 `/S/` 拍复位、TX 用 `init=(state==S_PRE)` ✓ 我逐拍推过：第一数据字拿到 `0xFFFFFFFF` 初值 ✓。
- **一个接口边界（低危）**：`m_cnt = 8 - popcount(keep)`，即修正只按 **popcount** 走，
  隐含假设 `keep` 高位连续。若有人喂 `keep=8'h0F`（低位连续），结果没有物理意义
  （我实测 20000 组随机 keep 里 15957 组"失配"正是这一类**非法输入**；换回高位连续 keep 后 0 失配）。
  模块头注释写了"`keep` 高位有效"，但**没有断言/门**拦非法 keep —— 建议登记（上游 RX 的
  `a_keep` 与 TX 的源约定都是高位连续，故当前不成问题）。

## 2. 缺陷清单（按严重性排序）

### D1【高】F-2 幽灵帧判据**没有判别力** —— 实证：有幽灵帧的变异仍 229/0 PASS
**证据链（仓外沙箱，交付 RTL 只读复制）**：
- 交付门在干净 RTL 上：`229 checks, 0 fail / VERDICT = PASS` ✓（我复现）。
- **M7 变异**（`S_ABORT` 的 `S_FLUSH` 改成 `S_IDLE`）：门 FAIL，但**只有 2 条判据响**
  （`stat_flush_done == 1`、`stat_flush_words >= 1`）；文档点名的
  `F-2 负对照: 新帧 60 字节逐字节 == 原始内容 (残字未混入)`（`tb_mac_10g.v:868`）与
  `F-2: 中止帧 /T/ 与新帧 /S/ 之间无任何数据字`（`:854`）**都没响**。
- **为什么没响（我用插桩 TB 打印了所有 `/S/` 位置）**：
  - 干净件：`base=2880, wi2=2989, /S/ at 2882, 2989`（2 帧，无幽灵）；
  - M7：`/S/ at 2882, 2858→(本轮 2967), 2992`（**3 帧 = 多出一个幽灵帧**），
    而判据取的主体是 `find_s(base+100)` ⇒ **`base+100` 恰好跳过幽灵、落在其后那个本来正确的帧 C 上**
    （2967 < 2980 < 2992）。
  - 另一条 `bad===0` 的扫描在**第二个 `/S/` 处就 `i = xcap_n` 收工**，而幽灵帧的载荷全在
    **它自己的 `/S/` 之后** ⇒ 结构性看不到。
- **致命一击（新增变异 M7b）**：把 M7 再补两行"计数器伪装"
  （`stat_flush_done++` / `stat_flush_words++`），即"**照样发幽灵帧、只是报告说冲刷过了**"：
  ```
  === M7b (发幽灵帧 + 计数器伪装) ===
  DBG base=2880 xcap_n=3034 wi2=2992
  DBG S at 2882 / 2967 / 2992         ← 2967 就是幽灵帧
  === tb_mac_10g done: 241 checks, 0 fail ===
  VERDICT = PASS
  ```
  ⇒ **门对"F-2 语义被违反"这件事完全瞎**；它抓 M7 靠的是两个**计数器**，
  而计数器与被测属性（"残字绝不被当新帧发出"）不是同一件事。
- **最小复现**（仓外，勿在仓内跑）：
  `mac_tx_10g.v` 里 `S_ABORT: begin state <= S_FLUSH; … end` → `state <= S_IDLE;` 并补
  `stat_flush_done <= stat_flush_done + 32'd1; stat_flush_words <= stat_flush_words + 32'd1;`
  ⇒ 门 `VERDICT = PASS`（229 或 241 checks 都过）。
- **影响**：F-2 是被替换模块的**两条冻结合同之一**，"幽灵帧"正是它的存在理由。
  单元门**不能**为这条合同背书（此前板级不可观测，`P7B_DATAPATH_CONTRACT.md` E6 已登记）。
- **修法建议（不代改）**：判据改成"从被中止帧的 `/S/` 数起、**第 2 个** `/S/` 必须就是新帧"
  （去掉 `+100` 的魔数偏移，或直接把 `ns` 计数与 `tx_stat_frames` 对账：
  发 1 个新帧时转移里应恰有 **2** 个 `/S/`，M7/M7b 会给出 3 ⇒ 有牙）。
- **并修正文档**：`P7B_MAC_DESIGN.md` §8.1 的 M7 行"（`stat_flush_done` 不涨、**残字混入**）"
  与实测不符，应改为"仅两个冲刷计数器响应"。
