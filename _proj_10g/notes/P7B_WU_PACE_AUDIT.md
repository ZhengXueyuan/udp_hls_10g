## 1. Q1：`PACE=100e6` 的单位到底是什么（不猜：读源码 + 读内核 + 读内核自己的读数）

### 1.1 传参链（逐字）

- `_proj_10g/notes/p7b_biz_tcpreg/tcpreg_j6.sh:24-25`：
  ```sh
  PACE=${PACE:-0}
  if [ "$PACE" != "0" ]; then EXTRA="--pace-bps $PACE"; else EXTRA=""; fi
  ```
  实测调用行（`wuloop_p100_j6_run1.txt:8`）：
  `SRC_CMD=./p7b_tcp_src --host 192.168.100.2 --port 8080 --seconds 6 --pace-bps 100000000`
- `_proj_pcie/p7b_biz/p7b_tcp_src.cpp:54,74`（**权威工具**，本轮的 diag/fix 变体继承同一行）：
  ```c
  else if (k == "--pace-bps") pace = atoll(nx());
  ...
  if (pace > 0) setsockopt(fd, SOL_SOCKET, SO_MAX_PACING_RATE, &pace, sizeof(pace));
  ```
  即：**`--pace-bps` 就是 `SO_MAX_PACING_RATE` 的字面值**，工具不做任何换算。

### 1.2 内核侧（对端机 own headers + own source，逐字）

- `/usr/src/linux-headers-7.0.0-34-generic/include/uapi/asm-generic/socket.h:76` → `#define SO_MAX_PACING_RATE 47`
- `/usr/src/linux-headers-7.0.0-34-generic/include/net/sock.h:493` →
  **`unsigned long sk_pacing_rate; /* bytes per second */`**
- `net/core/sock.c`（`linux-source-6.8.0`，语义多年未变）：`SO_MAX_PACING_RATE` 分支写
  `WRITE_ONCE(sk->sk_max_pacing_rate, ulval); pacing_rate = READ_ONCE(sk->sk_pacing_rate); if (ulval < pacing_rate) WRITE_ONCE(sk->sk_pacing_rate, ulval);`
- 执行侧是**协议栈内部 pacing**（对端 qdisc = `mq` + `fq_codel`，**没有 `fq`，没有 EDT 队列**）：
  `net/ipv4/tcp_output.c:2574 tcp_pacing_check()` + `:2623 limit = ... sk_pacing_rate >> sk_pacing_shift`（全是**字节率**记账）；
  实测 `tc qdisc show dev enp1s0f1np1` = `mq` + 4×`fq_codel`（无 fq）⇒ **帽子由 TCP 自己按字节率执行**。

### 1.3 ⭐ 判决性证据：**内核自己吐出来的 `pacing_rate`**（不是推断）

台架每秒采 `ss -tinm`（`tcpreg_j6.sh:51-54`），日志留在对端 `/tmp/ss_<TAG>.log`。逐字：

| 跑 | `PACE_BPS` | `ss` 里逐字 | = 8×PACE？ |
|---|---|---|---|
| `WU_BASE_P100` | 100000000 | **`pacing_rate 800000000bps/800000000bps`** | ✅ |
| attribution `PACED_J6`（同一档） | 100000000 | **`pacing_rate 800000000bps/800000000bps`** | ✅ |
| `WU_BASE_P160` | 160000000 | **`pacing_rate 1280000000bps/1280000000bps`** | ✅ |
| attribution `PACED160_J6` | 160000000 | **`pacing_rate 1280000000bps/1280000000bps`** | ✅ |
| attribution `PACED230_J6` | **1073741824** | **`pacing_rate 8589934592bps/8589934592bps`** | ✅ |
| `WU_BASE_P0` / `BIZ_J6`（未 pacing） | 0 | 无 `pacing_rate` 字段（`BIZ_J6` 打的是 cwnd 推算值 `63890598288bps`） | — |

⇒ **三个不同 pace 值、两次独立会话、8.000 精确**。加上达成值本身复现到 **0.006%**
（800.140 / 800.129 / 800.186 / 800.237 Mbps，四种工具二进制）：

**结论：单位 = bytes/s，`100e6 → 800 Mbps` 的 8 倍是单位换算，不是巧合。**
- 反向对照：若 pace 被内核忽略 ⇒ 该跑应与 `P0` 同病（4.6–5.1 Mbps），实测 800.186 Mbps ⇒ 帽**在位**；
- 反向对照 2：若单位是 bits/s ⇒ 100e6 的帽子是 100 Mbps，实测 800.186 ⇒ 单位不是 bits/s。

### 1.4 `P160`（= 1280 Mbps 帽子）**为什么反而塌到 13 Mbps**

不是单位问题，是**模态**问题：1280 Mbps **高于**板子 app 的消费率（≈1.07–1.11 Gbps，见 §2）⇒ 收窗被填满关闭
⇒ 板子从不通告"窗重开"（`wu` 缺陷）⇒ 对端只能等 **~207 ms persist** ⇒ 塌。

- 判据 W 在 `wuloop_p160.pcap` 上的签名（我复核，与 measrep 逐数一致）：`win_raw min=288`、`win<1460` 的 ACK **38 条**、
  **30 段** ~206.2 ms 静默。
- 塌陷**值**比未 pacing 高（13.2 vs 4.7–5.1 Mbps）也有机理：塌陷后每周期能塞进去的量 ≈ `窗口 × p/(p−R_app)`，
  `p` 越接近 `R_app` 每周期越能多塞（p=160 MB/s 时实测 ~294 KB/周期 vs p=线速时 ~83 KB/周期）——
  **⇒ 塌陷区里"pacing 越大吞吐越低"是正常的，阶梯判据必须知道这件事（§5）。**
  ⚠️ 这个公式只做量级对账（预测 11.6 vs 实测 13.2–14.6；未 pacing 预测 1.9 vs 实测 4.6–5.1），**未闭环，如实登记**。

### 1.5 ⭐ 顺带砸掉一条已入库的子结论：**"`2^30 bps` 帽子"叙事是错的，Stage 1 那片就是 app 天花板**

`P7B_BIZ_TCPREG.md` §1.3/§5/§8-#6·#7 的推理链：Stage 1 的 `1,073.043 Mbps` 恰是 `2^30 bps` 的 99.94%
⇒ 怀疑那次带了 `--pace-bps 1073741824` 限速 ⇒ "量的是工具的帽子" ⇒ 把 S1 的 "1,073.0 Mbps 被 app 的 RX 校验器钉死" **降级为未定**。

**三轮复核（纯算术 + 逐字重读原始件）后：这条链的三个环节都不成立。**

1. **单位环节**：`--pace-bps 1073741824` = **8.59 Gbps** 的帽子（`ss` 逐字 `8589934592bps`），压不到 1.07 Gbps；
   该臂（E）今天**实测就是塌陷 4.719 Mbps**（`paced230_j6_run1.txt:79`）。
2. **日志单位环节（新发现）**：`p7b_tcp_src.cpp:117` 的 `tx_MB` 是 **MiB**（`tx_bytes / 1048576.0`），
   而 `tx_Mbps` 是**十进制**（`tx_bytes * 8.0 / dur / 1e6`）。Stage 1 逐字：`132.656 / 265.062 / 397.469 / 529.906 / 662.312`
   ⇒ **稳态 = 132.41 MiB/s = 138.83 MB/s = 1,110.8 Mbps**。
3. **结构环节**：`0.889 B/拍 × 156.25 MHz = 138.89 MB/s = 1,111.1 Mbps`
   ⇒ **稳态/天花板 = 138.83/138.89 = 99.97%**。**这就是 `app_pattern` RX 校验器的天花板，不是任何帽子。**
   （`1,073.043` 这个**6 秒均值**比稳态低，是因为**最后一秒只发了 105.188 MiB**：缺口
   `6×132.41 − 767.50 = 28.3 MB = 0.204 s × 稳态速率` ⇒ **恰好是工具 `poll(&p,1,200)` 的一次 200 ms 超时**（`p7b_tcp_src.cpp:90`）——**台架粒度，不是板子**。）
   ⛔ **2026-10-07 独立复核（降级；只否掉归因，不否掉缺口）**：**缺口成立**（复核复算 = `132.414 − 105.188 = 27.226 MiB = 28.55 MB` ⇒ **0.2056 s**；
   与上句"28.3 MB / 0.204 s"同量级）。**但"恰好是 `poll` 超时 ⇒ 台架粒度、不是板子"是过度声称**：
   该循环是 `POLLIN|POLLOUT` 双事件、`poll` 返回即 `send()`，且**发送是 ACK 钟控的**
   （`ss` 逐字 `send 7535483871bps` / `notsent:154104` 表明发送缓冲常态满载）⇒ 要发生 200 ms 超时，
   必须**连续 200 ms 既不可读也不可写** —— **那本身就是板/链路侧 200 ms 无 ACK 的事件**；
   对端 `ss` 的 `rto:201` ⇒ **201 ms 的 persist/RTO 与这 0.2056 s 同样吻合**。
   原始件只有 1 s 粒度的 `SRC_T`、**没有 sub-second 时间戳** ⇒ 现有材料**无法**把两者分开（`P7B_WU_PACE_AUDIT_VERIFY.md` §2.5）。
   ⇒ **如实登记为"无法判定"**（全局 #48）。

⇒ **`1,073.043 Mbps` 与 `2^30 bps` 的巧合 = "MiB 当 MB 读" + "6 s 均值里含一次 200 ms 工具停顿" 两件事叠出来的。**
正确结论：**Stage 1 的读数就是 app 天花板（99.97%），S1 原文"被 app 的 RX 校验器钉死"是**对的**，
`P7B_BIZ_TCPREG.md` 台账 #6/#7 的降级与 `P7B_BIZ_S1.md`/`P7B_BIZ_PLAN.md` 加的限定**应撤回或改写**。**
（pace 帽若要成立，值必须 ≥1,110.8 Mbps —— 那不叫帽子，那叫板子的速率。）

## 5. Q5：把 J6 改成 pace 阶梯 —— 评估与判据原文

### 5.1 你的提案（0 / 200M / 500M / 800M / 1000M / 1200M **bytes/s**）有两个结构问题

1. **尺度不对**：这 6 点里除 0 之外**全部 ≥ 1.6 Gbps**，而板子上行天花板 ≈ **1.11 Gbps** ⇒
   5 个点全落在**同一个饱和/塌陷区**，测的是同一件事；且"每一点达到该 pace 的 ≥95%"对 **1000M/1200M 档
   在数学上不可能达成** —— 完美的板子也会判 FAIL（1.11/8 = 138.9 MB/s = 上限）。
2. **拐点区没被覆盖**：真正的拐点在 **100–160 MB/s**（本审计把它从"100–134.2"改成"≈138.9"，见 §2）。
   阶梯的全部信息量在这一段。

### 5.2 会不会撞台架帽子

- **会**，而且这次审计刚证明"贴 2 的幂"的那种帽子**真的发生过**（只是解释被写错了：不是 `2^30 bps`，而是
  `pacing_rate` 本身）。**帽子必须在船上被抓**，靠两件东西：
  ① **`PACE_BPS=` 与结果同一份 stdout**（measrep 已落地，✅）；
  ② **`ss` 的 `pacing_rate`**（内核自证：`== 8×PACE bps`）。⚠️ **现役台架的 `ss` 采样结构性近乎全盲**：
  `ss -tinm state established` + 板子 9 ms 就发 FIN 进 `CLOSE_WAIT` ⇒ **每跑只有第 1 秒一条可用样本**
  （我核了 `/tmp/ss_WU_*.log`：第 2 行起全空）。**这一条必须修**（去掉 `state established`，或只按端口过滤）。
- 判据里**不许**把"读数恰好贴某个二进制数"当作通过；也不许把 **≥1000 MB/s** 的档写进"≥95% of pace"判据。

### 5.3 ⭐ 建议的判据原文（可直接抄进 PLAN / 下一篇）

> **J6-ladder（pace 阶梯，收口判据）** —— 在**修复后的位流**上，同台架同参数（**`--seconds 12`**（§5.4-8）、
> 双向 pcap、`t0/t1` 紧贴快照）逐档跑 `PACE_BPS ∈ {0, 50e6, 100e6, 134e6, 160e6, 1000e6}`（**bytes/s**），
> **每档 ≥2 跑**；每跑先过四条"台架自证"：
> **(a)** stdout 里 `PACE_BPS=` 可查（现役脚本已保证）；
> **(b)** `ss -ti`（**已修掉 `state established` 过滤**）里 `pacing_rate == 8×PACE` bps；`PACE=0` 档豁免，改记"≥8×134e6 bps 或 cwnd 推算值"；
> **(c)** 该跑 pcap **只含一个连接**（现役 `tcpdump timeout=SECS+14` > 跑间隔 ⇒ 会串进下一跑，见 §8-③；必须先缩短或每跑 kill）；
> **(d)** `ΔW53(pre→post) == tx_bytes`（±0.5%，防"窗内没消化完、靠收尾排空"污染速率）。
> 然后**速率判据分两段**（因为上限是结构性的 `0.889 B/拍 × 156.25 MHz = 1.111 Gbps`）：
> **(e) `PACE ≤ 100e6` 的档**：`tx_Mbps ≥ 0.95 × 8×PACE/1e6`（帽子必须被达满；这是"帽子在位"的正面证据）；
> **(f) `PACE ≥ 160e6` 与 `PACE=0` 的档**：`tx_Mbps ≥ 1.00 Gbps`（= 结构天花板 90%；**上界只写到 1.11**，
> 旧的 `1.00–1.20 Gbps` 上限（`P7B_BIZ_PLAN.md:196`）在结构上不可达，**必须改**）；
> **(g) 阶梯单调非降**（`0 ≤ 50 ≤ 100 ≤ 134 ≤ 160 ≤ 1000` 各档实测值），且**相邻台阶比 ≤1.15**（"不再有 200× 断崖"）；
> **(h)** 形态判据（判据 W 翻面）：`PACE ≥ 160e6` 与 `PACE=0` 档的**板上行窗 `min(win_raw) ≥ 1460`** 且**无 >100 ms 静默段**。
> **⚠️ `134e6` 档只记读数、不进判据**（正落在拐点上，成败由环境抖动决定）。
> **负对照（同批必跑，判"有牙"）**：**缺陷位流 `d20c08c9…5ed5`** 上同阶梯 ⇒ **(g) 必 FAIL**（形状非单调：
> `100e6` 档 ~800 Mbps 是局部峰、`160e6` 档 ~13 Mbps）、**(f)(h) 在 `0/160/1000e6` 档必 FAIL**。
> 交付物另加一条**读数**：阶梯的**饱和拐点**（≈ 1.05–1.11 Gbps）就是"板子上行 app 通路容量"。

### 5.4 为什么这样改（理由，逐条）

1. **两段判据**是必须的：单段"≥95% of pace"在 pace > 天花板时**不可满足**（5.1-1）。
2. **`50e6` 档是帽子的正控制**：它给出的"`achieved/pace ≈ 1.00`"是**测量**出来的 8× 关系（现在只有 `100e6` 一档，
   严格说仍是"单点定单位"）。这一档也让"板子容量恰是 800"这类假说变成可判（§4-H3）。
3. **`134e6` 档只记为读数**：拐点处是 knife-edge（本审计的读数把边界从"2–2.5 MSS 余量"修正为"窗地板 29.6 KB = 20 MSS"，
   但那是 `100e6` 档；拐点本身仍不可靠）。
4. **单调性是比"≥95%"更锋利的那把刀**：缺陷位流上阶梯**本来就不单调**（100 档 800 → 160 档 13），
   修复后应单调饱和 —— 一个判据同时抓"塌"和"没有断崖"。
5. **负对照必须用**同一个阶梯**跑缺陷位流**（不能只跑一个 pace 点）：阶梯的判别力来自**形状**。
   ⚠️ 现有数据已经攒出 4 个点（0 → 4.631/5.060；100M → 800.186；160M → 13.281；2^30 → 4.719），**可直接当负对照的骨架**。
6. **跑间隔/截获隔离**：现在是每跑 ~11.3 s、`tcpdump timeout = SECS+14 = 20 s` ⇒ **下一跑的前 6 s 会被上一跑抓走**（§8-③）。
7. **别忘 `0x08` 纪律**：阶梯每跑前的 `identify_bars`/`MAGIC`/`BID` 现场读保留（本次审计复核过现态仍同）。
8. ⭐ **跑长一点（≥10 s），或至少记逐秒轨迹**：`poll(&p,1,200)` 的一次超时 = 6 s 窗里 28.3 MB = **3.3% 速率伪影**
   （Stage 1 那片就是这么来的，见 §1.5/§8-①'）。1% 级判据容不下 3% 的台架伪影 ⇒ `--seconds 12` 起，
   并把 `SRC_T` 逐秒行一起存档（它天然给出"有没有停顿"的见证）。
   ⛔ **2026-10-07 独立复核：要求（跑长 / 记逐秒轨迹）保留，措辞改** —— 那 28.3 MB 缺口**成立**（复核 = 27.226 MiB = **0.2056 s**），
   但"**是 `poll` 超时**"这个归因**不可判** ⇒ 应写成"**一次 0.2056 s 的停顿在 6 s 窗里就是 ~3% 的速率伪影**（归因不可判，见文首订正 ②）"。
9. **`tx_MB` 是 MiB**：读数表里要么统一换成 `tx_bytes`，要么标清单位（§8-①'）。

## 8. 顺带发现（都不是"现象变好"，是可修的错/隐患，逐条给判据）

① **`2^30 bps` 帽子叙事（§1.5）** —— 建议就地订正 `P7B_BIZ_TCPREG.md` §1.3 / §8-#6·#7、

   `pacing_rate 800000000bps` 等三档 8.000×），`1073741824 B/s` = 8.59 Gbps 且该臂实测塌陷；
   ② 日志 `tx_MB` 是 **MiB** ⇒ 该跑稳态 = **138.83 MB/s = 1,110.8 Mbps = app RX 校验器天花板
   （`0.889 B/拍 × 156.25 MHz = 1,111.1 Mbps`）的 99.97%**；`1,073.043` 是 6 s 均值含一次
   `poll(200 ms)` 停顿的伪影。⇒ **S1 原文'被 app 的 RX 校验器钉死'成立，降级撤回。**"*
   判据：**本文 §1.3 的三档 `ss pacing_rate` + §1.5 的逐秒复算**。
   ⚠️ 连带：`P7B_BIZ_S1.md §2/§6-⑪`、`P7B_BIZ_PLAN.md:20/52/65/132/196/409`、`P7B_BIZ_S2.md §10.5.1`、

   "= app 天花板 99.97%，见 `P7B_WU_PACE_AUDIT.md` §1.5"）。

①' ⭐ **两处"读数写法"陷阱（下一轮必踩，先登记）**：
- **`tx_MB` 是 MiB、`tx_Mbps` 是十进制**（`p7b_tcp_src.cpp:117,124-127`）⇒ 拿 `SRC_T` 的 MB 差当 MB/s 用会**少算 4.86%**。

- **`poll(&p,1,200)` 的 200 ms 超时会计进 6 s 窗**（Stage 1 那片就是这么少了 28.3 MB）⇒
  **判速率要么跑长一点（≥10 s），要么在读数表里记 `dur_s` 与逐秒轨迹**；1% 级判据下 3% 的伪影是致命的。
  判据：Stage 1 逐秒轨迹 + 缺口 28.3 MB/0.204 s 的算术（§1.5）。
  ⛔ **2026-10-07 独立复核（措辞订正，要求不变）**：缺口 = **0.2056 s**（复核值）成立；但"**是 `poll` 超时**"**不可判**
  （见文首订正 ② / §2.5）⇒ 本条的判据文字改写为"**一次 0.2056 s 的停顿**在 6 s 窗里 = ~3% 速率伪影"，
  **"跑长 / 记逐秒轨迹"的要求保留**。

② **J15 的"TCP 上行的新预测带"建立在错误前提上** —— `P7B_WU_LOOP_RECON.md:214` 写
   *"`P7B_10G` 下 app RX 校验器已改 8 B/拍 ⇒ 带子变了"*。实测：`rtl/app_udp_pattern.v` 有 21 处 `P7B_10G`，
   而 **`rtl/app_pattern.v`（TCP-8080 的 app）`grep -c P7B_10G` = 0**，其 RX 校验器仍是 `8/9 B/拍`
   （`P7B_BIZ_PLAN.md:409` 也把"app_pattern 改 8 B/拍"列为**待办**）。⇒ **TCP 上行的上界是 1.111 Gbps，不是 8.9 Gbps**；
   J15 定义里引用的 `4.803 Gbps`（`tcp_tx_frame` 380 拍/帧）是**下行帧器**的数，`UDP_TX_OVL` 后又已作废 —— **J15 必须重写**。
   判据：`grep -c P7B_10G rtl/app_pattern.v` = 0 + `board/wrapper_p4.v:1170` 的 `app_pattern` 例化。

③ **每跑 pcap 不隔离（跨跑污染）** —— `tcpreg_j6.sh:48` 的 `timeout $((SECS+14))` = 20 s > 跑间隔 ~11.3 s
   ⇒ 上一跑的 `wuloop_fin_p0.pcap` 里**同时含 FIN_P0（conn 37986，2,657 ACK，win min 152，30 段）与
   FIN_P160（conn 45148，8,028 ACK，win min 400，29 段）两条连接**；
   `analyze_window.py:104-105` 的"主连接 = ACK 最多者"**静默挑了 FIN_P160** ⇒ measrep §3.4 的 `WU_FIN_P0` 行
   其实是 **FIN_P160** 的读数（**同一跑被当成两次独立复现**）。
   判据：我按 4 元组分开统计逐字如上。**修法**：`timeout` 改 `SECS+3`，或每跑后 kill；分析器加"连接数必须 = 1"的断言。

④ **measrep §3.5-① 的"窗内只消化 1.63 MB"复现不出来** —— 实测 `ΔW53(t0→t1) = 3,201,132 B`（3.2 MB，
   占 `tx_bytes` 的 92.2%），`ΔW53(t1→post) = 272,176 B`（2.019 s，134.8 KB/s）。1.69 MB 那个数出自
   **对端 stdout 的第一秒 `SRC_T 1.000 tx_MB=1.688`**（发送侧的首秒突发），不是板侧消费。
   **结论方向（"t0/t1 紧贴窗会被排空污染"）成立**，但幅度要按实测改，否则下一轮会按错的量级设容差。

⑤ **`ss` 采样近乎全盲（台架）** —— `tcpreg_j6.sh:51-54` 的 `ss -tinm state established`：板子 9 ms 就
   发 FIN（app auto-close）⇒ 连接转 `CLOSE_WAIT` ⇒ **后续每一秒的采样都是空的**（我核了 5 份 `/tmp/ss_*.log`，
   第 2 行起全空）。**代价是**：J5 的 `bytes_retrans/retrans` 增量判据结构性地采不到；
   而**唯一那一条可用样本恰恰是本次审计确定"帽子在位"的关键证据**。修法：去掉 `state established`
   （或 `state established close-wait` / 直接按端口过滤），并把 `pacing_rate` 抽出来进读数表。
