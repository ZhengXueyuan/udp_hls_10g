## §2 as-built 到底是什么 (带行号)

**是 skid buffer, 不是 FIFO。深度 = 6 字 (48 B), 实现 = 6 组寄存器列 + 一条 3 态 FSM。**

| 件 | 行号 | 事实 |
|---|---|---|
| 状态机 | `rtl/rx_classify.v:52` | `S_FILL=0, S_DRAIN=1, S_PASS=2` (单 FSM, **FILL 与 DRAIN 互斥**) |
| 字数计数 | `:58` | `reg [3:0] n;  // skid 有效字数 (0..6)` |
| **skid 本体** | `:60-65` | `sk_d/sk_k/sk_l/sk_u/sk_c/sk_e` 各 `[0:5]` = **6 字寄存器组** (每字 76 位); **无 FIFO 例化、无 BRAM/LUTRAM** |
| 入口 tready | `:102-103` | `S_FILL → 1'b1`; `S_PASS → m_tready_sel`(下游组合); `S_DRAIN → 1'b0` |
| 出口 valid | `:84-85` | `S_DRAIN → 1'b1` (寄存器头字 hold); `S_PASS → s_axis_tvalid` (直通); `S_FILL → 0` |
| 出口数据 | `:78-83, 87-100` | DRAIN 取 `sk_*[0]`; PASS 取输入 (纯组合直通) |
| 填字 | `:122-150` | `S_FILL: if (s_acc) sk_*[n[2:0]] <= …` |
| 倒空 | `:151-165` | `S_DRAIN: if (o_acc)` 段移 + `n<=n-1`; `n==1` 时切 `S_PASS` |
| 直通到帧尾 | `:166-170` | `S_PASS: if (s_acc && s_axis_tlast) state <= S_FILL` |

**写址安全性**: `sk_*[n[2:0]]` 的 `n[2:0]` **恒 ≤ 5** —— FILL 在 `n==5` 接受那一拍就转 DRAIN
(`:142-146`), 所以写下标最大 5, **不存在数组越界**。`n` 的取指上界也是结构性的 (FILL 出口
只有三种: tlast / `n==2 && !wait_w5` / `n==5`)。

**判定: 出口/入口的"能不能收"判据是结构性的 (FSM 状态 + 一行组合 tready), 不是空间标志位。**

## §4 它是不是真实风险 —— 结论: **是风险, 但风险不在"丢字", 而在"每帧死 N 拍"**

### 4.1 已否证的两个假设 (否证也是产出)

- **否证 A: "DRAIN 期间顶背压会丢字/丢帧尾"** —— 不成立。DRAIN 是**寄存器 hold**,
  `tready=0` 期间上游必须保持 (AXIS 合同), 上游是 `fifo_sync`(FWFT) 或 `fifo_async`, 两者
  都是"不给 tready 就不推进 rptr"的实现 ⇒ 数据留在上游, **不丢**。
  既有门也背书: `sim/p4sim/run_tb_rxclass.bat` 跑 **NOSTALL / STALL / HARD 三种模式**
  (含"双路硬停窗口" `tb/tb_rx_classify.v:79-87`, 窗口 `[170,190)` 见 `tools/gen_stim_p4_rxclass.py:214-215`),
  逐字与 Python 模型比对 ⇒ 背压下的**内容保真**已被门覆盖。
- **否证 B: "1G 下会累积赤字"** —— 不成立, 算得出: 1G 时前端 1 字/8 GMII 拍 @125 MHz = **64 ns**,
  数据面 `dp_clk` = 156.2585 MHz ⇒ **字间隔 = 10 个 dp 拍**, 而每帧最多死 6 拍 ⇒ **留 4 拍余量**;
  连最小帧洪泛也不例外 (1G 最小帧 + IFG 的预算 = 12.5 + 15 = **27.5 dp 拍**/帧 vs 模块需 **14 拍** ⇒ ~51% 余量)。
  这与注释 `:9-10` 的判断一致, **注释在 1G 上是成立的**。

### 4.2 真正的风险: **硬吞吐天花板 `N/(N+停顿)`**

关键结构事实: **FILL 期间不输出任何字** (`:84-85` `o_v = (DRAIN) ? 1 : (PASS) ? s_valid : 0`)。
FILL 与 DRAIN 是**同一个 FSM 的先后状态, 不重叠** ⇒ 每帧占用 `N + 停顿` 拍, 其中停顿
= **3 拍**(非 TCP, w2 定案) 或 **6 拍**(TCP, 等 w5)。
⇒ 该模块的**输入接受率 = 输出发射率 = `N/(N+停顿)`**, 这是**通道级硬上限**。

算数 (最小 64B 帧: FCS 已剥 ⇒ 60 B = 7.5 字 ⇒ **N=8**):

| 路由 | 停顿 | 上限 | 数值 |
|---|---|---|---|
| 非 TCP (w2 定案) | 3 拍 | `8/11` | **72.7%** |
| **TCP (等 w5)** | **6 拍** | `8/14` | **57.1%** ← 与 `PORT_NOTES.md:3613` 的 "57%" **算数吻合** |
| TCP 满帧 (1518B, 190 字) | 6 拍 | `190/196` | 96.9% |

**关键推论: 加深上游 FIFO 修不了这个**。FILL 期间模块**没有可输出的字** (头字还在灌),
所以 FILL 的 3/6 拍是**整条链的死拍**, 与上游缓冲区多深无关 —— 缓冲区只能把"丢帧"换成
"积压增长", 最终还是丢。**只有让"收字"与"等决策/排空"不再互斥 (即 TODO 说的真 FIFO) 才能抬掉天花板。**

### 4.3 具体失效场景 (10G, 线速, 背靠背最小 TCP 帧)

输入序列: 连续最小帧 (`64 B`, 剥 FCS 后 8 字), 全部是 TCP 数据/ACK (走 w5 决策);
背压模式: 下游恒 ready (最有利的情形)。

1. 每帧: FILL 6 拍 (收 w0..w5) → DRAIN 6 拍 (发 6 字, **`s_tready=0`**) → PASS 2 拍 ⇒ **14 拍/帧**。
2. 线侧预算: 8 字 + 12 B IFG = **9.5 字槽/帧**。
3. ⇒ **净赤字 ≈ 4.5 字/帧** (TCP; 非 TCP 路径 = 3 − 1.5 = **1.5 字/帧**, 同样为正)。
4. 现有 1G 位流的弹性 = `mac_rx_64` 的 **8 深** `fifo_sync`(`rtl/mac_rx_64.v:361`) +
   P6b 的 **256 深** `fifo_async`(`board/wrapper_p4.v:430-431`) ≈ 264 字
   ⇒ 约 **59 帧 / ~3.6 µs** 填满, 随后进 `fifo_sync` 的"整帧丢弃"路径
   ⇒ **`mac_rx_64` 层整帧丢, 且带计数** (`stat_drop`/`stat_drop_full`: `rtl/mac_rx_64.v:257-263,337-341`)。
5. 受害帧**可以是 fast TCP 帧** (classify 不给任何路由优待) ⇒ TCP 触发重传, 有效吞吐塌到 <97% 且被重传放大;
   若换成 UDP 行情流 ⇒ **丢帧即永久丢失** (无重传)。
6. **不是静默**: 丢帧数走 `stat_drop_full` → 快照窗 **W34** (`wrapper_p4.v:2738-2741`, `P6E_OBS.md:80`)。
   ⚠️ 但前提是**新的 10G 前端保留这套 census** (见 §6)。

**另一个次级场景 (与 10G 无关, 但同类)**: rx_classify 会**原样传递下游的停等**
(DRAIN/PASS 的 `s_tready` 就是下游 tready) ⇒ 下游一次 ≥8 字 (或 10G 下 ≥264 字) 的停等
⇒ 上游 `mac_rx` FIFO 溢出 ⇒ **整帧丢 + 计数**。这是既有的"级间弹性预算"问题, 不是本次新发现,
一并记录以免混淆。

## §5 对 10G 的判断: **不安全 (有算得出的上限), 且不能只靠"加深 FIFO"绕过**

- **1G: 安全** —— 字间隔 10 dp 拍 > 6 拍停顿; 且板级实测利用率远低于此 ⇒ 注释成立。
- **10G (156.25 MHz, 1 字/拍, 几乎每拍有字): 不安全**。
  理由不是"背压变多", 而是 **§4.2 的硬上限**: 每帧死 3/6 拍 = 每帧 ~1.5 / ~4.5 字的**结构性赤字**。
  - 小帧洪泛: 上限掉到 **57%**, "10G 线速"目标**直接不成立**;
  - 满帧 TCP: 96.9% ⇒ **仍会周期性丢帧** (赤字 > 0 即无界积压), 表现为 TCP 重传 / UDP 永久丢。
- **判断等级: "需要实测" 只适用于量化 (实际丢帧率与帧长分布有关), "不安全" 是定性确定的**
  —— 赤字符号为正即结论, 不依赖任何未定参数。
- **修的方向 (供后续实现+审查+门流程参考, 本次不改代码)**: 把"等 w5 决策"从**阻塞输出通道**
  改成**由 FIFO 解耦** —— 深度不是要点 (**≥ 决策窗 6 字 + 少量抖动**即够), 要点是
  **收字与决策/排空不再互斥**; 抬掉后才谈得上 10G 线速。
- **门缺口 (本次未建, 记录)**: 现有 `tb_rx_classify`(125 MHz, 固定帧表) 只能证**内容保真**,
  证不了**吞吐**; `tb_udprx_rate.v:13` 自述其线速模型是"**每 8 拍 1 字**"(1G 口径)。
  ⇒ **全仓没有一条门在"1 字/拍连续输入"下跑数据面** ⇒ 这条缺陷在门层面**不可见**,
  10G 前必须先有一条 `1 字/拍 + 背靠背小帧` 的吞吐门。

## §7 附带 (可选项, 只报告事实, 未改代码): `rtl/udp_split.v` 在"1/8 速率消费者"下的长期行为

- **消费者速率**: `rtl/app_udp_pattern.v:389` `assign rx_tready = !nx_v` (前瞻寄存器空才收),
  稳态 **1 字 / 8 拍** (= 1 字节/拍 @125 MHz = **恰好 1G 线速**)。
- **缓冲**: `rtl/udp_split.v:464` `frame_fifo #(.W(73), .D(512))` = **512 字 = 4 KB**。
  生产速率 (1G 线速 = 1 字/8 拍) 与消费速率**恰好相等 ⇒ 零余量**; 任何帧内开销/背靠背都会积压。
- **积压后果 = 整帧丢 + 计数, 不静默**: `udp_split.v:484` `uf_ovf = u_word && uf_full`
  → `:556` 置 `u_abort_r` → `:560` `stat_drop_ovf` 计数 → 帧回卷 (`:519-522`) 整帧作废。
  该计数**已接出**: `wrapper_p4.v:945` `udp_drop_ovf (app_udp_stat_drop_ovf[15:0])`
  ⚠️ 但在 UART 状态行里**截成 16 位** (计满回绕后不可判)。
- **判据精确性**: 该写口**不是 F4 形态** —— `udp_split.v:571` `assign uf_wr = u_wr_evt;`
  是**组合**写门, 用的是 `frame_fifo` 的**同拍组合** `full` (`rtl/frame_fifo.v:260` `assign full = full_n;`),
  没有"寄存器化 push + 寄存器化 full"的一拍错位。
- **10G 含义**: 消费者比 10G 字速慢 **8 倍** ⇒ 必然持续 `uf_full` ⇒ 持续整帧丢 (带 `stat_drop_ovf`),
  这正是 `CLAUDE.md` 已记的 "10G 需换 8 路并行 (8 步 xorshift/拍)" 所对应的代价。
  **本次未核实**: `frame_fifo` 在"写满 + 回卷"下的快照/回卷交互 (该模块另有既有门与结论, 本次未读)。
