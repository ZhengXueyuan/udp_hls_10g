## 2. ⭐ 步 4：把"窗单调下降"钉死 —— 机理与判据

### 2.1 现象的正确形态（订正 Stage 2 的"单调下降"）

两臂 pcap 逐 ACK 还原（`analyze_window.py`，判据 `redge_est = ack + win`）：

| 量 | RATE 臂 | BIZ 臂 |
|---|---|---|
| 板纯 ACK 数 / 其中 `win < 1460` | 2519 / **79** | 2705 / **98** |
| `win` 范围 | **56–49152** | **128–49152** |
| >100 ms 的静默段 | **31 段，周期 207.6 ms（202.2–207.9）** | **33 段，周期 207.2 ms** |
| 每周期对端送达 | ~69.7 KB | ~68.0 KB |
| `redge_est` 推进量 | 3,353,332 B（≈交付量） | 3,544,984 B（≈交付量） |
| 静默期间的双向包 | **0**（板没发任何 ACK/wu） | **0** |

⇒ **窗不是"单调下降不恢复"，而是"每周期：重开到 49152 → 被一个窗容量的突发压到 <MSS → 等 208 ms persist 定时器"。**

### 2.2 机理（三个环节，逐环节有读数）

1. **窗被突发压垮**：对端以窗容量（≤49 KB）为单位突发（GSO 超级段 29,200/19,584 B），
   而 app 的消费是硬件速率 ⇒ 每个突发把 `occ` 推到 `winq` ⇒ 窗口跌破 MSS（最低 56/128）。
2. **信用回收正常**：`redge_est = ack + win` 与交付量 **1:1 前进**；板侧 BIZ 臂
   **`ΔW53 = 0x35fbfc = 3,538,940` ≈ 对端 `tx_bytes = 3,538,944`（差 4 B）**、**`ΔW54 = 0`**（逐字节干净）。
3. **通告缺失（缺陷在此）**：`rtl/app_ctrl.v:1109-1122` 的 C6 窗口重开通告（`wu_pend`）只有两个触发：
   ① `pb_wscan == 0`（**恰好** 0）；② `pb_wscan ≥ wu_mark + WU_STEP(24576)`。
   - ①：窗口的下界被 app 的持续消费托在 **56–128**（消费 21 B/µs × RTT ≫ 残窗 56 B ⇒ **occ 永远追不上 winq**，
     "Zeno 式"），⇒ **永不触 0** ⇒ `wu_zero` 永不置位；
   - ②：`wu_mark` 在建连时初始化为 `winq`（=49152），而 `wscan ≤ 49152` ⇒ 需 ≥ 73728 才触发 ⇒ **结构性不可达**。
   ⇒ **板从不主动通告窗口重开**；对端唯一的恢复手段是 persist/RTO（实测 207.6 ms，与 `ss` 的 `rto:201` 同量级）。

### 2.3 ⭐ 本轮构造的"信用回收"判据（可复用）

> **判据 W（pcap 侧，不需要板侧新字）**：把板发的一切 ACK 画成 `redge(t) = ack(t) + win(t)`
> （窗口 scale=0，板不协商 wscale ⇒ `win_raw` 即真实窗口，两臂 pcap 已证）。
> · `redge` **冻结而 ack 前进** ⇒ 信用**没回收**（右沿锁死）；
> · `redge` 与交付量 **1:1 前进** ⇒ 信用**在回收**（则问题在"通告"或"消费"）。
> 本轮读数：**两臂都是"在回收"** ⇒ 直接排除"信用不回收"这一整类假设。
>
> **判据 X（板侧自证，纯存量字）**：`ΔW53`（app 消费字节）对 `ΔW22 × 1460`（交付字节）。
> · `ΔW53 ≪ 交付` ⇒ app 没消费（背压）；`ΔW53 ≈ 交付` ⇒ app 消费了（本轮：**差 4 B / 3.5 MB**）。
> 与判据 W 合起来 = **"消费 ✅ / 回收 ✅ / 通告 ❌"** 三段定位，全部用**存量字 + 对端 pcap**完成。

### 2.4 仍判不了的那一格（**下一轮缺哪几个字**）

`winq / occ / redge / wu_pend / wu_zero / wu_mark` 在板上**都读不到**：`app_ctrl` 的寄存器总线在 wrapper 里被
**恒定接死**（`board/wrapper_p4.v:1280-1281`：`app_reg_addr=8'h00; app_reg_wr=1'b0`），
`dbg_redge0/dbg_winq0` 也未进快照 ⇒ 本轮结论靠"pcap 窗轨迹 + W22/W53"**间接**闭合。
**建议（一行 RTL + 两个字）**：把 **`app_ctrl.stat_wu`（已存在！寄存器 0x96；语义 = `wu_gnt` 拍数，
即"**wu 条目确实入了 ackq**"的次数，不是"已上线"）** 与 **`rx_occ_bytes`** 接进 61 字窗口
⇒ "**`wu_pend` 从未被置位（触发条件不可达）** vs **置位了但 ackq 不接（饿死）**"变成**一次读数**。
（本轮已用 pcap 证明"没发出"；但上面这一格仍缺见证。）

## 5. ⭐ 速率对照实验（4 组，同板同工具同参数；每组前**重烧 + 重核 sha256**）

| # | 发送侧 | `tx_Mbps` | 板侧 `ΔW53` vs 对端 `tx_bytes` | 判读 |
|---|---|---|---|---|
| A | 未 pacing（RATE 臂） | **4.544** | （RATE 窗无 W53） | 塌陷 |
| B | 未 pacing（BIZ 臂） | **4.719** | 3,538,940 / 3,538,944（**差 4 B**） | 塌陷 |
| C | `--pace-bps 100000000`（100 MB/s） | ⭐ **800.140** | 600,099,704 / 600,105,096（差 0.0009%） | **不塌陷，pace 限速** |
| D | `--pace-bps 160000000`（160 MB/s） | **13.195** | 9,895,272 / 9,895,936 | 塌陷（较 A/B 好 2.8×） |
| E | `--pace-bps 1073741824`（**2^30**） | **4.719** | 3,538,940 / 3,538,944 | 塌陷（与未 pacing 逐数同值） |

### 5.1 三条结论

1. **稳定性 ⟺ 发送速率 ≤ app 有效消费率**：100 MB/s ✅ / 134.2 MB/s ✗ / 160 MB/s ✗ ⇒
   **今日的有效消费率界 ⊂ (100, 134.2] MB/s**（源码模型 0.889 B/拍 = 138.9 MB/s；实测略低，差在帧级开销）。
2. **塌陷与 pace 的大小无关，只要超过消费率**：E（134.2 MB/s）与 A/B（线速）**逐数同值**（3,538,944 B）
   ⇒ 一旦进入"persist 周期"主导，发送侧多快都没用（每周期就 ~68 KB）。
3. **拐点是 knife-edge**：稳定时窗的平衡值 = 速率 × RTT ≈ (100~134 MB/s) × 27 µs = **2.7–3.6 KB ≈ 2–2.5 个 MSS**
   ⇒ **窗口平衡点离"跌破 1 MSS"只有几十微秒级的余量** ⇒ 环境/参数变化百分之几就能翻转结局
   （这解释了 09-30 与今天的巨大反差，也解释 §1.3 的 `2^30` 巧合）。

#### ⚠️ 2026-10-07 订正（独立复核裁定 = `P7B_WU_PACE_AUDIT_VERIFY.md` §5 / §2.6 / §2.4；上面的实验与读数全部有效，**只订三处口径**）

1. **`134.2 MB/s` 这个数作废（它来自旧的 bits/s 误读）**：`2^30 bps = 134,217,728 B` ⇒ 当年（错的）读法下它成了"134.2 MB/s 的帽"。
   正确读法下 **E 臂的帽 = `1073741824 B/s = 8.59 Gbps`（≈1073.7 MB/s）** ⇒ 结论 2 的那句应读作
   "**E（8.59 Gbps 的帽）与 A/B（线速）逐数同值**"；结论 3 的平衡值区间也随之改为 **⊂ 100–138.9 MB/s 内**。
   ⇒ **有效消费率界只能写 ⊂ (100, 138.9] MB/s**（结构值 `0.889 B/拍 × 156.25 MHz = 138.89 MB/s`）。
   判据：`/tmp/ss_WU_BASE_P100.log` 逐字 `pacing_rate 800000000bps/800000000bps`（= 8 × 100e6 B/s 的纯单位换算）+ §1.3 订正 (1)。
2. **"knife-edge"降级为"在 `100e6` 档被实测证伪、在拐点本身未测"**：逐 ACK 复核 `wuloop_p100.pcap` ⇒
   **窗地板 = 29,584 B = 20 MSS、`#win<1460` = 0、persist 静默段 = 0** ⇒ `100e6` 档的余量**很大**，不是 knife-edge。
   拐点（`100e6` 与 `160e6` 之间）**没有单独测过** ⇒ 该词只能写"未测"，不能写成结论。
3. ⚠️ **`ΔW54 = 0`（§0 ④ / §2.2-②）的适用范围要收窄（引另一路的登记，非本订正轮裁定）**：
   `P7B_WU_LOOP_MEASREP.md` §4.6 登记了一条**测试工具缺陷** —— TCP 工具"整块 `fill` + 非阻塞 `send` 部分发送
   ⇒ 线上图案流**内部跳字节** ⇒ 板侧连续 LFSR 检查器（`W54`）永久失步 ⇒ **假失配**（该轮给出直接见证 +
   修好后 A/B 双向对照；`ΔW54` 在长/高速跑上可达 ~99.5%）。⇒ **引用 `W54` 必须带上"该跑无部分发送"这一前提**。
   （本订正轮**未**独立复核该条 ⇒ 按 `P7B_WU_LOOP_MEASREP.md` §4.6 的口径引用，不升级为本文件结论。）
