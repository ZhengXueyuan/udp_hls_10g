## §1 缺陷本体的判据（拍级，本文所有推导的地基）

合同原文在 `rtl/fifo_sync.v:6-17`（P6b F4 修复时写下）。用同一套记号写死两条：

设生产者推入是**寄存器** `wr(T)`（T 拍决定），则它**在 T+1 拍末落笔**，落笔判据是 FIFO 内部
`wr && !full` 里的 `full` 取**T+1 拍**的值。于是

> **丢失的充要条件**（占用 `occ`、深度 `D`、`in_flight(T)` = T−1 拍决定的那笔写）：
> ① `occ(T) = D-1`；② `in_flight(T) = 1`（T 拍有在飞写，它会在 T 拍末把 `wptr` 顶到 D）；
> ③ T 拍**本拍还要再决定一笔写**（否则 T+1 拍没有在飞写 ⇒ 无字可丢）；
> ④ T 拍无 pop（有 pop 则占用回落）。
> 三条同时成立时，T 拍决定的那笔写落在 `occ(T+1)=D` 的拍上 ⇒ 被 `wr_ok` 静默丢。

修复 = 把空间门从 `!full(T)` 换成 `!full_next(T) ≡ !full(T+1)` ⇒ ③④ 无关，判据变**精确**。

⚠️ **条件 ③ 是全篇的关键，也是两份"够不着"读法（以及本笔记第一轮构造）栽的地方**：
生产者只要在 T 拍处于"不决定写"的相位（实例 2 的 `P_LOAD` 空拍、实例 1 的
`T_IDLE/T_PRE/hc<4`），则**一个字都不会丢** —— 占用即使到 `D` 也丢不了。
⇒ "能不能到饱和"只是**必要条件**，**相位对齐**才是充分条件。

## §2 实例 1：`slow_tx_adp.u_wf`（`frame_fifo`, D=512, W=73）

### 2.1 门在哪、错在哪

- 写决定：`rtl/slow_tx_adp.v:141`（满字/末字两处 `wf_wr <= 1'b1`）+ `:180`（commit 判据）。
- 老门（修复前）：`:141` `if (hc == 3'd4 && !wf_full && !abort)`、`:180`
  `if (hc == 3'd4 && !abort && !wf_full)` —— **本拍** `wf_full`。
- `frame_fifo` 修复前**没有** `full_next` 端口 ⇒ 不能照抄 `fifo_sync` 的修法（这是本实例
  与实例 2 的唯一差别；修法见 §4）。

### 2.2 为什么 abort 安全网救不了它（本实例的"命门"）

`slow_tx_adp` 有一层安全网：`T_DATA` 里只要在 `hc==4` 的检查拍看到 `wf_full`，就把该帧
`abort`（`:145-147`），帧尾 `rollback` + `stat_purge++` ⇒ **整帧丢弃、无静默丢失**。
但 §1 的丢失条件里"落笔拍 = `occ(T+1) = D`"与"决定拍 = `occ(T) = D-1`"**不是同一拍**：

- 决定拍 T：`occ = 511` ⇒ `wf_full = 0` ⇒ 检查**通过**，正常写 + 正常 `commit`（`stat_frames++`）；
- 落笔拍 T+1：`occ = 512` ⇒ 该笔写被丢；
- **而 T+1 拍 FSM 已经回到 `T_IDLE`**（末字拍就是帧尾，`:159 tstate <= T_IDLE`）⇒
  **没有任何检查拍** ⇒ 帧被记成"已提交"，线上却永远等不到它的 tlast。

⇒ 后果不是"丢一个字"，而是 **帧合流**：该帧的字全在，唯独 tlast 字没了 ⇒ 播放器
`O_SEND` 读到下一帧的字，两帧粘成一帧；后续帧还因为 FIFO 钉在满而被 abort。

### 2.3 构造（帧几何 + 占用对齐 + 激励，全部可复算）

1. **帧几何**：内容 `C = 1017` 字节（`C % 8 == 1` ⇒ 帧末字是**1 字节部分字**，
   与它前面的**整字**构成**背靠背两笔写决定** = §1 条件 ② ③ 同时成立）；
   每帧字数 `W = ceil(C/8) = 128`。
2. **占用轨迹**：无读、无 pop 时，第 k 笔写决定的占用 `occ(d_k) = 起点 + (k-2)`（前一笔还在飞）。
   要 `occ = 511` 正好落在**末字那拍**（k = W = 128）⇒ **帧起点 = 513 − W = 385**。
3. **对齐手段**：均匀 128 字帧只能落在 384 的倍数 ⇒ 在**第 3 个大帧之后插一个 1 字小帧**
   （内容 8 B，`:135` 的 `pc==7 && in_last` 单笔即整帧）把起点从 384 抬到 385。
   帧序列 = `[C, C, C, 8, C, C, C, C]`。
4. **激励**：`m_axis_tready` 在整个喂入期恒 0（模拟 `tx_arb` 把慢路径饿死；
   慢路径在 `tx_arb` 里优先级最低，被 fast/app 压住 ≥33 µs 完全合法）。
   喂入 7 个大帧 + 1 个小帧 ≈ 8200 拍 ≈ 66 µs @125MHz。

预期（可复算）：F1..F4 提交并落满 385 字 → F5 从 385 起写 128 字 ⇒ 前 127 笔落到 511、
末字落笔拍到 512 被丢（F5 已 commit） ⇒ F6..F8 在第 1 个检查拍看到满 ⇒ abort/purge。

### 2.4 第一轮构造失败的教训（**必读**）

第一版台架用**均匀 128 字帧 + 全程饿死**，结果 **PASS**（`frames=4 purge=4 words=512`）。
原因正是 §1 的相位：F4 的起点是 384（不是 385），决定拍占用只有 **510** ⇒ 落笔拍 511 ⇒ 不丢。
数一下就更清楚：均匀帧给出的是 `512 = 4×128`（正好整除），**丢掉了一格相位**。
⇒ **"能到满" 不等于 "会丢字"**；必须把"哪一拍做决定"也算进去。凡是只论证"占用到不了 D"
或"到了 D 有 abort 兜底"的读法，都在这一点上不成立。

### 2.5 裁定

**可达**（构造性反例，见 §7 读数）。既有构建里没有任何东西阻止"慢路径被饿死 ≥33 µs +
HLS 持续产出 ≥4 帧内容"这一组合（HLS 侧字节 FIFO 2048 深，`u_wf` 侧无背压）。

## §3 实例 2：`slow_rx_adp.u_ofifo`（`fifo_sync`, D=2048, W=9）

### 3.1 开播门算术 ⇒ **唯一闸 = 单帧字节数**

播放器写口：`P_PRE`（`:267`，8 个前导拍）、`P_EMIT`（`:281`，每字 `nb` 拍），
老门 `if (!o_full)`（本拍满）。开播门 `rtl/slow_rx_adp.v:158/237`：
`start_play = (pstate==P_IDLE) && (committed!=0) && (occ <= 12'd256)`。

- `occ` 与 FIFO 精确同步（`o_wr` 只在一笔真写入时置位，见 `:135-138` 的注释），
  且**每帧只走一遍 `P_IDLE → P_PRE → P_LOAD/P_EMIT* → P_IDLE`**（`:237` 重进门）⇒
  **门是逐帧判的**。
- 一帧写出的字节数 = 8（前导）+ Σ`nb` = 8 + 该帧载荷字节数（`keep2n` 只认"前缀有效"，
  非法 keep 退化为 1 字节 ⇒ 上界就是载荷本身）。
- ⇒ **峰值占用 ≤ 256 + 8 + 载荷**。要摸到 §1 的 `occ = 2047`：**载荷 ≥ 1783 B**。

⚠️ 这同时解释了"复核 agent 说的 `occ<=256` 部分挡住"——**挡住的量级是"标准 1518 B 以太帧"**：
`256+8+1518 = 1782 < 2047`。也就是说，"够不着"的证明**依赖一条从未写进任何地方的假设**：
"送给慢路径的帧 ≤ 1518 B"。

### 3.2 相位（第二处关键）

第一版实例 2 台架（1 字/8 拍喂 376 字、饿读者 4000 拍）也 **PASS**。探针给出
`maxocc=2048 full_seen=1` —— **占用确实到了 2048，就是一个字节都没丢**。原因：
- `P_EMIT` 每字之间有一个 `P_LOAD` 空拍（**不决定写**），`P_PRE` 之后也有一个；
- 写的相位是"每组 8 笔（`nb=8`）后跟 1 个空拍"，而 `occ=2047` 恰好落在**空拍**上
  ⇒ §1 条件 ③ 不成立 ⇒ 无字可丢。
- **修法**：把每字字节数改成 `nb=7`（`tkeep=0xFE`）⇒ 空拍相位变成"每 7 笔一停"，
  丢字点 `occ=2047`（第 2049 笔）不再落在空拍上 ⇒ 丢 **1 字节**。

这条正是 §1 强调的：**占用够 + 相位对** 才丢；也解释了为什么"单靠占用论证"永远只是必要条件。

**实测钉死（变异件 = 旧门，两次跑只差每字字节数）**：
`logs/bench_mut.log` 的第三条 —— 同一份旧门 RTL、同样**到满 2048**：
- `2100 7 0`（`nb=7`）：`maxocc=2049 full_seen=1 ovf_cyc=1` ⇒ **丢 1 字节** ✗
- `3008 8 0`（`nb=8`）：`maxocc=2048 full_seen=1 ovf_cyc=0` ⇒ **一个字不丢** ✓
⇒ "到不到满"与"丢不丢"是**两个独立的量**；只证前者得不出后者。

### 3.3 长帧在现存构建里到底能不能出现（**没有守卫**）

- `rtl/rx_classify.v`：无长度逻辑（帧直接分流）。
- `rtl/slow_rx_adp.v.u_ff`（`frame_fifo` D=512）：**唯一的**事实上界 = 512 字回卷
  ⇒ 一个"被 commit 的帧"最多 512 字；每字最多 8 字节 ⇒ **载荷上界 4096 B** ⇒
  **1784..4096 的窗口非空** ✓。
- `rtl/mac_rx_64.v`（1G）：无长度逻辑（grep `len|max|1518|jumbo` 0 命中）。
- `_proj_10g/p7b_mac/rtl/mac_rx_10g.v`（10G，10 条判据里点名的那份）：有
  `ETH_MAX_FRAME=1518` / `ETH_MAX_QTAG=1522`，但超长帧走的是
  **`:398 else if (len_now > ETH_MAX_QTAG) stat_rx_long <= stat_rx_long + 1`**
  —— **只计数，交付路径不变**（`frame_push_ok` 是空间判据不是长度判据）⇒ **超长帧照常交付** ✓。

### 3.4 裁定

**可达**，条件是"有一个 > 1783 B 的帧到达本适配器"。该条件：
① 在现存构建的**任何一级都没有 RTL 守卫**；
② 10G MAC 明确**计数并交付**超长帧；
③ 用户手册/设计文档里也**没写**"慢路径只收标准帧"。
⇒ 按本工程的既有教训（`app_udp_pattern` 当年也被判"够不着"），**不接受"标准以太帧"作为
未成文的隐含前提** ⇒ **按可达处理并修**（修法零风险、且把门变成精确判据）。
（诚实标注：没有做"线路上真发一个 jumbo 帧 → 整流链 → 适配器"的端到端演示，
本轮证据停在适配器边界的合法 AXIS 激励，见 §7 的 NC 与 §8 的风险。）

- **在既有门覆盖的激励下两版逐笔同值**：证据 = 修后 `p4_slowrx`/`p4_slowtx` 仍与

## §7 验证证据（全部读数在 `_proj_10g/notes/p7b_latent/logs/`）

### 7.1 反例双跑（**同一台架、同一激励与判据，只差 RTL 的写门**）

台架：`tb_lat_wf.v`（实例 1，字节流源 → DUT → AXIS 捕获，判据 J1/J2/J3）、
`tb_lat_of.v`（实例 2，字流源 → DUT → 字节捕获，逐字节判据 + 占用/拒写探针）。
入口：`run_lat.bat`（正例）/ `run_lat_mut.bat`（同一台架 + `mut/` 里把写门改回本拍 `full`）。

| 读数 | 修前 = 变异（本拍 `full`） | 修后（`full_next`） |
|---|---|---|
| 实例 1 | `frames=5 purge=3 words=512 tlasts=4 maxrun=128 dangling=1` · `fifo_ovf=1` · **J1/J2/J3 全 FAIL** | `frames=4 purge=4 words=385 tlasts=4 maxrun=128 dangling=0` · `fifo_ovf=0` · **三条全 PASS** |
| 实例 2（`2100 7 0`） | `popped=2107 expect=2108 first_bad=2048` · `maxocc=2049 ovf_cyc=1 stat_fifo_ovf=1` · **FAIL** | `popped=2108 expect=2108 first_bad=-1` · `maxocc=2048 full_seen=1 ovf_cyc=0 stat_fifo_ovf=0` · **PASS** |

- 实例 1 的 `words=512 = 385 + 127` 与 §2.3 的复算**逐数吻合** ⇒ 构造是精确的（不是统计现象）。
- 实例 2 的 `maxocc=2048`（修后）说明**饱和照样到得了**，但**不再丢字节** ——
  修复把"静默丢"换成了正确背压（写口在满时停一拍等 pop）。这比"到不了满"强得多：
  它是**在饱和态下**被验证的。
- `J1 (#tlast == stat_frames)` 是**协议合同**级判据（每个 commit 的帧必须在输出侧恰好
  出现一次），不依赖任何内部信号 ⇒ 修前的 FAIL 是"板上也会发生的现象"的直接搬演。
