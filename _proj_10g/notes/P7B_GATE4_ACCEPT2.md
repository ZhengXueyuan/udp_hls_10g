### 5.1 ⭐ F3 的独立判据（本轮新增，取代上一轮"无判别力的 8080 对照"）

## 9. 三处 FAIL / 一处 SKIP 的归因（每条都给原始证据；**未做任何"改东西凑 PASS"**）

### 9.1 速率类：`N_XCHK` / `F4` / `N_SELF` / `T_RUN` —— **偏差与 FAIL 都归到判定口径侧**

**四口径同窗对照**（板子自报 `W20` / 网卡 `port_rx_good` / pcap 时间戳 / 内核 `rx_packets`）：

| 轮 | 板侧 ΔW20/dt | 网卡 Δport_rx_good/dt | 偏差 | 备注 |
|---|---|---|---|---|
| accept 测量窗 | 630,681 / 5.9399 s = **106,177 fps** | 423,598 / 3.9028 s = **108,539 fps** | +2.2% | 两窗不同刻 |
| xchk 探针（**严格同窗**） | 535,141 / 5.0492 s = **105,985 fps** | 561,027 / 5.0488 s = **111,124 fps** | **+4.6%** | 同窗、同长 |
| var 探针 轮1（同窗） | 425,261 / 4.0119 s = **106,000 fps** | 529,498 / 4.0116 s = **131,993 fps** | **+24.5%** | |
| var 探针 轮2（同窗） | 425,200 / 4.0115 s = **105,996 fps** | 349,230 / 4.0115 s = **87,057 fps** | **−17.9%** | |
| var 探针 轮3（同窗） | 425,264 / 4.0119 s = **106,001 fps** | 423,598 / 4.0120 s = **105,582 fps** | **−0.4%** | |
| **pcap 时间戳**（独立路径，12:41:56） | — | 2999 帧 / 0.028306 s = **105,949 fps** | — | 与板侧 −0.05% |
| **本轮内容抓包时间戳**（12:52） | — | 2999 帧 / 0.028298 s = **105,944 fps** | — | 与板侧 −0.05% |

**结论（证据级，不是推断）**：
1. **板侧 `W20` 帧率极稳**：三轮同长窗口 `106,000 / 105,996 / 106,001 fps`（**±0.002%**），
   且载荷字节自洽：`ΔW9 = 787,727,056 ≈ 535,141 × 1472 = 787,727,552`（差 **496 B = 半帧在飞**，
   是快照锁存时刻的正常截断）⇒ 载荷率 **1.248 Gbps ≈ 1 B/拍 × 156.25 MHz**（与设计明文"字节串行"一致）。
2. **网卡计数口径不稳**：同一台机、同样长的窗口，`Δport_rx_good/dt` 给出 **87 k ~ 132 k fps**
   （±25%），**物理上不可能**（板侧的帧源是固定速率硬件发生器）。
3. **第三条独立路径站在板侧一边**：pcap 时间戳两次都给 **105,949 / 105,944 fps**（与板侧 −0.05%）。
4. ⭐ **`port_rx_*` 不是独立硬件计数**：`port_rx_packets` 与内核 `rx_packets` **逐字相同**
   （`1081941695 == 1081941695`）、`port_rx_bytes` 与 `rx_bytes` **逐字相同**（`346179975404 == 346179975404`）
   ⇒ 与上一轮对 `port_tx_*` 的发现**同族**：**NIC 报出来的"硬件计数"就是内核计数的镜像**，
   **不构成独立口径**（这正是用户全局指令里"多校验器逐位一致 ≠ 独立证据"的又一实例）。
5. `N_SELF` 的 1 帧偏置（`423,598 + 0 ≠ 423,597`）与上面同源：`ethtool -S` 逐字段**非原子**读取
   （一次 dump 里各字段取自不同时刻的寄存器）⇒ 在 42 万帧窗口内出现 ±1 偏置。**独立窗口复算**
   `N_SELF` 成立（`561,027 + 0 == 561,027`）。⇒ 归因"**判定口径的读取非原子**"，**未归因到设计**。
6. **F4/N_XCHK 判 FAIL 的口径本身不成立**（参考侧不稳）⇒ 本轮**不给设计下定论**；若要闭合，
   需要一条**真正独立**的速率基准（例如把 pcap 时间戳口径固化成判据，或换一台 NIC）。

**`T_RUN` FAIL = 工具侧天花板，不是板子**：`p6e_udp_pattern` 是**用户态 UDP socket** 收包，
其 `SO_RCVBUF` 被内核钳在 8 MB（工具自报"实收 8.0 MB"），而板子以 **106 k fps × 1472 B ≈ 156 MB/s** 在发，
且它对每个落位不齐的帧要做 64 KB 窗口重同步（每帧最多 6.5 万次 xorshift）⇒ **实收只有 ~100–1660 帧/轮**、
`接收侧掉包 ~50%`；当连续丢帧超过 64 KB 重同步窗时它报"真失配"（本轮 `4/1665`、`1/1662`）。
⇒ 与它自己的注释一致（"**接收侧丢包 ≠ 图案错**"）。板的**内容清白由 §5.1 的独立口径判定**（2999/2999）。

### 9.2 ⚙️ 工具缺陷：`p7b_gate4_accept.sh` 的 **N_XCHK 判据结构性永不评估**（未改脚本）

`main()` 里的守卫是 `if [ -n "${NQ_NC+x}" ] && [ -n "${NB_NC+x}" ]`，而 `NB_NC`/`NQ_NC` 是
**关联数组**（`declare -A`，键是 `port_rx_good` 这类非数字串）。bash 语义：**`${assoc+x}` 只测下标 0**，
下标 0 不存在 ⇒ **恒为空** ⇒ 该 `if` **永远为假**。
实测（本机 bash）：
```
declare -A A; A=(); A[foo]=1; echo "[${A+x}]"        →  []
declare -A C; C[bar]=2;       echo "[${C+x}]"        →  []
D=(); D[0]=1;                 echo "[${D+x}]"        →  [x]   ← 普通数组才成立
```
⇒ 上一轮报告里写的"N_XCHK SKIP（ΔW20=0）"**其实也从未被评估过**（当时也打不出这一行；本轮 `grep -c XCHK
accept_run1.txt` = **0** 证实）。本轮的 N_XCHK 读数是**我手工复算**的（`p7b_gate4_2/xchk_computed.txt`）。
**未改脚本**（纪律要求），登记为工具待修项。

### 9.3 C8 FAIL 的归因：**饱和计数器不可判"在涨"**（事实未变，判定口径变严）

`board/wrapper_p4.v:3366-3379` 的 RTL 逐字：
```verilog
if (pcs_vcc_sr[2] && (pcs_vcc_cyc != 8'hFF)) pcs_vcc_cyc <= pcs_vcc_cyc + 8'd1;
```
`pcs_vcc_cyc` 是 **8 位饱和计数器**，在 `dp_clk`(156.25 MHz) 下 **1.6 µs 内就饱和到 0xFF**；
同一段 RTL 的注释自己写着："用途是'这条线有没有动过'；★ **不得当精确事件数引用**"。
⇒ 本轮 `255 → 255`：
- **正证据成立**（"线被钉 0"会读 0，这里是 255）—— C8 想防的"恒 0 假干净"没有发生；
- **"持续增长"结构性不可判**（已饱和）。
⇒ 如实判 **FAIL**（脚本口径），归因"**观测量设计上限**，非被测设计的状态问题"，并登记：
若要闭合需**加宽该计数器或另加一个 tick 位**（属观测面改动，本轮无权限）。

## 13. 结论

1. **lane4 修复在板上兑现**：单发 1/1、成批 **20/20**（p ≈ 1.1×10⁻⁸）被 app 认领；
   **图案流 2999 帧逐字节等于图案流、偏移 0 起连续、覆盖 100%**（独立路径 + 实现自检 + 锚点自证）。
2. **`rx_classify`/RX 前端在 2M 最小帧（754 kpps）洪泛下 `drop_full` 恒 0，守恒律逐字成立**。
3. **PCS/链路/B 组/G 组判据全绿**，三域频率反解全部落在标称 ±0.22% 内。
4. **3 条 FAIL 全部归因到判定口径**（C8 饱和计数器 / T_RUN 用户态接收天花板 / N_SELF 非原子读），
   **没有一条指向新的设计缺陷**；**N_XCHK 因参考侧（网卡计数）自身不稳而不可判**，
   并新发现 **`port_rx_*` 是内核计数的镜像、不构成独立口径**。
5. **未测**：F5（TCP @10G）、10G 线速（app 发生器是 1 B/拍，结构性到不了 10G）、lane4 的 +1 拍双模态。
