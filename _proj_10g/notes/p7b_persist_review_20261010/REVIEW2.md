### ①-1 环真的断了吗？—— **成立（断），且 mux 顺序变更是真载荷、不是装饰**

依赖图（【事实】，逐线核）：

```
probe_sel(组合) ← { ps_stage_rdy, ps_stage_estab(寄存器),
                    rx_idle=(rx_state==RX_IDLE)&&recv_first(寄存器),
                    rx_flush(寄存器), ctrl_slot_busy(寄存器),

svc/ring_eval/scan_now ← 只含 rx_idle/ack_pend_r/retx_active/rx_flush/retx_req(端口)/

                        ⇒ **均不含 rb_id 派生项**          （`:510-517` 逐行核过，v2 说法成立）
```

- **判**：`probe_sel → rb_id → rb_state` 这条边存在，但 `rb_state` **不再回到 `probe_sel`**（`probe_sel` 只吃寄存器 `ps_stage_estab`）⇒ **组合环断** ✅。
- **派单的"环只是被延后一拍"这一疑点 —— 不成立**：采样拍 = `scan_now` 拍；在 v2 的 mux 顺序里 **`scan_now` 优先级高于探询 arm**，且 `scan_now=1 ⇒ svc=ring_eval=0`（`:516-517` 逐字）⇒ 采样拍 `rb_id ≡ scan_id`，**与 `probe_sel` 无关** ⇒ 样本载荷不来自探询自身 ⇒ 无"延后一拍"的反馈。【事实+一步推理】
- ⭐ **顺带一条 v2 没说、但确实修掉的隐患**：v1 把探询 arm **插在最前**，则**扫描拍**若 `probe_sel=1`，`:998-1020` 的 RTO 扫描、`:798-802` 的 `fin_push`/`rst_push`（都读 `rb_state/rb_snd_nxt/rb_snd_una`）会**读成探询连接**的值 ⇒ v2 的"arm 挪到 `scan_now` 之后"把这半也堵上了。⇒ 该顺序变更**是有牙的**（且 `!scan_now` 子句**不是冗余**：它保证 fire 拍槽装载（`:1025-1034` 的 `ctrl_id/ctrl_seq/ctrl_wnd/cam_rd_*`）真的取自 `ps_stage_conn`，而不是靠 mux 兜底）。【推断·结构性】
- ⚠️ **唯一前提**：采样必须**被扫描拍门控**（v2 修订表 row 2 与 §2.3 都这么写）。但 **§2.5-③ 的措辞是"T+2 收 (byte, seq, estab)"** —— 与 §2.3"T 拍锁 seq/conn/estab"**冲突**；若实现者按 §2.5-③ 在 T+2 采样，样本可能取自**别的连接**（T+2 拍 `rb_id` 未必 = `scan_id`）⇒ 守卫语义漂移。**【事实·行文歧义】⇒ 见「TL 必须拍板」#3。**

### ①-2 ⭐⭐ **新发现（本轮最重）：`probe_sel` 漏了第 5 个 `rb_id` 消费者 —— 数据帧启动拍**

v2 的守卫集合 = `!svc && !ring_eval && !scan_now && !retx_active`，声称"rb_id 读槽互斥"。**核判：不完整。**

【事实】`:547-548` 的 mux 里 `rb_id` 的 arm 有**五个语义用途**：svc 拍、ring_eval 拍、scan_now 拍、**`(rx_state==RX_IDLE) ? start_id : f_conn[rx_bank]`**，加上（v2 新增的）探询 arm。其中 `start_id` 这个 arm 被**两处**消费：

1. `start_ack` 槽装载（`:1022-1040`）—— 这正是 v2 处理过的（靠 `!svc` 等）；
2. ⭐ **数据帧启动拍的 TCB 锁存**（`:1043-1057`）—— **`start_data`（`:562-565`）的门里没有 `probe_sel` 也没有任何与其互斥的项**。

【事实】`:1043-1057` 那一段（`accept && recv_first`）用 `rb_*` 与 `cam_rd_*` 锁存 `f_seq/f_ack/f_wnd/f_dmac/f_dip/f_sport/f_dport/tap_seq`，而 `f_conn <= start_id`；`:673 w_tap_seq = start_data ? rb_snd_nxt : tap_seq` 还把 **ring 写游标**也钉在 `rb_snd_nxt` 上。

【事实】对照组：`start_data` 自身**逐字包含** `!svc && !ring_eval && !scan_now`（`:562-565`）⇒ 那三个 owner 与"数据帧启动"是**双向互斥**的；而探询拍与"数据帧启动"**没有任何一项互斥**：

- `probe_sel` 要 `ackq_empty`（不是 `!ack_pend_r`）；数据启动要 `!ack_pend_r` —— 两者**可同拍为真**（FIFO 弹出的次拍：`:912 ack_pend_r <= !ackq_empty` 滞后 1 拍）；
- `probe_sel` 不检查窗口；数据启动要 `wnd_open=1` —— 两者**可同拍为真**（正是"窗刚重开"的恢复瞬间；`wnd_open` 是 `tcb` 的**注册**输出 `rtl/tcb.v:153-157`，其 `win_id = rb_id`（`board/wrapper_p4.v:2006`，头注 `:1741`））；
- `probe_sel` 不检查 `s_axis_tvalid/fifo_full/bank_rdy/rx_flush`；数据启动要它们全开。

⇒ 同拍出现 `probe_sel=1 && start_data=1` 时，mux 给出 `rb_id = ps_stage_conn`（探询 arm 在 `start_id` arm **之前**），于是：
**【推断·结构性，链条逐步有源码依据】** 数据帧的 `f_seq/f_ack/f_wnd` 取**探询连接 A** 的 TCB、`cam_rd_*`（`cam_rd_id=rb_id`）取 **A 的对端四元组**、`tap_seq`/`w_tap_seq` 也取 **A 的 `snd_nxt`** —— 若 `ps_stage_conn ≠ s_axis_tid`（多连接场景），结果是：**该数据帧带着 A 的 dst MAC/IP/端口与 A 的 seq 上线，并按 A 的 seq 写进 ring**。单连接（A == B）时四元组恰好自洽 ⇒ **门/板级的"单连接"用例结构性看不见它**。

【事实·可达性所需的三个条件**全部不依赖时序侥幸、都是结构量**】① 探询已武装并完成暂存（多连接里有一条在 stall）；② fire 拍上 `ackq_empty=1 ∧ ack_pend_r=0`（ACK 帧 T_DONE 之后的稳态拍）；③ 同拍另一条连接的数据帧满足 `start_data`。★ 注：`wnd_open` 用的是 `rb_id` 的窗口 ⇒ 本碰撞要求**探询连接 A 的注册窗已开**（即"窗刚重开"那一小段）—— 这既是可达条件，**也是这条缺陷最讽刺之处：它正好落在探询机制"要修好"的那个瞬间**。

**要不要推翻 v2？** 不推翻 v2 已写对的与有据的；但 **v2 §2.4-2 的收束句"…⇒ 环断"与"rb_id 读槽互斥"** 按上面核判 **是不完整断言**（漏一个消费者）⇒ **降级为"部分成立"**。【补一句公平话】v1 同病且更糟（arm 在最前，scan 拍也会被抢）；**v2 不是引入者，但自述已解决 —— 这一半没解决。**

⛔ **实现警告（给修法的人）**：最省事的补法 `probe_sel && !start_data` **会形成新组合环** —— `start_data` 含 `!tx_blk_sid`（`:505`），而 `tx_blk_sid = tx_blk[start_id] | ~st_ok | ~acks_ok`，其中 `st_ok = (rb_state == 4'd1)`（`:489`）是**组合** `rb_state` ⇒ `probe_sel → rb_id → rb_state → st_ok → tx_blk_sid → start_data → probe_sel` = **环**。【事实·逐线推导】环安全的候选 = 只排除"数据帧**即将启动**"的**无 `rb_state` 派生项**条件，例如
`&& !(recv_first && s_axis_tvalid && !ack_pend_r && !fifo_full && !bank_rdy[rx_bank] && wnd_open)`
（全部操作数都是寄存器/输入/FIFO 状态；`wnd_open` 是注册输出 ⇒ 不引环；stall 期 `wnd_open=0` ⇒ 不饿死探询）。**本候选是我方建议、未受设计者复核。**

### ①-3 "打拍 = 用陈旧状态"：连接离开 ESTAB 时探询会不会照发？—— **会；v2 未处理；这是修法引入的新边界**

【事实】`ps_stage_estab` 的**刷新周期 = 扫描周期 = 16 连接 × 16 拍 = 256 拍 ≈ 1.638 µs**（`scan_tick` = `tick_cnt==15`，`:476`/`:914`）。守卫样本在 T 拍采样，到**下一次扫到同一连接**之前不会再更新。⇒ 若连接在 `[T, 下一次扫描]` 内离开 ESTAB（对端 FIN、本端 close→`fin_sent_r`、abort→`rst_sent_r`、慢路径拆链），**探询仍会发出**（`probe_sel` 里没有任何"当前态"检查）。

- 这不构成组合环（打拍的意义所在），但**代价正是"陈旧"**：v1 的组合读**总是当前值**（代价 = 环）；v2 换成样本 ⇒ 环断、**引入 ≤1 扫描周期（+暂存链 2 拍）的陈旧窗**。**v2 的正文（§1.1/§2.3/§2.4/§3.4/§8.3）没有登记这个窗**。
- 落点冲突：**§3.4-3 的板级可判量写着"连接拆除后 0 探询"** —— 按上面的窗，**该判据字面不保证成立**（拆除后 ≤1.64 µs 内发出的 1 条探询不会被任何东西拦住；而 §3.4-3 的机器落点"扫描拍 + 暂存命中同 id 时清"**最早就发生在下一次扫描**）。
- 危害量级：一条 1 字节旧数据段 + `flags 0x18`（对端回 ACK 或 dup-ACK）；**不是**"垃圾字节"（D-5 的 FIN/RST 角已在武装条件里排除，因为 `fin_sent_r/rst_sent_r` 在**采样拍**已置位即可挡住），故记为**边界/口径问题**而非数据损坏。
- ⇒ **裁定：成立**（作为"D-2 修法引入、v2 未登记"的新边界）；建议：登记 + 把 §3.4-3 的板级口径改成"拆除后**至多 1 条**且时间 ≤1 扫描周期"，或加廉价复验（见下）。

### ①-4 `!svc` 等四条守卫"加得对不对"

- 【事实】`svc`（`:510-511`）不含 TX 引擎状态、不含 `ctrl_slot_busy`。`!svc` 对"svc 拍抢读槽"**足够**：探询让位是单向的（`probe_sel` 含 `!svc`），而 `svc` 无需知道探询 —— 与 mux 里 svc 优先级更高自洽。
- 【事实】**既有 `ack_pend_r` 互斥没有被 v2 破坏**：HEAD 的互斥是"`start_ack` 要 `ack_pend_r`；`svc/ring_eval/scan_now` 要 `!ack_pend_r`"；⑤ 把 `|| probe_sel` 折进 `start_ack` 后，`start_ack` 落到 `!ack_pend_r` 那一侧 —— 但 `probe_sel` 自带 `!svc`（且 `!ring_eval/!scan_now`）⇒ 四拍仍是两两互斥。`upd_wr_ctrl` 的 FIX-2' 语义也被 ① `&& !probe_sel` 保住（`:534` 一线未动，靠新子句门掉陈旧 `ackq_dout`）。**结论：这四条子句本身加对了**；缺口在**未列**的那条（①-2）。
- 【事实】`!retx_active` 与 `!ring_eval` 冗余（`ring_eval ⊆ retx_active`），冗余无害。
