## 2. 主判据

### 2.1 算式（逐字，可直接实现）

```
# 取同一快照 A 与 B（§5.3 的编排）
dW5  = (W5_B  - W5_A ) mod 2^32          # FE 域拍数
dW24 = (W24_B - W24_A) mod 2^32          # DP 域拍数
dW20 = (W20_B - W20_A) mod 2^32          # MAC 发帧数

# 时基两种取法（必须互证）
fps_FE = dW20 * f_fe / dW5               # ⭐ 首选：同**束**（W20 与 W5 同在快照 FE 束；
                                          #    ⚠️ 但锁存钟 gmii_clk 与 W20 的源钟 tx_fe_clk 是两个
                                          #    时钟，标称同频、ppm 级差 —— 见 §1.2 与 §5.3）
fps_DP = dW20 * f_dp / dW24              # 交叉：DP 域，兼验"三域同频"
f_fe = 156.25e6  (标称; 由 §5.2 的墙钟自证落在 ±1% 内)
f_dp = 156.25e6  (同上)

载荷吞吐 (bps) = fps * 1472 * 8          # 1472 = app 的 UDP 载荷（W9 口径的每帧字节数）
线上吞吐 (bps) = fps * 1538 * 8          # 1538 = 1500(IP 总长)+14(ETH)+4(FCS)+20(PRE+IFG)
                                          #  ⇒ 两者之比恒为 1472/1538 = 0.9571（口径自洽检查）
```

**为什么时基用板内自由计数而不是主机墙钟**：
① 主机墙钟的分辨率/抖动（PCIe 事务、调度）会把误差直接写进分母；
② 两次触发之间的**真实间隔**在板内被 156.25 MHz 数得**精确到 1 拍**（相对 6.4e-9）；
③ 触发延迟抖动**不加偏**——它被计进 `ΔW5`（真实墙钟）而不是漏掉（§5.3 说明为什么）。
主机墙钟**只用来**给 `f_fe`/`f_dp` 做 ±1% 的粗校准（既有判据 C9 的形态）。

### 2.2 期望值推导（拍/帧 → fps → Gbps，全部为设计真值，不是估计）

**每帧 XGMII 拍数**（`mac_tx_10g.v:19` 的公开公式，1472 B 载荷）：

```
帧内容长度 L = 1472 + 8(UDP) + 20(IP) + 14(ETH) + 4(FCS) = 1518 B
拍/帧 = 1(前导) + ceil(1518/8)(内容, 末字与尾向量合并) + 1(尾字) + IFG(1~2, 平均 1.24)
      = 1 + 190 + 1 + 1.24 = 193.24 拍        ← 与 P7B_RATE_BOTTLENECK.md §1 第 6 级逐字相同
```

⇒ **fps = 156.25e6 / 193.24 = 808,579 fps**
⇒ **载荷 = 808,579 × 1472 × 8 = 9.523 Gbps**
⇒ 线上 = 808,579 × 1538 × 8 = 9.951 Gbps = 10G × **99.51%**

**与 802.3 口径上限的关系**（必须自洽，否则口径写错了）：

| 口径 | 拍/帧 | Gbps |
|---|---|---|
| 物理口径（8 B/拍 @156.25 MHz） | — | 10.000 |
| 802.3 满效（1472/1538 无损） | **192.25** | **9.571** |
| **本 MAC 的实测天花板** | **193.24** | **9.523** |
| 仿真全链（`P7B_RATE_FRAMER.md` 实测） | **193** | **9.534** |
| 旧模态（1 B/拍发生器） | 1474 | 1.248 |

> ⚠️ **9.534（仿真全链）不大于 9.523（MAC 公式）** 的原因：仿真取整到 193.000 拍，
> 而公式含 IFG 的平均 1.24 拍。**板级读数应落在 [9.50, 9.54] 内**；低于 9.50 说明有真实损失
> （查 §2.5 的四条辅助判据），高于 **9.571 则说明口径错**（§2.3 的硬上界）。

### 2.3 界的设定（为什么是 6.8 Gbps —— **不钉在任何样本极值上**）

可分辨的**模态**（每个都是实测/设计真值，不是猜测）：

| 模态 | 载荷 Gbps | fps | 含义 |
|---|---|---|---|
| M0 | **1.248** | 106,003 | 两刀都没生效（旧位流实测） |
| M1 | **4.870** | ~413,000 | **只有一刀生效**（8 路并行单独，实测；帧器仍 378 拍） |
| M2 | **9.523** | 808,579 | 两刀都生效（设计天花板） |

**界的设定规则**（全局指令第 7 条）：界要按"两个模态之间的**间隔**"设，钉在极值上会被噪声翻转。
⇒ 取 **M1 与 M2 的几何中点**（对数量纲上对两端等距）：

```
界 = sqrt(4.870 * 9.523) = 6.810 Gbps   ⇒ **判据取整 6.8 Gbps** (= 577,400 fps 载荷 @1472B)
（取整方向对判别力无害：到 M1 仍 +39.6%，到 M2 仍 −28.6%）
```

**这个界的判别力（两端各留多少）**：

| 方向 | 距离 | 相对裕量 | 含义 |
|---|---|---|---|
| 到 M1（只一刀） | +1.93 Gbps | **+39.6%** | 只生效一刀**达不到**界 ⇒ 判别力成立 |
| 到 M2（满效） | −2.72 Gbps | **−28.6%** | 板级实现损失允许 ~29% 仍算达标 ⇒ 不过脆 |

> ⚠️ **文档 / 代码 / 速查表三处必须是同一个数 6.8**（`p7b_rateplan/rate_calc.py` 的 `BOUND_GBPS`）。
> 本方案的取数器在自检里就带一条"**分级表与达标界不冲突**（界−ε 不达标 / 界+ε 达标）"的断言
> —— 因为第一版把分级表写成"≥4.5 不达标"在"≥界 达标"之前，6.81 附近两档互相打架，
> **是自检当场抓住的**（见 §10）。

**附加的硬上界（反向判据，防"口径错"）**：读数 **> 9.571 Gbps 一律判"不可信"**
（物理上不可能；成因是分母口径写错、窗口错位、或拿了两次不相邻的快照）。
**硬下界（防"空读当 0"）**：读数 < 1.0 Gbps 时，先按 §5.2 的守卫复查，
**不得**直接报"板子退化了"（历史上"空读被 `$(( ))` 当 0"伪造过"计数冻结"。

### 2.4 分级读数表（triage 用，判据之外的归因工具）

| 实测载荷 | 判定 | 首要归因 |
|---|---|---|
| > 9.571 | **口径错** | 分母/单位/窗口，先查 §5.2 守卫 |
| 9.50 – 9.57 | 满效 | — |
| 8.5 – 9.50 | 达标（有可解释损失） | 查 §2.5 四条：abort / flush / txwire_stall / 每帧字数 |

| 2.5 – 4.5 | 不达标 | ≈ 4.87 且有余量损失 ⇒ 同时查 W21/W41 |

### 2.5 主判据的"有牙"证据（同批必须一起读的四条辅助判据）

主判据是**比值**，单看它会漏掉几类真实缺陷。以下四条**必须在同一快照对里成立**：

| # | 判据 | 期望 | 不成立时说明 |

| A2 | **`ΔW8 − ΔW20`** | **0 ≤ 差 ≤ 2**（且 `ΔW21 == 0`） | >2 ⇒ app 发了 MAC 没发出（管道堵塞）；<0 不可能 ⇒ W20 多计（见下） |

## 3. 独立口径（逐条评估 + 优先级 + 独立性核实）

### 3.0 "独立"必须分两个含义说清（本工程踩过的坑，全局经验第 34 条）

- **含义①（对端内部）**：对端主机上报的两条计数，是不是同一条的复制品？
  → 若是 ⇒ **不能**拿它们互证。
- **含义②（跨设备）**：对端口径与**板侧**口径是不是不同源？
  → 跨设备天然不同源；但**只有当口径本身是硬件计数、且不被主机侧行为截断时才可信**。

**本次 ssh 实测（2026-09-30，只读）** 把两个含义都钉死了，见 §3.1.2 与附录 A。

### 3.1 口径 A（首选）：对端 NIC 的 MAC 硬件计数

**硬件**：`Solarflare SFC9120 10G Ethernet Controller [1924:0903]`（`01:00.1` = `enp1s0f1np1`），
驱动 **in-tree `sfc`**（`/lib/modules/7.0.0-34-generic/kernel/drivers/net/ethernet/sfc/sfc.ko.zst`，
内核 7.0.0-34-generic，固件 `6.2.7.1001 rx1 tx1`）。

#### 3.1.1 字段族与用途

| 字段 | 语义（本方案认定） | 用途 |
|---|---|---|
| **`port_rx_packets`** | MAC 层收到的帧总数 | ⭐ **与 `ΔW20` 对账**（"线上真的到了吗"） |
| `port_rx_good` | MAC 判 good 的帧 | 与 bad 一起做分裂分析 |
| `port_rx_bad` | MAC 判 bad 的帧（⚠️ **与 `rx_crc_errors` 逐字相同**） | 非 0 增量 ⇒ 帧到了但被判坏 |
| `port_rx_bytes` / `port_rx_good_bytes` | 字节系列 | ⭐ **平均帧长自检**（§4-N-b0） |
| **`port_rx_nodesc_drops`** | MAC 侧因**无描述符**丢弃的帧 | ⭐ **"对端吃不下"的量化器** |
| `port_rx_overflow` | MAC 内部 FIFO 溢出 | 非 0 ⇒ 该窗口 NIC 计数是**下界** |
| `rx-0.rx_packets`（per-channel） | DMA 通道**交付**计数 | ⭐ 与 `port_rx_good` 做**四项差分账**（§8-R1） |
| **`rx_eth_crc_err`** | **EF10 MAC stats**（另一统计块） | ⭐ **与 `port_rx_bad` 相互独立的 CRC 证据** |

#### 3.1.2 ⭐ 独立性核实（本次 ssh 实测原始读数，三对逐字相同）

```
/sys/class/net/enp1s0f1np1/statistics/rx_packets   = 2600444047
ethtool -S  ...  port_rx_packets                   = 2600444047      ← 逐字相同
/sys/class/net/.../statistics/rx_crc_errors        = 1020633512
ethtool -S  ...  port_rx_bad                       = 1020633512      ← 逐字相同
/sys/class/net/.../statistics/rx_dropped           = 109876
ethtool -S  ...  port_rx_nodesc_drops              = 109876          ← 逐字相同
（另：rx_errors = 1020633512 ≡ rx_crc_errors ≡ port_rx_bad）
```

**结论（三条，逐条可用）**：

1. ❌ **对端内核 netdev 计数不是独立口径** —— 它是 MAC 统计的**别名**（sfc 驱动
   `efx_nic_update_stats` 把 MAC 统计写进 netdev）。⇒ **禁止**把"内核说收到了 N 帧"当作
   "MAC 说收到了 N 帧"的独立确认（这正是 `P7B_GATE4_CRITERIA_CLOSEOUT.md` §3.2 的结论，
   本次是**第二次独立复证**）。
2. ✅ **`port_rx_*` 本身是硬件计数、且独立于板侧** —— 它是另一颗芯片的另一套计数器；
   **`rx_eth_crc_err`(1) 与 `port_rx_bad`(1,020,633,512) 值完全不同** ⇒ 它们是**两套独立统计块**
   （前者 = EF10 MAC stats，后者 = legacy port stats），不是别名。
   ⇒ 用 `port_rx_*` 与板侧 `W20` 对账，是**跨设备**的独立口径。
3. ✅ **内部结构自洽**（可当"读数确实是一次真读数"的自证）：
   `port_rx_good + port_rx_bad = 1,579,810,536 + 1,020,633,512 = 2,600,444,048`
   vs `port_rx_packets = 2,600,444,047` ⇒ **差 1**（RX 通路上有两个计数点，至多一帧"在飞"）
   ⇒ **容差 ±2**（`p7b_gate4_accept.sh` 的 `N_SELF` 已就地改成 ±2，同一现象）。
   同理 `port_rx_good_bytes + port_rx_bad_bytes = port_rx_bytes`（**逐字相等**）。

#### 3.1.3 ⚠️ 必须实测验证的一条（V1）：ring 满时 `port_rx_packets` 还准吗？

**这是整个独立口径的支点，不许假设。** 两种可能的硬件行为：

- **(甲)** `port_rx_packets` 统计"MAC 收到的帧"，**与驱动能否取走无关**
  （`port_rx_nodesc_drops` 单独存在、且与 `rx_dropped` 逐字相同，**支持甲**）
  ⇒ 那么"对端仅计数不抓包"就是**最高速率下唯一可行的独立口径**（这正是任务书问的
  "对端不需要吃满的口径"）。
- **(乙)** `port_rx_*` 只统计"成功 DMA 到主机"的帧 ⇒ 那么它在 800 kfps 下会**退化成台架天花板**，
  读数会与板侧 `W20` 出现无法归因的差额。

**裁决实验（零成本，就是本方案的一次常规测量）**：在同一窗口内同时取

```
d_board = ΔW20                     （板侧说发了多少帧）
d_mac   = Δport_rx_packets         （对端 MAC 说收到多少帧）
d_dma   = Δrx-0.rx_packets         （对端 DMA 说交付多少帧）
d_nd    = Δport_rx_nodesc_drops    （对端 MAC 说丢了多少帧）
```

| 观测 | 判定 | 后续 |
|---|---|---|
| `d_mac ≈ d_board`（±0.5%） | **甲成立** ⇒ 独立口径可用 ⭐ | 若 `d_dma < d_mac` 且 `d_nd ≈ d_mac − d_dma` ⇒ 差额被解释为"对端交付瓶颈" ⇒ **板子达标** |
| `d_mac ≈ d_dma < d_board` | **乙成立** ⇒ 独立口径在高速档**不可用** | 降级：速率裁决只报板侧 + §4-N-b0 量程自检；独立对账**移到低速档**（§4-N-b1） |
| `d_mac < d_board` 且 `d_dma ≈ d_mac` 且 `d_nd = 0` | 疑似**线上丢失**（物理层） | 查 `Δrx_eth_crc_err` / `Δport_rx_bad` / `Δport_rx_overflow`（§8-R1） |

> ⭐ **这条实验同时解决两个历史欠账**：① 上面 V1；② 现存
> `port_rx_good`(1,579,810,536) 与 `rx-0.rx_packets`(1,403,489,479) 之间 **1.77 亿帧**的历史差额
> —— 用**同一窗口的 Δ** 就能判定这两族计数是不是"同一条路径的两个副本"（V2，§9）。

#### 3.1.4 A 的优先级与代价

- **优先级：A1（最高）**。成本 = **一条 ssh 命令**（`ethtool -S` + 9 个 sysfs 字段）。
- **不需要**抓包、不需要 socket、不需要主机把包交付给栈。
- 唯一要求：网卡**在线**（carrier=1）且我们是**唯一的流量源**。

### 3.2 口径 B：`tcpdump -w` 落盘 + 离线统计（评估结论：**内容口径，不作速率**）

**定量评估**（1472 B 载荷 ⇒ 线上 1518 B/帧，800 kfps）：

| 项 | 数值 | 结论 |
|---|---|---|
| 落盘带宽（全帧 + 16 B pcap 头） | 800k × 1534 B = **1.23 GB/s** | 普通 SSD（~0.5 GB/s）**必丢**；NVMe 也贴边 |
| `-s 96` 截断后 | 800k × 116 B = **93 MB/s** | 盘能扛 ✅ |
| **pps（截断不改善）** | **800 kfps** | ⚠️ 这是真瓶颈：**单队列 + 单核**，经验上限 ~1 Mpps ⇒ 贴边 |
| sfc 队列实测 | `rx-0` 独跑（14.03 亿），`rx-1/2/3` = 0 / 5 / 1546 | ⚠️ **单流 RSS 到单队列** ⇒ 无多核分担 |

**丢包自证**：tcpdump 退出时打印 `N packets dropped by kernel`（`PACKET_STATISTICS`，
统计 `packet_rcv` 里 ring 满的丢包）。**它的覆盖面有硬边界**：

- ✅ 能证"**ring 满了**"（此时该行非 0）；
- ❌ **不能**证"**全收到**"：抓包点在 `__netif_receive_skb_core` 的 `ptype_all`
  ⇒ **驱动侧 `nodesc` 丢掉的包根本到不了 tap** ⇒ "0 drops" 只说明"到了 tap 的没丢"。
  ⇒ **必须与 `Δport_rx_nodesc_drops` 联读**（否则会把"驱动丢包"读成"全收到"）。

**结论与用法**：
- **降级为内容口径 + 帧数下界**。它最大的价值是**逐字节**（`F3` 已用 pcap 逐字节 2999/2999 通过），
  以及**端点跨度时间戳**（`pcap_rate.py` 的端点口径，`F4` 的独立口径）。
- ⚠️ **时间戳是批量打戳的**（同一条流 3000 条记录只有 555 个不同时间戳）⇒
  **禁用帧间隔分布**，只用端点跨度 + 去重自证（`pcap_rate.py` 已写死这条纪律）。
- ⚠️ 在 800 kfps 下**端点跨度可能仍不可用**（帧数太少 ⇒ Δt 极短 ⇒ 桶粒度不确定度爆炸）。
  实测方式：先跑 3 秒，看 `pcap_rate.py` 打印的"不同时间戳 / 桶宽"是否大到不可用。
- **优先级：B2**（内容）；速率不用。

### 3.3 口径 C：对端减小帧（评估结论：**不推荐**，方向可能相反）

**核心事实**：板子的帧率上限由**每帧拍数**决定（`mac_tx_10g.v:19` 的公式），**不是**由字节数决定：

```
拍/帧 = 1 + ceil(L/8) + 1 + IFG       ⇒ L 小 ⇒ 拍/帧小 ⇒ 帧率更高 ⇒ 对端 pps 压力更大
```

| 载荷 L | 拍/帧 | fps | 载荷 Gbps | 对端 pps |
|---|---|---|---|---|
| 1472 | 193.24 | 808,579 | 9.523 | 808 k |
| 512 | 92.24 | 1,693,900 | 6.941 | **1.694 M** ⚠️ |
| 64（最小） | 36.24 | 4,311,400 | 2.207 | **4.31 M** ⚠️ |

⇒ **"减小帧换来对端吃得下"这条因果链在此设计上不成立**：总带宽确实降了，**但 pps 涨了 2–5 倍**，
而 pps 才是对端的天花板。**不可用于 CPU 侧口径的抢救**。

**保留其正确的一半（并入 A）**：**用帧数（而不是字节数）做交叉核对** ——
这正是 §3.1 的做法（`Δport_rx_packets` vs `ΔW20`，两边同单位）。
**尺寸口径的零成本等价物**也保留：`port_rx_1024_to_15xx` / `port_rx_64` 等**长度桶**必须与
`Δport_rx_good` 对得上（§4-N-b0 的第三连）。

**优先级：C3**（只保留"帧数对账"与"长度桶"两个子项，已并入 A）。

### 3.4 口径 D：对端"只在线、不吃包"（**这是 A 的用法层，也是任务书问的那条**）

**做法**：测量窗内**不跑任何抓包、不跑任何收包应用、不给 socket**，只让网卡在线。
- ✅ 这是**唯一在 800 kfps 下仍然可行**的独立口径（B 会丢、C 方向反）。
- ⚠️ 但要额外确认：**没有别的进程在收这批帧**（`ping`/`ss`/后台抓包）。
  `p6e_udp_pattern` 这类工具**必须停掉**（它自己就是 0.091% 的收包天花板）。
- ⚠️ 主机侧仍要**避免把包交给协议栈**（否则 800 kfps 会把主机打爆，产生
  连锁的 `nodesc_drops`）。最稳的是**关掉 netdev 或改 MAC 滤波**？—— **不要**：
  关掉 netdev 会让 `ethtool -S` 的读取路径也可能受影响。
  ⇒ **保持 up、不发包给 socket 即可**（没人 bind 那个端口 ⇒ 内核会回 ICMP port unreachable？
  ⚠️ 注意：UDP 无监听会回 ICMP，这会**产生反向流量**。⇒ 用 `iptables -I INPUT -p udp --dport 8081 -j DROP`
  **不产生回包**地吃掉它，或者接受这点微不足道的反向流量并**在 NIC 的 `port_tx_*` 上把它认出来**）。
  ⚠️ 该 iptables 规则会改对端机状态 ⇒ **需要用户/带 `--sudo` 的执行者确认**，本方案只登记为选项。

### 3.5 优先级总表

| 优先级 | 口径 | 独立于板侧 | 独立于对端内核 | 800 kfps 可用 | 成本 |
|---|---|---|---|---|---|
| **A1** | `port_rx_packets`（MAC 计数） | ✅ | — | ✅（待 V1 裁决） | 1 条 ssh |
| **A2** | `port_rx_nodesc_drops`（吃不下量化） | ✅ | 是（≠ 内核 rx_dropped 之外无别名） | ✅ | 同 A1 |
| **A3** | `ΔW43/ΔW20` 与 `Δport_rx_good_bytes/good`（量程自检） | 两边各一 | ✅ | ✅ | 零 |
| **A4** | per-channel `rx-0.rx_packets`（四项差分账） | ✅ | ✅（≠ port 族） | ✅ | 同 A1 |

## 4. 负对照（三条，全部要求"真做得到"）

### N-a（零重建，最高优先）：拉 `TX_DIS` 掉链

**动作**（逐字，注意 `0x08` 不是 `0x10` —— 闸 4 首轮被这条误导过一次）：

```bash
T=/home/a/xdma_test                       # reg_rw 所在目录（按对端实际部署调整）
$T/reg_rw /dev/xdma0_user 0x08 w 0x2      # scratch[1] = 1 ⇒ sfp2_tx_dis = 1
echo -n scratch_readback=; $T/reg_rw /dev/xdma0_user 0x08 w | tail -1   # 必须读回 0x00000002
sleep 2
for f in carrier operstate speed carrier_changes; do echo -n "$f="; cat /sys/class/net/enp1s0f1np1/$f; done
```

**判据（两条，必须都成立）**：

| # | 判据 | 期望 | 说明 |
|---|---|---|---|
| N-a1 | 写后**读回** `0x08` | **`0x00000002`** | 自证"写落地了"（否则负对照本身没做） |
| N-a2 | 对端 `carrier` | **0**（且 `carrier_changes` **+1**） | ⚠️ **判 link 只认 `carrier`/`operstate`/`Link detected`**；`Speed:` 在无 link 时是**陈旧残留值**（仍读 10000） |
| **N-a3** ⭐ | **`Δport_rx_packets` = 0**（在掉链后的窗口内） | = 0 或 ≤ 2 | **证明对端口径有牙（不是恒真）** |
| **N-a4** ⭐ | 同时读 `ΔW20`（板侧） | **记录实测值，不预设** | 两种结果**都有信息**：<br>· 若 `ΔW20 = 0` ⇒ 板子依赖 link（判据也不是恒真），且两条口径**同步失效**（弱化独立性主张，需补 §4-N-b0）<br>· 若 `ΔW20 > 0` ⇒ ⭐ **两条口径的独立性被直接证明**（板子在空发，对端一无所知） |

**恢复**：`$T/reg_rw /dev/xdma0_user 0x08 w 0x0` ⇒ `sleep 3` ⇒ 复核 `carrier=1`（`carrier_changes` 再 +1）。
**恢复后必须重新建流**（见 §7 步骤 7：peer 表需要 learn-on-RX）。

**代价**：**零重建**。一条写寄存器 + 一次 carrier 读 + 恢复。**不改位流、不改 RTL、不改构建。**
⚠️ 副作用：掉链会中断本次测量会话 ⇒ 放在**主测量之后**做；且恢复后要重跑一轮主判据确认读数回到原值。

### N-b0（零重建）：量程自检二连（**用设计真值检验两套计数器**）

**思路**：速率判据是"每秒多少帧"，要证它可信，就要用**另一个已知真值量**灌进同两套计数器。
这里有两个**彼此独立、且都由设计确定**的真值：

| # | 判据 | 期望 | 独立性 |
|---|---|---|---|
| B0-1 | **`ΔW43 / ΔW20`** = 每帧 XGMII 字数 | **193.24 ± 0.1** | 板内（分子分母同一 MAC 的两个计数器） |
| B0-2 | **`Δport_rx_good_bytes / Δport_rx_good`** = 平均帧长 | **1518 ± 2** | 对端（分子分母同族，但**与 B0-1 是不同设备、不同单位**） |
| B0-3 | **`Δport_rx_1024_to_15xx / Δport_rx_good`** ≈ 1 | ≥ 0.99 | 长度桶（另一个计数器） |

**判别力**：两个设备、两套单位、同一个物理量（帧长）——**同时**落到设计真值上，才能说
"计数器在工作、单位对、窗口对、流是我们这批帧"。
❗ 若 B0-1 对而 B0-2 错 ⇒ **对端的帧不是我们的帧**（别的东西在打流，或混了背景流量）。
❗ 若 B0-2 对而 B0-1 错 ⇒ **板子在发非 1518 B 的帧**（短帧/超长/中止残帧）。
❗ 两个都错 ⇒ 先查 §5.2 守卫（空读/窗口/回绕），**不要**先怀疑设计。

**代价**：**零**（就在主测量的同一批读数里算）。

### N-b1（**需重建**）：`TX_GAP` 低速档 ⇒ 读数必须精确落到预测值

**动作**：把 `rtl/app_udp_pattern.v` 的 `parameter [15:0] TX_GAP`（现默认 `16'd0`）改为
**一个已知的大值 `G`**（建议 `G = 100000` ⇒ 期望 fps ≈ 156.25e6/(193.24+100000+2) ≈ **1559 fps**，
载荷 ≈ **18.4 Mbps**，比任何插座/内核路径的天花板低三个数量级）⇒ 重建 ⇒ 烧 ⇒ 重启对端。

**判据（相对式，不依赖绝对标定 —— 这是本条的判别力来源）**：

```
θ = 1 + 193.24/fps_TG0                      # 用同构建 TG=0 档实测的每帧拍数反解
预测 fps_TG1 = fps_TG0 / (θ + G * fps_TG0 / 156.25e6)
判据：|fps_TG1实测 − 预测| / 预测 ≤ 1%
```

**为什么必须是相对式**：`TX_GAP` 改的是 RTL 参数，**改造后的发生器/帧器每帧拍数可能与 §2.2 的
193.24 不同**（8 路并行 + 乒乓会改 app 侧的 T_GAP/T_IDLE 拍数）。
⇒ 用 **TG=0 档的实测 `fps_TG0`** 反解出真实每帧拍数，再预测 TG=G 档。**这样两档共用同一个未知量，
未知量被消掉。**

**这条负对照证明什么**：证明判据**不只会在一个点上读** ——
它能在相差 **500 倍**的两个速率上都精确落到预测值 ⇒ **量程可信**。
同时：低速档下对端**必定吃得下**（1559 fps）⇒ 此时 `Δport_rx_packets ≈ ΔW20` **必须逐字吻合**
（±2 帧）⇒ 这也是 §3.1.3 的 **V1 裁决的实验版**（若低速档都不吻合，说明对端口径本身坏了）。

**代价（必须写清）**：
1. 改 `rtl/app_udp_pattern.v` 的**一个数字**（parameter 默认值）⇒ **改源码**；
2. **一次全设计构建**（`board/run_build_p7b_ku5p.bat` 级，**~22 min**，
   `P7B_HANDOFF.md` §3 记载的实测值）；
3. **一次烧录** + **一次对端机重启**（顺序：先烧后重启）；
4. **一次恢复构建**（把 `TX_GAP` 改回 0，再 22 min + 烧 + 重启）——
   ⚠️ **不做第 4 步就会把低速位流留在板上**（下一轮接手会读到一个"明明是 18 Mbps"的板子）。
   ⇒ **实际总代价 ≈ 2 次构建 + 2 次烧录 + 2 次重启 ≈ 1.5 小时**。
5. ⚠️ **构建期间不得烧位流、不得起 Vivado**（本工程铁律 + 另一路 agent 的构建所有权）。
6. ⚠️ `TX_GAP` 的**语义**在 8 路并行/乒乓改造后可能变化（"帧间插入 N 拍空闲"的插入点）
   ⇒ **动手前先读改造后的 RTL**，并以上面的相对式为准（相对式对语义变化免疫）。

> ⭐ **建议的取舍**：**先做 N-a + N-b0 + 一轮主测量**。只有当
> ① 主判据落在 4.5–6.8（疑似只一刀生效）或 ② §3.1.3 的 V1 判成"乙"（独立口径退化）时，
> 才值得付 N-b1 的代价。**N-b1 是"可选加固"，不是"必做"**。

### 5.1 回绕预算（每一个用到的字都要算，不是只算 W24）

| **W5** `gmii_free` | 32 | 156.25 MHz | 27.49 s | 391 M | ✅ |
| **W24** `dp_free` | 32 | 156.25 MHz | 27.49 s | 391 M | ✅ |
| **W43** `stat_tx_words` | 32 | 808,579 × 193.24 = 156.2 M/s | **27.49 s** ⚠️ | 391 M | ✅（同量级，别拉长窗口） |
| W20 / W8 | 32 | 808.5 kHz | **5,311 s** | 2.02 M | ✅ |
| W0/W1/W36/W37（RX 侧） | 32 | 低 | 长 | — | ✅ |

⇒ **窗口 = 2.5 s（下限 2.0 s，硬上限 3.6 s）**。
**回绕的处理原则**：主判据只用 W20/W5/W24（窗口内**结构上不会回绕**）；
W9 与 W43 **只作交叉**，且**必须带回绕校正 + 回绕标记**（`Δ = (B − A) mod 2^32`，
并打印"本窗口是否发生过 mod 回绕"，发生过 ⇒ 该交叉项**降级为旁证**）。

> ⚠️ **不用 20 s 长窗的理由**：20 s 内 W9 回绕 5 次、W43/W5/W24 各 0–1 次
> ⇒ 回绕校正变成主路径，脆弱且难以自证。**短窗 + 高帧数（2 M 帧）已经把统计误差压到 7e-4**。

### 5.2 自证（四层守卫，逐层都要打印，缺一层整轮作废）

| 层 | 检查 | 失败含义 |
|---|---|---|
| L1 **身份** | `MAGIC == 0x50360001` 且 `BUILD_ID == 期望` 且 `MARKER == 0xDEADBEEF` | 读的不是我们的逻辑 / 位流是旧的（**sha256 也要核**） |
| L2 **完整** | 51 个字**下标连续 0..50、无重复、无空读**（值必须匹配 `^0x[0-9a-f]{1,8}$`） | 空读 ≠ 真 0；旧脚本的"末字回绕成低地址字"正是**重复**形态 |
| L3 ⭐ **归属** | **`gen` 恰好 +1**（`0x1C[31:16]`，mod 65536） | **这一代快照不是我触发的 / 有并发写者** ⇒ 读数不可归因 |
| L4 ⭐ **稳态** | 同一配置连做 **A/B 两轮**，`fps_A` 与 `fps_B` 差 **≤ 1%**；且两轮的 `ΔW21=ΔW41=ΔW42=0` | 差 >1% ⇒ 窗口内有启停/竞争 ⇒ 该轮读数不作速率裁决 |

> ⚠️ **L3 不是可选项**：本工程实测踩过"读失败被 `$(( ))` 当成 0 ⇒ 静默伪造出'计数冻结'"，
> 以及"拿一个值和它自己比"（`PORT_NOTES.md` 的"失聪"小节）。
> **现成实现**：`_proj_pcie/p7b_gate4_accept.sh` 的 `rd()` / `rd_new()` / `snap()` / `round()`
> 四层守卫 + `parse_snap()`（含上面 L1/L2/L3 全部检查）—— **直接复用，不要自己重写**。

### 5.3 取数编排（关键：时基来自板内，不来自主机时钟）

```
T0:  触发快照 #1 → 轮询 done → 读 51 字（记 W5_A / W24_A / W20_A / ...）
     [此刻板侧锁存发生，锁存时刻被 W5/W24 计数记下]
sleep 2.5
T1:  触发快照 #2 → 轮询 done → 读 51 字（记 ..._B）

Δt = ΔW5 / 156.25e6                 # 两次锁存之间的真实间隔（板内精度 1 拍）
fps = ΔW20 / Δt
fps' = ΔW20 / (ΔW24 / 156.25e6)      # 交叉（应一致到 ppm 级；差 >0.1% ⇒ 报警）
```

**为什么触发延迟抖动不会破坏读数**：
设触发 #1 的写事务延迟 `d1`、触发 #2 为 `d2`。板侧的锁存时刻分别是 `t1+d1`、`t2+d2`。
`ΔW5` 数的是 `(t2+d2) − (t1+d1) = (t2−t1) + (d2−d1)` ⇒
**`ΔW5` 里已经包含了真实的锁存时刻差**（它度量的就是"两次锁存之间"），
所以 `fps = ΔW20/Δt` 度量的是**两次锁存之间的平均帧率**——**d 的抖动不引入偏置**，
只是把窗口的边界挪动了 ≤ 几 ms（相对 2.5 s = 2e-3 相对误差，且两侧对称）。
⚠️ 唯一的真实风险是"锁存时刻恰好落在一个帧的中间" ⇒ 边界效应 **±1 帧 / 2 M 帧 = 5e-7** ⇒ 可忽略。

**同束优先（附一条时钟域订正）**：`W20` 与 `W5` **同在快照 FE 束** ⇒ 首选 `fps_FE`。
但**"同束"不等于"同时钟"**（见 §1.2）：

| 量 | 生产者 | 真实时钟 | 来源 |
|---|---|---|---|
| `W20` / `W21` / `W41` / `W43` | `mac_tx_10g` | **`tx_fe_clk = tx_mii_clk_1`** | 本地晶振 Y2（156.25 MHz） |
| `W5`（锁存 FE 束的钟） | wrapper | **`gmii_clk = rx_clk_out_1`** | **对端 CDR 恢复**（跟踪对端） |
| `W24` | wrapper | **`dp_clk`** | Y1 100 MHz × 1.5625 |

⇒ 三者标称同频、**互差 ppm 级** ⇒ 用 `W5`/`W24` 当 `W20` 的秒表，引入 **ppm 级**误差
（相对 §2.3 的 40% 判据裕量：**可忽略，但必须登记**，否则会被当成"读数没有来源"）。

**它换来的一条免费报警判据（写进判据表）**：

```
|fps_FE / fps_DP − 1| ≤ 0.1%      ← 三域同频的自证
```
- 成立 ⇒ 三把时钟都在 156.25 MHz 上（既有的 C9 判据是 ±1% 粗判，这条是 10× 更严的交叉）；
- **不成立 ⇒ 报警**：某个时钟真跑偏了（CDR 没锁在 156.25 / MMCM 配置错 / 构建宏错）。
  ⚠️ 这条**不是**为了提精度（判据裕量 40%），而是为了**发现"位流配置不对"这一类错误**
  （例如 `DP_156MHZ` 没开 ⇒ `dp_clk` 还是 125 MHz ⇒ `fps_DP` 会偏 25% ⇒ 立刻现形）。

## 8. 风险清单（按"会不会让读数变成台架天花板"排序）

### R1 ⭐⭐ 最大的坑：**对端"交付"天花板把读数变成台架极限**

**机理**：sfc 的 `port_rx_*` 与内核计数同源（§3.1.2）；若硬件行为是**乙**（只数交付到主机的帧），
则 800 kfps 下驱动单队列（`rx-0` 独跑，~1 Mpps 经验上限）会先到极限 ⇒
**对端口径报出的速率是"对端能吃多少"，不是"板子发了多少"** ⇒ 读数变成台架天花板。
历史上同一个坑已经以另一种形态出现过：`p6e_udp_pattern` 收包率 **0.091%**
（socket 层，`_proj_10g/notes/P7B_GATE4_CRITERIA_CLOSEOUT.md`）。

**怎么区分是板子慢还是对端慢（四项差分账，必须同时读、同刻读）**：

```
d_board = ΔW20                      板侧: MAC 发了多少帧
d_mac   = Δport_rx_packets          对端: MAC 收到多少帧
d_dma   = Δrx-0.rx_packets          对端: DMA 交付多少帧
d_nd    = Δport_rx_nodesc_drops     对端: MAC 因无描述符丢了多少帧
d_ovf   = Δport_rx_overflow         对端: MAC 内部 FIFO 溢出
d_crc   = Δrx_eth_crc_err           对端: EF10 MAC 的 CRC 错帧
```

| 观测组合 | 判决 | 下一步 |
|---|---|---|
| **`d_mac ≈ d_board`**（±0.5%）且 `d_dma < d_mac` 且 `d_nd ≈ d_mac − d_dma` | ⭐ **板子清白、对端交付瓶颈** ⇒ **板子达标**（"板子慢"被排除） | 报"板侧达标 + 对端天花板"，并**用 A3 量程自检**给这份结论背书 |
| `d_mac ≈ d_dma ≈ d_board` | 全链对账 ⇒ **最强结论** | 收工 |
| `d_mac < d_board` 且 `d_dma ≈ d_mac` 且 `d_nd ≈ 0` | **线上真丢**（不是对端） | 看 `d_crc`（>0 ⇒ FCS/物理层）、`d_ovf`；再查 `ΔW21/ΔW41` |
| `d_board` 本身就低（如 400 kfps） | **板子慢** | §2.5 的 A1–A5；查是哪一刀没生效 |
| `d_mac` 与 `d_board` 都低，但 `ΔW43/ΔW20 = 193.24` 正常 | 板子在按 MAC 天花板发，但**上游供不上** | 查 `ΔW29`（txwire_stall）、`ΔW8 − ΔW20` |
| `d_crc > 0` | 帧到了但对端判坏 | **物理层/链路**（不是速率问题）：查板对板连接器/光模块（本板是贴边设计） |

**预防措施（在测量前就能降低这个风险的三个动作）**：
① **停掉对端一切收包进程**（§3.4 口径 D）；
② **先做 §4-N-b1 的低速档**（1559 fps ⇒ 对端必定吃得下）⇒ 在该档上先证明
   `d_mac ≈ d_board`（**证明对端口径在量程内是准的**），再上高速档 ⇒
   高速档的差额就有了"锚"（**这是最干净的归因顺序**）；
③ **把 `ΔW43/ΔW20` 与 `Δport_rx_good_bytes/good` 当"锚"**：只要这两个都落在设计真值上，
   就说明两套计数器都在正常工作，差额就不是"计数器坏了"。

### R2 主判据的分子分母同错（**同源失效**）

`fps = ΔW20/Δt`。若 `Δt` 的时基错（例如 `f_fe` 实际是 125 MHz 而非 156.25），
读数会整体偏 25% 且**看不出来**。
⇒ **防御**：① `fps_FE` 与 `fps_DP` 互证（§2.1）；② 用**墙钟**对 `W5`/`W24` 做 ±1% 检查（C9）；
③ §4-N-b0 的**每帧字数**与**帧长**两个绝对量把"单位"钉死。

### R3 快照读的"空读/陈旧/回绕"三连（本工程实测踩过每一种）

- 空读被当 0 ⇒ 伪造"计数冻结"；重复下标 ⇒ 末字回绕成低地址；`gen` 不涨 ⇒ 读的是上一代。
⇒ **防御**：直接复用 `_proj_pcie/p7b_gate4_accept.sh` 的 `parse_snap()`（三种都查），
**不自己重写**（重写就是重新踩一遍）。⚠️ 未实现地址 = **`0xEC`**（不是 `0xB0`，那是 36 字时代的）。

### R4 32 位回绕（**W9 只有 3.61 s**）

⇒ 窗口 ≤ 3.6 s；主判据只用不回绕的三个字；交叉项带回绕校正 + 标记（§5.1）。

### R5 `/32` 路由被 NetworkManager 静默冲掉

⇒ **每一轮发送前** `ip route get 192.168.100.2` 必须是 `dev enp1s0f1np1`（步骤 5）。
否则流量走默认路由 ⇒ 板侧收不到 ⇒ peer 表空 ⇒ **`ΔW20 = 0`**（看起来像"板子坏了"）。

### R6 烧录/重启的次序（不可换）

⇒ 见 Runbook (P2)。PCIe 端点只认"FPGA 先配置"；反序则根端口放弃链路，**四种主机侧补救手段实测全无效**。

### R7 构建期间不得烧位流（并发 agent）

⇒ 见 Runbook (P1)。**另一路 agent 正在跑合并构建**：`board/build_p7b_ku5p.tcl`、
`board/p7b_ku5p_*`、`vivado_prj/p7b_ku5p_prj*`、`_proj_10g/notes/P7B_RATE_BUILD.md`
**都不许碰、不许起 Vivado**。

### R8 对端单队列 + 单流 RSS

⇒ 800 kfps 全部落在 `rx-0` 一个核上。**不要**期望多核分担；也不要因为它而误判板子。
（可选的缓解：`ethtool -N`/RSS 改哈希—— **会改对端状态，本方案不做**，只登记。）

### R9 `port_rx_bad` 的 10 亿历史量与尺寸分布不匹配

实测 `port_rx_bad = 1,020,633,512`，其尺寸桶集中在 **128–255 B**（`port_rx_128_to_255 = 1,020,633,506`），
而 good 集中在 1024–15xx。⇒ **历史累计**（早期调试流），**与本次 1518 B 帧无关**。
⇒ **必须用 Δ，不用绝对值**；且若测量窗内 `Δport_rx_bad > 0` **且**尺寸桶指向 1024–15xx
⇒ 那是**我们的帧被判坏**，必须查（`Δrx_eth_crc_err` 是独立证据）。

### R10 W20 的计数语义（帧内中止会多计）

⇒ §2.5-A3：`ΔW21 = ΔW41 = ΔW42 = 0` 是主判据的**前提**，不是可选检查。

> ⚠️ **自检当场抓到过一个真错**（记录在案，因为它正是"量测函数自检"这条纪律的价值证明）：
> `grade()` 的第一版把分级表的 `≥4.5 不达标` 写在 `≥6.8 达标` **之前**
> ⇒ 6.81 附近两档互相打架（**判据表自相矛盾**）。
> 若不带自检，这个错会在板上读数落进 6.8–8.5 区间时报"不达标"，
> **看起来像"板子只跑了一刀"** —— 归因方向全错。现已修，并加了
> "**分级表与达标界不冲突（界−ε 不达标 / 界+ε 达标）**"这条常驻断言。
