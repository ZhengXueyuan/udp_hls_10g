## 1. 第一步：反例双跑裁定 —— "这两条门对该缺陷不敏感" 成立，且原因是结构性的

### 1.1 台架怎么造的（为什么不能直接拿门跑缺陷版）

门脚本把 RTL 源**硬写**成 `%REPO_ROOT%\rtl\app_udp_pattern.v`，而工作区那份**必须是修好的**
（不许覆盖 = 派单边界）。⇒ 造一个**配方逐行照抄**的台架：

* 文件表、TB 源（`tb/tb_app_udp_rate.v`）、cfg→`-d` 映射、implicit 检查、判据行 **全部与门同款**；
* 只多两个旋钮：**被测 `app_udp_pattern.v` 的路径** 与 **额外 `-d`**（经 `RATE_ARM_DEFS` 环境变量传入）；
* 每条臂的日志头留 `certutil -hashfile` 的 **md5 + 绝对路径** ⇒ 反例跑用的确实是缺陷版。

**台架 ≡ 真门（等价性实测，不是声明）**：同一份固定 RTL、同一 cfg（`g0p1472`）下，
台架 `H5` 与**真门** `gate_g0p1472` 逐项相同 —— `checked pushes=7640`、`full_cyc=3640`、
`framer 1514 x40`、`wire 1525 x35`。两者只差"RTL 源怎么选"。

### 1.2 裁定

| 门 | 缺陷版（`...prefix.v`, md5 `20137a9b…`） | 裁定 |
|---|---|---|
| `sim/p5e_rate/run_tb_rate.bat` | **绿**（exit 0） | ❌ **无牙** —— 两层原因，见 §1.3 |
| `sim/p5e_udp/run_tb_app_udp.bat pos` | **红，但红错了原因**（`errs=1`） | ❌ **判别力 0** —— 见 §1.4 |

### 1.3 速率门为什么绿（两层，缺一不可）

**① 它根本编不到缺陷所在的那条路径。** 缺陷只在 `P7B_10G`（8 B/拍）下可达，而：

```
$ git show HEAD:sim/p5e_rate/run_tb_rate.bat | grep -n 'P7B_10G'      # 空
$ git show HEAD:sim/p5e_udp/run_tb_app_udp.bat | grep -n 'P7B_10G'    # 空
$ git grep -n 'P7B_10G' HEAD -- tb/                                    # 空
```

⇒ 改动前门的 cfg 只有 `{g0,g1380,g2760,g5000,g58000}×{p1472,p996,p512}`，**没有任何档加 `-d P7B_10G`**；
`tb/` 下**所有 TB** 也都不含该宏。**"8 B/拍" 这条路径在全仓仿真里从未被编过。**
（本轮新增的 `p7b1472` 就是补这一格。）

**② 就算编到了，它也没有判据。** `run_tb_rate.bat` 的判据只有一行
`findstr /C:"RATE TB DONE"`（跑完就算过），其余 7 行全是 `findstr` **打印**。 ⇒ 把缺陷版强行
编进 `P7B_10G` 后（台架 `H2`），**判据行全部命中**（`EVIDENCE_step1.txt` §E1 逐键计数：7/7 命中），
门照样 exit 0 —— 而它的打印里 `mean wire len = 1517`（修好是 `1525`），**差 8 B 摆在那里没人判**。

**③ 默认档为什么"看起来没事"（对 `P7B_W9_FIX.md` §2 的一处订正）。**
那份笔记说默认构建"占用长期只有个位数 ⇒ 结构性够不到 `D-1`"。**本门实测不支持这句**：
默认档 `g0p1472` 下 `full_cyc = 3640`（FIFO **确实**被顶满过 3640 拍）。
真正的理由是**相位锁定**：逐字节发生器每 8 拍才置一次 `pause`（`bcnt` 与排水相位锁死），
"落笔拍恰满"这个**一拍宽**的交点始终不出现 ⇒ 实测缺陷版在该档 `C1 = 0`（**不丢字**，
与修复 agent 的"输出逐位相同"一致）。⇒ 结论不变，但**理由要写成"相位锁定"，不是"够不到满"**；
这也正是覆盖见证 `full_cyc` **只能是必要非充分条件**的原因（见 §2.3）。

### 1.4 `p5e_udp pos` 为什么"红错了"（同址同刻，双版本逐字节相同）

把 `-d P7B_10G` 强加给它之后：**缺陷版与修复版给出完全一样的失败**：

```
udp_pos_def_p7b (app md5 20137a9b…): Memory Collision Error on RAMB36E1 :
   tb_app_udp.u_split.u_uf.gen_mem[0].u_main.gen_sdp.gen_wide.INT_RAMB_SDP.chk_for_col_msg
   at simulation time 24572.   |  P5E UDP APP GATE: FAIL errs=1
udp_pos_fix_p7b (app md5 58db9d5d…):  同上, 同一址、**同一时刻 24572**
```

⇒ 它红的是**另一件事**（`udp_split` 帧缓冲 BRAM 的读写碰撞），与本缺陷无关 ⇒ **判别力 0**。
外加它对自己的 `u_app` 用 `TX_GAP(16'd5000)`：8 B/拍发生器每帧只忙 ~190 拍、然后等 5000 拍，
FIFO 每帧都被排空 ⇒ **激励结构性到不了饱和**（实测同类档 `full_cyc=0`）。

**⇒ 该门**：**不建议**落本判据（跑不起来 × 激励到不了饱和），改为**明确写出**
「本门不能覆盖饱和档，由 `sim/p5e_rate` 的 `p7b1472` 档覆盖」（派单允许的第二种交付）。

> ⚠️ **顺带发现的未覆盖面（不在本轮范围，需另立一项）**：`P7B_10G` 的 **RX 侧**（宽比对
> `rx_tready`）**没有任何 TB 编过**（`git grep P7B_10G -- tb/` 为空），一旦强行编出来就在
> `udp_split` 的帧缓冲上出 BRAM 碰撞。**它可能是 TB 激励问题（坑 17 同族），也可能是真 RTL 问题 ——
> 本轮没做三态判别**，只登记现象与证据（`logs/EVIDENCE_step1.txt` §E2）。

## 2. 第二步：判据设计（按合同逐句配，不按现象）

### 2.1 合同原文 → 判据

合同（`rtl/fifo_sync.v` 头「写口合同」+ `rtl/app_udp_pattern.v` u_txf 处）：
`txf_wr` 是**寄存器**（本轮决定、**下拍落笔**）⇒ 落笔那一拍 FIFO 必须不满；否则这笔
**已计入 `stat_tx_bytes`/`seg_sent`** 的推入被 FIFO 静默丢弃。逐字写成不变式：

```
不变式 (合同):  txf_wr(T) ⇒ !txf_full(T)
```

| 判据 | 形式 | 观测点 | 为什么这样写 |
|---|---|---|---|
| **C1（主）** | `u_app.txf_wr && u_app.txf_full` 的**拍数必须 0** | app 的**生产者侧**两根寄存器 | 合同逐字、**逐拍**（不是采样）；**无假阳性** —— 合法"把 FIFO 填满"那拍 `full(T)=0`（落笔发生在满之前），只有"落笔拍已满"才算违约 |
| **C2** | 帧器逐帧输出长度 == `FRM_EXP` 且 `min==max` | 帧器 AXIS 口（`m_tvalid&&tready` 按 `tkeep` 计字节，`tlast` 处取整） | 不变式的**可观测形态**①：帧几何恒等 + 单元素 |
| **C3** | 线上逐帧长度 == `WIRE_EXP` 且 `min==max` | `mac_tx_64` 的 `gmii_tx_en` 拍数 | 形态②，且与 C2 **不同观测点**（跨了配置/组帧/物理编码三层）⇒ 两条互为独立证据 |
| **COV** | 饱和模态下 `full_cyc >= SATFLOOR` | app 的 `txf_full` 累计拍数 | **覆盖率见证**：防"激励到不了饱和 ⇒ 判据空转" |

**期望值是推出来的，不是抄读数**（并在三档对账）：

```
FRM_EXP  = 42(ETH14+IP20+UDP8) + PAYLEN                // FCS 由 mac_tx_64 加
WIRE_EXP = 8(前导+SFD) + 42 + PAYLEN + 4(FCS) - 1       // -1 = 本 TB 计数约定
  实测: PAYLEN=1472 → 1514 / 1525 ✓   PAYLEN=996 → 1038 / 1049 ✓   PAYLEN=512 → 554 / 565 ✓
```

**判别力（能区分相邻错值）**：本缺陷的错值是**每帧 -8 B**（少 1 个整字）。
C2/C3 的**绝对值判据**（`1517 ≠ 1525`）与**单元素判据**（`1506 vs 1514`）会同时/分别触发；
一半帧短一半帧长（锁相漂移）由单元素判据抓。实测 H2：C2 **两条都触发**（真实混布 1506/1514），
C3 触发绝对值那条（35 个采样帧全 1517，本台架相位锁死 ⇒ 未采到混布样本，见 §5 风险①）。

### 2.2 为什么落在**速率门**（而不是 `p5e_udp` / p7b 单元门）

1. **它本来就是"帧几何"的门**：它已经在量线上长度（`mean wire len`）——判据不是新加一个观测量，
   而是把**已经量到的量**从"打印"改成"判"，判据与门的主题同源；
2. **它的链最短**：`app → udp_tx_cfg → udp_tx_frame → mac_tx_64`，没有 `tx_arb`、没有慢路径、
   没有 HLS ⇒ 出问题时可归因面最小；
3. **它有"结构性 8:1 产消差"的档**：`P7B_10G`（8 B/拍）对 `mac_tx_64`（1 B/拍 GMII）
   —— 只要 `TXGAP=0` 就**必然饱和**，覆盖模态不需要"造"人肉相位；
4. **另一条门（`p5e_udp`）结构性不合适**：§1.4。

### 2.3 覆盖面论证（**必须**写在纸上的那句）

* **能覆盖**：`p7b1472` = `-d P7B_10G` + `TXGAP=0`。物理模态 = 发生器 8 B/拍、消费者 1 B/拍、
  背靠背推 ⇒ FIFO 被顶到满并**长期驻留**。实测 `full_cyc` = **55670**（修复臂 H3）/ **55326**（缺陷臂 H2），真门同档亦 55670，
  远高于 `SATFLOOR = 20000`。
* **边界怎么定的**（按"两模态之间的间隔"，不钉极值）：饱和档 `55670` ↔ 非饱和档
  `{0（g58000/g1380/g5000 带 P7B_10G）, 949（p512）, 1411（p996）, 3640（g0 默认档）}` ⇒ 取 **20000**
  （离两端各 2.8× / 5.5×）。**且** `SATREQ` 只在 `` `P7B_10G`` 且 `TXGAP==0` 时要求饱和
  ⇒ 既有档一个都不会被误判红（实测 H4/H9/H10 `full_cyc=0` 但 `satreq=0` ⇒ 绿）。
* ⚠️ **诚实标注（不许当"充分"）**：`full_cyc>0` 是**必要非充分** —— 默认档 `g0p1472` 实测
  `full_cyc=3640`（顶满过）而缺陷版 `C1=0`（**不丢字**，相位锁定）⇒ 这条见证**只能证伪
  "激励够不到饱和"，不能替 C1 担保**。判据本体是 C1（逐拍、无假阳性、不看采样）。
* ⚠️ **本门覆盖不到的相邻模态**：`P7B_10G` 但**有**帧间隔（`TXGAP≠0`）实测 `full_cyc=0`
  ⇒ 该模态结构性不可能触发本缺陷（H4/H9/H10 三条臂实测全绿，含缺陷版）——
  这是**结论**，不是空白（`SATREQ` 的条件就是按它写的）。

## 5. 踩到的坑（都是本轮实机撞的）

1. **`xvlog.log` 不能自己占用**：台架最初把 xvlog 的输出重定向到 `xvlog.log` —— 那正是
   Vivado 工具自己默认要写的日志名 ⇒ `CRITICAL WARNING: [Common 17-183] Failed to open handle
   xvlog.log ... restart from a writable working directory`，**工具根本没跑**，看着像权限问题。
   真门用的是 `xvlog_<cfg>.log` 才躲过。⇒ 重定向目标**不能与工具默认日志同名**。
2. **`call set "X=%%X%% -d %%D"` 会把 `%%D` 先吃掉**：`%%DEXTRA%%` 被解析成 `%%D` + `EXTRA` + `%`
   ⇒ 拼出 `P7B_10GEXTRA` ⇒ `ERROR: [XSIM 43-4316] Can not find file: P7B_10GEXTRA`。
   改成"字面量第 4 参 / 环境变量整串传入"。
3. **cmd 不能执行正斜杠相对路径**：`cmd //c "_proj_10g/notes/.../x.bat"` ⇒
   `'_proj_10g' 不是内部或外部命令` ⇒ 整条臂**静默无输出**（我用 `grep` 判红绿，聚合结果看着像"全红"，
   实际是"全没跑"—— 又一个"工具安静地什么都没做"）。批处理里一律用反斜杠形式。
4. **有符号/无符号比较**：`integer f_max <= -1` 作"未赋值"哨兵，与 `reg[31:0] + 4bit` 的**无符号**和
   比较 ⇒ `-1` 变成 4294967295 ⇒ "单元素"判据**结构性永不触发**（首跑把修复版判成
   `framer len NOT a singleton: min 1514 max -1`）。改用 `0` 作初值。
   ⚠️ 这正是"判据自己悄悄失效"的形态：**它红了**（假红），比不红更难发现。
5. **覆盖率见证的"必要条件"陷阱**：`full_cyc>0` 一开始被我当成"饱和已覆盖"的充分证据，
   实测默认档也 `3640` ⇒ 只是必要非充分。**"注入过 ≠ 测到了"**。
