# P7B 数据面速率独立核算 —— 64 位数据面本身能跑到多少 Gbps

**日期**: 2026-09-30 · **性质**: 独立核算（另一路 agent 在查"发生器那一跳"，本件**不依赖**其结论）
**方法**: ① 逐行读 RTL 推演每帧拍数；② 自建**只读**仿真 harness（`_proj_10g/notes/p7b_rate_dp/`，不改 `rtl/`、不改 `tb/`）实测同一批数字；③ 两者互证。
**前提（任务设定）**: **发生器不是瓶颈** —— 载荷源按"每拍 1 字 = 8 B/拍"的**饱和源**驱动（数据由寄存器组合导出，`!ready` 期间恒定，`ready` 下一拍立刻换字，零气泡）。

---

## 0. 一句话结论

| 问题 | 答案 | 证据等级 |
|---|---|---|
| **数据面上限（单流：只有 UDP，或只有 TCP）** | **4.84 Gbps**（1472 B 载荷 / **380 拍**）· TCP **4.80 Gbps**（1460 B / 380 拍） | 仿真实测（帧数 + TLAST 脉冲数双口径定拍，见 §6-B） |
| **数据面上限（双流并发：UDP + TCP，= wrapper 真实拓扑）** | ⭐ **9.51 Gbps**（实测 9507 Mbps，两个窗口复现） | 仿真实测 |
| **瓶颈级** | **`udp_tx_frame.v` / `tcp_tx_frame.v` 的"整帧存转发"结构**（一帧 380 拍里：收 184 拍 + 发 196 拍，**两段串行**） | 读 RTL + 实测双证 |
| **要跑到线速动哪一级** | 只动这两个帧器：**载荷 FIFO 改 ping-pong（双缓冲）⇒ 收帧 N+1 与发帧 N 重叠**，单流上限 **4.84 → 9.53 Gbps**（改动局部，两个模块）。⚠️ **双流（UDP+TCP 各一路）当前已经 9.51 Gbps，不需要改** | 读 RTL 推的（未落实现） |
| `rx_classify` v2 写侧 | ⭐ **每拍灌一个字**（不是每帧一个字）：实测 IN=OUT=**1.000 字/拍**、STALL=0、OVF=0、占用不增长 | 仿真实测 |
| `mac_tx_10g` / `mac_rx_10g` | **不是瓶颈**：TX 实测 11 拍/帧（最小帧，95.4%）· 193 拍/帧（最大帧，99.6%）；RX 结构 1 字/拍 | 仿真实测 / 读-RTL |

⚠️ **一句话给决策**: 修好发生器只能到 **4.84 Gbps**（单流天花板），**不等于 10G**；要单流吃满须同时动帧器。

## 1. 线速判据（自己复算，不抄注释）

**① 线速 → fabric 拍**
10GBASE-R 线速率 10.3125 GBd，64b/66b ⇒ `10.3125e9 × 64/66 = 10.0e9 bit/s`。
XGMII 侧 `64 bit × 156.25 MHz = 10.0 Gbps` ✔ 自洽。
⇒ **1 拍 = 64 bit = 8 B；10 Gbps = 8 B/拍 @156.25 MHz。**
（`mac_tx_10g` 每拍无条件发 1 个 XGMII 字，`stat_tx_words` 逐拍 +1 —— 这一条由实测 `XGMII_WORDS = CYCLES` 确认。）

**② 每帧线开销（字节）**：前导+`/S/`+SFD 组 **8** ＋ IFG（≥12 个 `/I/`）**12** ＋ FCS **4** = **24 B**（不含内容）。

**③ 载荷天花板（算式）**

| 封装 | 内容 = 14(eth)+20(ip)+L4头+载荷 | 线上字节 | 载荷天花板 |
|---|---|---|---|
| UDP/IPv4 | 14+20+8+**1472** = 1514 | 8+1514+4+12 = **1538** | `1472/1538 = 95.71%` ⇒ **9.571 Gbps** |
| TCP/IPv4（无选项） | 14+20+20+**1460** = 1514 | 8+1514+4+12 = **1538** | `1460/1538 = 94.93%` ⇒ **9.493 Gbps** |
| 最小帧（内容 60） | UDP 载荷 = 60−42 = **18** | 8+60+4+12 = **84** | `18/84 = 21.4%` ⇒ 2.14 Gbps（帧率上限 156.25/10.5 = **14.88 Mfps**） |

（1500 B L2 载荷 = 1472 B UDP 载荷；"1518 B 帧"= 1514 内容 + 4 FCS ✔ 与 `mac_tx_10g` 的 `ETH_MAX_FRAME` 一致。）

**每帧拍数模型（两种独立口径实测全覆盖，逐点一致）**：

```
P_udp = 2·⌈plen/8⌉ + 12   （末字 7/8 字节 = "尾分支"；末字 1..6 字节时 11）  ← 实测 18 / 28 / 104 / 196 / 380（k = 3 / 8 / 46 / 92 / 184）
P_tcp = 2·⌈plen/8⌉ + 14   （末字 3..8 字节 = "尾分支"；末字 1..2 字节时 13）  ← 实测 16 / 20 / 30 / 106 / 198 / 380（k = 1 / 3 / 8 / 46 / 92 / 183）
```
**固定开销 12（UDP）= S_WAIT 3 + S_HDR 5 + S_TAIL 1 + S_DONE 1 + `tx_arb`×2（2 拍）**；
**固定开销 14（TCP）= S_WAIT 5 + S_HDR 6 + S_TAIL 1 + S_DONE 1 + `tx_arb`×1（1 拍）**。
TCP 的偶发 `+1`（实测 106.17 / 198.09 = 每帧 0.09~0.17 拍）已归因 = **RTO 扫描 tick 撞车**（`tcp_tx_frame.v:332` 的 `!scan_now`，每 16 拍一次），与源码注释自述的"~1/16 帧"吻合。
⚠️ 这组数字由**两种互不依赖的口径**定死：① 窗口内**完整帧数**（周期是整数拍 ⇒ 唯一解）；② 全程 **TLAST 脉冲数** `cyc/pulses`（`AVG_PERIOD_X1000`）。两口径在 7 个 k 值上逐点一致（差 < 0.02 拍）。
⚠️ **仪表注**: TB 里那个"相邻 TLAST 间隔"仪表（`*_PERIOD_MIN/MAX`）**系统性低报 1 拍**（计数器在被测拍读到的是上一拍写入的值），第一版草稿曾据此误写成 379 / 17 —— 已按上面两口径纠正。**一律以帧数/脉冲数为准。**

## 4. 关键问题逐条回答

**Q1 稳态下限：一个背靠背最小帧（64 B 线上 / 60 B 内容）最少几拍？**
- `mac_tx_10g`：**11 拍**（实测；线侧预算 84 B = 10.5 拍 ⇒ 95.4%，是全链唯一接近线速的一级）。
- 数据面 `udp_tx_frame`（UDP 载荷只剩 18 B ⇒ k=3，末字 2 字节 = **无尾分支**）：**17 拍/帧**（实测，`AVG=17.003`）⇒ 帧率上限 **9.19 Mfps**（线侧可达 14.88 Mfps）⇒ **线上 6.18 Gbps，载荷只有 18/17 = 1.06 B/拍 = 1.32 Gbps**。
- TCP 最小帧（载荷 6 B ⇒ k=1，带尾分支）：**16 拍/帧**（实测，`AVG=16.004`）⇒ 9.77 Mfps ⇒ 线上 6.56 Gbps / 载荷 6/16 = 0.375 B/拍 = **0.47 Gbps**。
- `rx_classify`：8 拍/帧（= 字数，零死拍，实测）。

**Q2 1518 B 帧呢？** 实测 **380 拍/帧**（UDP，1472 B 载荷）→ **4.842 Gbps**；TCP 1460 B → 380 拍 → **4.803 Gbps**。**不是帧越小越快**：最小帧的载荷率只有 1.32 Gbps（UDP）/ 0.47 Gbps（TCP）。

**Q3 有没有哪一级的每帧固定开销让"背靠背满速"达不到？**
有，但**主因不是固定开销**，而是：
① **主因（结构性，−50%）**：两个帧器都是 **整帧存转发** —— 收 k 拍 + 发 k 拍**串行**，`s_axis_tready` 在发送期恒 0（`udp_tx_frame.v:502` / `tcp_tx_frame.v:473`）。⇒ 每帧 = `2k + 固定`，k 越大越接近 50%（1472 B 时 380 拍里只有 190 拍在往外吐字）。
② 次要固定开销（12 / 14 拍/帧，**已含仲裁的 2 / 1 拍**，占 380 的 ~3.2%）：UDP `S_WAIT 3 + S_HDR 5 + S_DONE 1 + S_TAIL 0/1`；TCP `S_WAIT 5 + S_HDR 6 + S_DONE 1 + S_TAIL 0/1`；`tx_arb` 每帧 1 拍重仲裁；TCP 另加 RTO 扫描 tick 的 ~1/16 概率 +1 拍。
③ 没有"每帧必须排空整条链"这种停顿；各级之间都是**弹性 FIFO + 帧级背压**（见 Q5）。

**Q4 ⚠️ 特别核：`rx_classify` v2 的写侧是"每拍灌一个字"还是"每帧灌一个字"？**
⭐ **每拍一个字**（P7b 刚改的那个模块已实测达标）：`s_axis_tready = !w_full`（`rx_classify.v:84`），分类只走**并行流水**（`widx` 计数 + 路由队列），读侧 `rd_ok = !w_empty && !rq_empty`。
实测（饱和源 + 双路由 ready）：`words_in = 20000 = cycles`、`words_out = 20000`、`STALL=0`、`OVF=0`、`RQ_OVF=0`、字 FIFO 占用稳定（6 或 3，不增长），**FW=8（最小帧 8 字）与 FW=19、fast 与 slow 路由全部 1.000 字/拍**。
⇒ v1 的"每帧死 3/6 拍"已确实消除，**这一级不再是瓶颈，也不需要再动**。
⚠️ 顺带（观测通道坑，非速率）：`dbg_stat_words_out` 只在 **fast 路由**时 +1（`rx_classify.v:177,187` 的 `f_acc`）⇒ slow（UDP/HLS）流水的"中间站词数"恒读 0，三站对账时别误判为丢字。

**Q5 各级之间的 FIFO 深度 / 反压语义**
| 级 | 深度 | 反压语义 |
|---|---|---|
| `mac_rx_10g` 输出 | 16 字 | `push_ok = !full_next`（精确下一拍满）⇒ 稳态 1 字/拍；装不下**整帧丢 + TERM 收尾**（F4），**绝不反压线上** |
| `rx_classify` 字 FIFO / 路由队列 | 16 / 16 | 写侧与下游**解耦**（下游停顿先吃 16 字弹性）；两队列同深 = 设计不变式 |
| `udp_tx_frame` / `tcp_tx_frame` 载荷 FIFO | 256 字（2048 B） | **存转发的物理载体**；深度就是长度上界的由来（`PLEN_MAX=1500 < 2048` ⇒ 结构性不死锁） |
| `tcp_tx_frame` ACK 队列 | 32 深 | 满则丢 + 计数（`stat_ack_drop`），不阻塞数据面 |
| `tx_arb` | 无缓冲 | 帧级锁定到 TLAST；每帧 1 拍重仲裁气泡 |
| `mac_tx_10g` 输入 | 16 字 | 断供 ⇒ 帧内中止 + 冲刷到 TLAST（F-2），不留幽灵帧 |
| `u_txcdc`（DP→FE） | 256 字异步 | DP 侧 `tready = !full`，本地组合、不跨域 |

**Q6 `tx_arb` 仲裁：TCP 空闲时 UDP 能不能独占？**
能。`busy` 锁到本帧 TLAST，`!busy` 才重仲裁，`sel` 在帧内冻结 ⇒ **帧原子性**保证；
TCP 有数据时**整帧抢占** UDP（单帧有界 ≤1518 B ⇒ 不会饿死）。
实测：单流时两个 `tx_arb` 合计只加 0~1 拍/帧；**双流并发时 UDP 仍拿到 155/311 帧 ≈ 50%**（TCP 156）⇒ 严格优先**没有**把 UDP 锁死，两条流按各自 50% 占空比自然交错。

## 5. 结论：瓶颈级与"要动多大"

**瓶颈级 = `udp_tx_frame` / `tcp_tx_frame`（整帧存转发 ⇒ 单流 50% 占空比）。**
- `mac_tx_10g` / `mac_rx_10g` / `rx_classify` v2 / 各 FIFO **都不是瓶颈**（前者实测 99.6% 线利用率，中间者实测 1 字/拍零死拍）。
- **单流上限 4.84 Gbps（实测）**；**双流并发上限 9.51 Gbps（实测）**。

**到线速要动什么（按性价比排序）**
1. ⭐ **帧器改 ping-pong（双缓冲）**：收帧 N+1 与发帧 N 重叠 ⇒ 每帧 ~`max(k_in, k_out) &asymp; k` 拍。
   改动 = 载荷 FIFO `256 → 2×256 字`（LUTRAM/BRAM，各 +2 KB）+ 帧首锁存/校验和寄存器成对化 + FSM 增加"收/发并行"一组状态；**模块局部**（`udp_tx_frame.v`、`tcp_tx_frame.v` 各一）。
   **预期上限 = `mac_tx_10g` 的 193 拍/帧 ⇒ 1472/193 = 7.627 B/拍 = 9.53 Gbps**（= 线速载荷天花板 9.571 的 99.6%）。**≈ 当前单流的 1.97×** —— 旁证：**双流并发时实测每帧 192.9 拍、聚合 9.507 Gbps**，那正是"帧器不再限速"之后的样子。
2. 发生器等上游必须同时到 8 B/拍（**另一路 agent 的范围**）——否则第 1 项改完也只到 1.25 Gbps。
3. app RX 校验器 1 B/拍 → 8 路并行（`app_udp_pattern`），否则 RX 方向 1.25 Gbps 就封顶，且帧缓冲会 `stat_drop_ovf`。
4. `tcp_rx` 在满尺寸段上的 ~99% 利用率（余量 ~2 拍/帧）**建议实测确认**：任何新增每帧开销都会把它推过 100%。

**不必动**: `mac_tx_10g`/`mac_rx_10g`（XGMII 层）、`rx_classify` v2、`tx_arb`、各级 FIFO 深度（除帧器内的载荷缓冲）。

## 6. 证据等级标注（本件坚持三分）

**A. 读 RTL 推的**（未实测，逐行可复核）
- 各 FSM 的状态数与拍数（UDP 固定 12 = `WAIT 3 + HDR 5 + TAIL 1 + DONE 1` + 两个仲裁器；TCP 固定 14 = `WAIT 5 + HDR 6 + TAIL 1 + DONE 1` + 一个仲裁器）、`rx_classify` 写侧的组合判据、`mac_rx_10g` 的 1 字/拍与 lane4 +1 拍对齐、`udp_split` 永不反压、`tcp_rx` 的 `7 + ⌈plen/8⌉`、`u_txcdc` 深度与反压、`tcp_tx_frame` 的 RTO 扫描 tick。
- 线速判据算式（§1）与"载荷天花板"数字。

**B. 仿真实测的**（本件自建 harness，xsim，156.25 MHz；原始读数 = `_proj_10g/notes/p7b_rate_dp/RESULTS.txt`）
- `mac_tx_10g`：L=60 → **11 拍/帧**（95.4%）· L=1514 → **193 拍/帧**（99.6%）（`stat_tx_words` 与拍数逐拍相等）。
- `rx_classify` v2：**IN=OUT=1.000 字/拍、STALL=0、OVF=0、RQ_OVF=0**（4 个组合：FW 8/19 × fast/slow）。
- UDP 单流全链：每帧 **18 / 17 / 28 / 104 / 196 / 380 / 380 拍**（plen = 24 / 18 / 64 / 368 / 736 / 1472 / 1469 B，`AVG_PERIOD_X1000` = 18006 / 17003 / 28009 / 104048 / 196243 / 380447 / 380447），窗口均值 **1666 / 1323 / 2857 / 4422 / 4696 / 4838 / 4848 Mbps**。
- TCP 单流：**16 / 20 / 30 / 106 / 198 / 380 拍**（k = 1 / 3 / 8 / 46 / 92 / 183，`AVG_PERIOD_X1000` = 16004 / 20007 / 30011 / 106169 / 198092 / 380386），窗口均值 312 / 1250 / 2500 / 4292 / 4621 / 4799 Mbps。
- **UDP+TCP 双流并发：311 帧 / 60000 拍（155 UDP + 156 TCP），聚合 9507 Mbps；100000 拍窗口逐位复现。**
- 全链所有配置 `MAC_ABORT=0 / FLUSH=0 / DENY=0 / DROP_LEN=0 / EEND=0`（无中止、无丢字，速率不是靠丢帧换来的）。

**C. 板级实测（引用，非本件产出）**
- app 图案流峰值 **1.248 Gbps**（1 B/拍 @156.25 MHz）= **发生器当前天花板**。
- P6b 1G 验收 956 Mbps（数据面 156.25 MHz 域）——1G 下 DP 有 ~5× 余量，**本件的 50% 惩罚在 1G 上被完全掩盖**（这也是"1G 全过"与"10G 只有 12.5%"能同时成立的原因）。
- 闸 1 的 9,999.94 Mbps 只证明官方 PCS/链路，**与数据面无关**。
