### 1.2 今天的正确性是怎么来的（这是判"乒乓会不会破"的唯一标准）

单 FSM 的三条串行事实：
1. 一帧从 `S_IDLE`(start_data) 到 `S_DONE` 全程**离开 S_IDLE** ⇒ 期间 `s_axis_tready=0` ⇒ 下一帧的帧首拍不可能落在本帧发送期内；
2. `upd_wr` 在 `S_DONE` 的末字消费拍，`state <= S_IDLE` **同拍** ⇒ 帧 N 结束后**第一拍**的 `start_data` 读到的 `rb_snd_nxt` 已是 `seq_N + plen_N`（`tcb.v` 组合读，代码注释 `:111-112` 原文"下一帧最早下拍启动, 读到的是更新后的值"）；
3. 同理 `svc`/`ring_eval`/`scan_now` **全部要求 `state == S_IDLE`**（`:297-301/:332-333/:906`）⇒ 帧在飞期间不可能发生回卷/重放/扫描 ⇒ **TCB 的单写口（本模块内唯一写源）天然被 FSM 串行化**。

⇒ **"ring 写游标 = 帧基址"这条不变式是这三条串行事实的推论，不是独立保证的。**

### 1.3 乒乓下的具体损坏场景（时刻 / 地址 / 谁覆盖谁）

前提（乒乓按 UDP 版骨架实现，`udp_tx_frame.v:201` 的接受门 = `(rx_state==RX_IDLE) && !fifo_full && !bank_rdy[rx_bank]` ⇒ RX 引擎最多领先 TX 引擎 1 帧）：

```
t0        : 帧 N 的 RX 引擎收完 184 beat，bank A 归还态置 1；TX 引擎开始发帧 N（需 191 拍）
t0        : 同时 rx_bank 指向 bank B ⇒ RX 引擎立刻开始收帧 N+1（184 beat，189 拍）
t0+0..183 : 帧 N+1 的 183 个载荷 beat 逐拍写 ring：
              w_tap_seq(帧首拍) = rb_snd_nxt  ← 此刻 TCB 未更新，值仍是 seq_N
            后续拍 = tap_seq（由 :987 从同一个 stale 值初始化）
            ⇒ 写地址区间 = [seq_N, seq_N + plen_{N+1})   ← **与帧 N 刚写的区间重合**
t0+190    : 帧 N 的 S_DONE 才把 snd_nxt 写成 seq_N + plen_N（:453-458/:1125-1143）
```

**损坏**：`retx_ram` 里 `[seq_N, seq_N+plen_N)` 区间的字节 = **帧 N+1 的载荷**（帧 N 的字节被整段覆盖）。若此后发生回卷（RTO 或 3×dup-ACK）重放该区间：
- 重放帧的载荷 = 帧 N+1 的字节，而它的 **TCP 校验和是在 ring 读回之后重算的**（`:619-643` 的 `u_csum` 入口 `csum_din = ring_wr ? ring_w : s_axis_tdata`）⇒ **线上 FCS/TCP checksum 全"干净"**；
- 对端拿到"合法但错误"的字节 ⇒ 只有 **app 层图案校验器**（对端 `peer.exe --expect-pattern`）能看见；RTL 侧**零计数**（`stat_retx` 只数会话数）。
- 反向同时受害：帧 N+1 的"正确地址区间"`[seq_{N+1}, …)` **从未被写** ⇒ 它自己重放时读回的是**更早的陈旧字节**。

### 1.4 ⛔ 范围订正：设计件把这条写窄了（这是我要加的最重一条）

设计件 (b) 只说"**ring 写游标**会从帧 N 的基址重写 ⇒ 重传数据整体错位"，并提出"把 ring 写游标本地化（每 bank 维护 `next_seq`）"。
**但 `rb_snd_nxt` 在帧首拍有 4 个消费者**，只修第 1 个会换出另一类错：

| 消费者 | 不修的症状 | 危害等级 |
|---|---|---|
| ① ring 写游标 `w_tap_seq`（`:551`） | 重传数据错位（设计件写的这条） | 静默数据损坏 |
| ② **帧头 seq** `seq_r <= rb_snd_nxt`（`:964`） | 帧 N+1 被盖上帧 N 的 seq ⇒ 线上**同 seq 两段**（重复段）。对端把它当重传丢弃 ⇒ **帧 N+1 的载荷永远到不了** | 协议级：连接停流/卡死 |
| ③ **TCB 推进值** `upd_val = seq_r + plen_r`（`:458`，来自②的 stale `seq_r`） | `snd_nxt` 停在 `seq_N + plen_{N+1}`，不再推进；`snd_una` 继续被对端 ACK 推进 ⇒ `win_diff = snd_nxt − snd_una` 下溢成大数 ⇒ `win_open=0`（`tcb.v:142-148`）⇒ **数据面永久冻结** | 死锁 |
| ④ **ring 重放帧的 `seq_r`**（`:842`，`ring_start` 拍） | 重放帧的 seq 取 stale 值 ⇒ 重放区间整体错位 | 静默数据损坏 |

⇒ **修法必须覆盖 ①–④（或者说：把"帧基址账本"整体本地化，而不是只本地化 ring 游标）**，并在**再锚定点**从 `rb_snd_nxt` 重新同步。设计件给的再锚定点（"rewind 会话结束 / 引擎全空"）方向对，但**没有覆盖 ④ 的重放路径**（重放帧的 seq 从哪来，在"本地账本 + 回卷"下需要单独定义）。

### 1.5 另一条设计件没写的：(h) 之外，**乒乓还拆掉了"TCB 单写口被单 FSM 串行"这条隐式不变式**

今天 `upd_wr` 是全模块**唯一**的 TCB 写源，且被单 FSM 串行化（一帧在飞 = 无 svc/ring/scan）。乒乓后：
- **活帧 TX 在飞**（TX 引擎忙）与 **回卷会话 / ring 重放**（原 `S_IDLE` 才允许）**可以并发**：重放帧进 bank B、活帧在 bank A 发；
- 于是同一拍窗口内会出现**两个 S_DONE 类 TCB 写**（活帧的 `seq_r+plen_r` 与重放帧的 `seq_r+plen_r`）⇒ `snd_nxt` 的写序/写值语义必须重新论证；
- 设计件 (h) 只说"乒乓后重放期间不能同时收活数据（**与今天同**）"—— **不完全**：今天排他的还有反方向（**回卷期间不可能有活帧在发**），乒乓后这条没了，必须显式互斥或重证。

⇒ 这条与 §1.4 合起来构成我在本件里的**两条结构性新增**。

## 3. ⛔ 阻断项裁定（明说）

**问：② 没有定稿修法，是实施前的阻断项吗？**

**答：是 —— 对"构建 2（TX）"是硬阻断；对"构建 1（RX R1）"完全不是。** 三条理由：

1. **判据层**：设计件自己在 §7-5 登记"**没有把两种候选写法定稿、也没证明与 `svc_rewind`/`ring_eval` 的互斥**"。按本工程纪律（"不许把估计当事实"），**没有定稿修法 = 没有可实施的 ②**；而 ② 的收益（9.456 Gbps）恰恰是它的全部卖点。
2. **危害层**：不是"性能不达标"，而是§1.3/§1.4 的**静默损坏 + 停流/死锁**三类后果，且**本工程历史上最贵的一类缺陷就是"静默"**（"三台仪器一致却都错"的 8B/帧）。这类缺陷的门必须**先有设计面的不变式**才写得出来（否则门只能靠"跑够久"）。
3. **顺序层**：R1（RX）**不碰** seq / ring / TCB / 帧边界（现役 `app_pattern.v:272-280/:524-544` 只有 `rw_*`/`rx_lfsr`/`rxs`/两个计数器，`:558-559` 注释原文"帧尾/连接号未消费"）⇒ **"先做 RX"这条顺序建议正好绕开阻断项 —— 我判它是对的**（见 §7.3 of 被审件 §6）。

**但**：构建 1 开工前，有一条**判据级前置**必须先做（不是施工阻断，是"10G 这个结论"的阻断）：`tcp_rx` 的 190 拍**实测**（`P7B_RATE_DATAPATH.md:101` 自标"读-RTL（**未实测**；边际风险项）"）。理由见 §4。

## 4. `tcp_rx` 190 拍/段 —— 独立复算 + 余量口径订正

### 4.1 我从 RTL 数一遍（结论：190 成立）

| 相位 | 拍数 | 依据（逐行） |
|---|---|---|
| `S_HDR` | **7** | `wcnt` 0→6 各接受 1 字（`:547-696`；`wcnt==6` 拍判 `acc_l` 后转 S_PAY/`:671-678`） |
| `S_PAY` | **183** | 字 7..189 = 183 字；接受门 `(!emit_v \|\| m_axis_tready)`（`:701`）在 `m_axis_tready≡1` 下**每拍成立**（emit_v 当拍置、下拍清：`:466`）⇒ 1 字/拍 |

### 4.2 ⚠️ 余量口径要订正：不是 +2.8%，是 **+1.2%~+1.6%**

| 级 | 每 1460 B 段拍数 | 折算 B/拍 | 相对线上预算 |
|---|---|---|---|
| 线上（理论 1538/8） | **192.25** | **7.5948** | —— |
| 线上（**实测帧周期 193**） | **193** | 7.5648 | —— |
| `tcp_rx` | **190** | **7.6842** | 190/192.25 = **98.83%**（190/193 = 98.45%） |
| app 校验器 R1 | **187** | 7.8075 | 97.27% |

⇒ **chain 的限速级 = `tcp_rx`**（不是 app）：`tcp_rx` 的 7.6842 vs 线上 7.5948 ⇒ **余量 +1.18%**（对 193 拍口径 +1.58%）。
⇒ 设计件 §2.2 的"+2.8%"是 **app vs 天花板**的余量（7.8075/7.5948 = 1.028），**不是链的余量**。两数都 >1，结论（"8 路够"）不变，但**判据该写 +1.2%**：因为**只有 `tcp_rx` 那 3 拍余量是真的**（2.25 或 3 拍），app 那 5.8 拍余量在链里根本用不到。

## 5. 口径逐项（`9.493 Gbps` / `1538`）

**线上开销（逐项）**：

```
1460 (TCP 载荷)  + 20 (TCP 头) + 20 (IP 头) + 14 (以太头)      = 1514 B 内容
              + 4 (FCS)                                      = 1518 B 线长
              + 8 (前导 7 + SFD 1) + 12 (IFG)                = 1538 B 线位宽
1460 / 1538 = 0.949284  ×  10.000 Gbps（= 64 bit × 156.25 MHz）  = 9.4928 Gbps  ✅ 算式逐项成立
```

⚠️ **两条口径修正**（不影响 9.493 作为"上限"的用法，但影响"可达"):
1. `8 (前导) + 12 (IFG)` 在 XGMII 上是 **IDLE 控制字**，不是数据字节；这里按"占 8 B/拍的槽位"计 —— **这个用法只有实测能背书**（见下）。
2. **测量把 192.25 钉成了 193**：`P7B_BIZ_S2.md` 的 `ΔW43/ΔW20 = 192.999989`、`809,577.9 fps = 156.25e6/193` ⇒ **每帧实测 193 拍**（不是 192.25）⇒ 线上**可达**载荷天花板 = `1460/193 × 156.25 MHz = 9.456 Gbps`（= 设计件 §3.2 的目标值，自洽 ✅）。
   ⇒ **判据里"天花板"要写 9.456（可达）/9.493（理论）两个数**，否则会把 0.4% 的记账差当成设计亏空。
3. 1518 B 这个线长**对本设计是常数、对 RATE 轮是巧合**：UDP(1472 载荷) 与 TCP(1460 载荷) **线长逐字节相同** ⇒ 193 拍的锚可以跨用（`P7B_RATE_DATAPATH.md` + `P7B_BIZ_S2.md` 两份独立读数）✅。

## 9. 被漏掉的竞争方案？（去算了，结论：没有便宜路）

**RX：**
- M1（补一级前瞻气泡）= `1.0 B/拍 = 1.25 Gbps`（设计件 §1.3 的 8 拍/字）⇒ 差 8×；
- 4 路（`rxs==1` 里一次比 4 lane）= `1460/(2×182+5) ≈ 1460/369 = 3.96 B/拍 = 4.94 Gbps` ⇒ **只有一半，不够**；
- ⇒ **必须 8 路**（1 拍/满字）才够；没有中间档能到 10G。**设计件结论正确。**
- 反方向"不走校验器"（把校验挪到快路径/旁路）**不是选项**（那是 app 的功能本体）。

**TX：**
- 只 A1（2 拍/字）= 3.25 Gbps；只 A2 = 4.80（撞帧器）；只乒乓 = 0.998 ⇒ 都不够（设计件 §3.3 表复算无误）；
- **有没有"不乒乓但重叠"的路？** TCP 校验和覆盖"伪头+头+全载荷"，**校验和字段在头里（先发）** ⇒ 帧必须"整帧入缓冲 → 校验和落定 → 才能出头字" ⇒ **store-and-forward 是协议结构性的**（`tcp_tx_frame.v:5-7` 头注释原文即此）。要重叠只能双 bank ⇒ **乒乓是唯一路**。这条比设计件写的"收/发串行"更硬，可作为"必须同批"的第二条论证。
- ⇒ **设计件"两处必须同批"的结论成立**（且理由更强）。

5. **(b) 定稿修法的正确性**：我给了**范围**（4 个消费者 + 再锚定点）与**危害链**，但**没有**写出定稿 RTL（这正是我判它阻断的原因）。
6. **RTT**：只有既有 `ss` 读数（缺陷态）+ 我核的算术 ⇒ "不成帽"是**条件结论**。
7. **未起仿真、未烧板**（纪律）⇒ 本件全部是静态分析；与并发验收 agent（只读复算）**无文件重叠**（本 agent 只写本文件）。

## 13. 一句话给用户

**RX（R1）可以按设计件开工，但"RX 到 10G"这句话在 `tcp_rx` 190 拍被实测之前只是模型值（余量 1.2%，不是 2.8%）；
TX（构建 2）在 §1.4 的 seq 账本定稿之前**不能开工** —— 设计件点名的 (b) 是真的，但它写窄了：stale 的 `rb_snd_nxt` 有 4 个消费者，只本地化 ring 游标会从"静默数据损坏"换成"同 seq 重复段 + 数据面冻结"；且乒乓还额外拆掉了"TCB 单写口被单 FSM 串行"这条**没人写下来的**不变式。
顺序建议（先 RX 后 TX）**正确且正好绕开阻断项**；`9.456 Gbps` 这个目标数**站得住**（TX 引擎应为 191 拍、帧周期仍 193），但它只在 ② 定稿后才存在。**
