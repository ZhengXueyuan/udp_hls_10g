## 1. Q1：RX 那个"9 拍"是 bug 还是结构代价？

### 1.1 逐行比（TCP 版 vs UDP 版）—— 这是本节的全部证据

| 环节 | `rtl/app_pattern.v`（TCP 版） | `rtl/app_udp_pattern.v`（UDP 版，同一图案语义） |
|---|---|---|
| 接收合同 | `:280` `assign rx_tready = (rxs == 2'd0);` —— **只在"取值态"收字** | `:613` `assign rx_tready = !nx_v;`（默认）/ `:658` `assign rx_tready = !nx_v \|\| cmp_ld_w;`（`P7B_10G`） |
| 中间级 | **无**。`rw_data/rw_keep/rw_n` 是**唯一**级（`:524-536` 取值态锁存） | **有前瞻寄存器 `nx_d/nx_k/nx_n/nx_v`**（`:577` 声明，`:887-892` 装载） |
| 取值与比较的关系 | **结构性互斥**：`rxs==0` 取值 ⇒ 本拍**一个字节都不比**；`rxs==1` 比较 ⇒ `rx_tready=0` **不收字**（`:537-544`） | **重叠**：比较引擎在 `cmp_i==7` 那拍把 `nx` 搬进 `cmp_*`（`:908-924` 的 `cmp_end` 分支），**装载与之并行**（`nx_v` 同拍被清 ⇒ 下一拍 `rx_tready` 立刻为 1） |
| 每字拍数（满字 8 B） | **1 + 8 = 9 拍** ⇒ `0.8889 B/拍 = 1,111.1 Mbps` | **8 拍** ⇒ `1.0 B/拍 = 1,250 Mbps` |
| 实测/引证 | xsim 直测 `dcyc/bytes = 9002/8000 ⇒ 9.002 拍/字`（Gap#9 §1.3）；板级稳态 **1,110.8 Mbps = 结构值 99.97%**（`P7B_WU_PACE_AUDIT_VERIFY.md` §2.4） | 头注释自述「**1 字节/拍 II=1 无缝**（1 字前瞻寄存器）」（`:573`） |

⇒ **两个实现的差异恰好是一级前瞻寄存器**：UDP 版把"取值"藏在"上一字的最后一个字节比较拍"里，TCP 版没有这一级。

### 1.2 判决 + 判据（**两条都要给**）

**判据 A（怎么证明它"是"可消除气泡 —— 工科判据：存在同语义对照件）**
1. **接口不构成约束**：TCP 版的上游是 `tcp_echo` 的零拷贝 `frame_fifo`（FWFT），其头注释原文
   「**FWFT 上游天然保持，AXIS 合同成立**」（`app_pattern.v:19-20`）。UDP 版的 `rx_tready` 合同**逐字相同地**建立在同一类 FWFT 上游上，
   却做到 1 B/拍 ⇒ **"比较期必须停收"不是 AXIS/FWFT 要求的**，是这一实现的选择。
2. **取值拍的工作量在本拍已全部就位**：第 0 字节所需的两个量（`rx_tdata` 与本拍 `rx_exp = rx_lfsr[31:24]`）都是本拍可用量，
   不依赖"本拍锁存的结果" ⇒ 组合上**可合并进取值拍**（把 `rw_i` 从 0 起改成从 1 起、LFSR 在取值拍先推 1 步）。
3. **代价可忽略**：补齐一级前瞻只要 77 FF（`nx_d64 + nx_k8 + nx_n4 + nx_v1`，Gap#9 §3.4），占现役 FF 的 `77/69,744 = 0.11%`。

**判据 B（怎么证明它"不是"可消除气泡 —— 若要把"结构代价"这条支路撑住，必须同时满足）**
- ① 上游不能承受连续收字；② 寄存器资源不够；③ AXIS 合同要求"接受拍与消费拍严格一一对应"。
- **三条逐条否**：① 上游是 FWFT 零拷贝缓冲，UDP 版正是靠在比较期连续收字跑满的；② 77 FF = 0.11%；③ AXIS 只要求
  `tvalid && !tready ⇒ 数据保持`，**不要求**每个 tready 拍都必须"立即产生可观测效果"。
  ⇒ **"必要结构代价"这条支路不成立。**

**结论（我的裁定，措辞分层）**：
- **不是正确性 bug** —— 数据、计数、失配判定全对（板级 1,110.8 Mbps 稳态、`ΔW13 ≡ 0` 有板级背书），且文件头注释
  显式写着设计意图「1 拍吞 1 字, 之后按字节比对（每拍 1 字节…）」（`:19-20`）⇒ **是"设计选择"**。
- **但这个选择确实丢掉了 11.1% 的吞吐（1 拍/字）**，且**同仓已有反例证明可以做到 1 B/拍** ⇒ 对"以 10G 为目标"这件事，
  它是一个**可消除的吞吐缺陷**。按用户裁定的字面（"如果是 bug 就修复"）⇒ **归属"缺陷"一侧，但修法不是去补那 1 拍**（见下）。

### 1.3 最小修法（两条，都有预计落点）

| 修法 | 做法（最小改动） | 预计拍/字 | 折合 | 评价 |
|---|---|---|---|---|
| **M1：取值拍顺带比第 0 字节** | 在 `:524-536` 的 `rxs==0` 分支里，`rx_tvalid` 当拍加一次 `byte_at(rx_tdata,0) != rx_exp` 比对 + `rx_lfsr <= xs_next` + `rw_i <= 1`；`:537-544` 的比较循环照旧（从 `rw_i=1` 起，末字节判据 `rw_i+1 >= rw_n` 不变）。需要注意 `pop8(tkeep)==0` 的空尾字分支**不要**比（`:530-532` 原有语义） | **8 拍/满字** | `1.0 B/拍 = 1,250 Mbps`（+12.5%） | 改动 ~6 行，**但单独做只到 1.25 Gbps（离 10G 差 8×）⇒ 不值一次构建** |
| **M2（推荐）：R1 = 8 路并行（Gap#9 §3.3）** | `rxs==0` 且 `pop8(rx_tkeep)==8` 时**一拍比完 8 lane**（`rx_exp_word = xs_word8(rx_lfsr)` + 8 个 lane 比较 + `pop8` + `stat_mismatch += rx_bad_n`），`rxs` 保持 0 ⇒ 背靠背 1 拍/满字；`pop8(tkeep)≠8` 的**尾字/0 长字自动回落**原 `1+N` 串行路径 | 满字 **1 拍**；1460 B 段 = `182 + (1+4) = 187 拍` | **7.81 B/拍 = 9.76 Gbps** | ⭐ **这是唯一有意义的修法**：气泡被吸收（1 拍/满字），且它是 `J6-ladder` 的判据解锁件（现上界 1.111 Gbps） |

> ⚠️ **M1 与 M2 的关系**：M2 下 M1 自动多余（满字 1 拍，根本没有"取值拍"这个概念了；尾字仍走串行 = `1+4` 拍）。
> ⇒ **不要为气泡单独排一次构建**。这一条就是 Q1 的最终答案。

## 2. Q2：RX 到 10G 需要什么（核对 Gap#9 算式 + 口径）

### 2.1 算式核对（我逐项重算，**结论：无误**）

```
结构上限        = 8 B/拍 × 156.25 MHz = 1,250 MB/s = 10.000 Gbps          （= XGMII 带宽，fabric 侧天花板）
一个 1460 B 段  = 183 个字 = 182 满字(1456 B) + 1 尾字(4 B)
R1 下            = 182×1（满字 1 拍/字） + (1 取值 + 4 比对)（尾字回落串行）
                = 187 拍 / 1460 B
平均            = 1460/187 = 7.8075 B/拍 × 156.25 MHz = 1,219.9 MB/s = 9,759 Mbps
```
⇒ **核对通过**：Gap#9 的 `182 + (1+4) = 187 拍 ⇒ 7.81 B/拍 = 1.22 GB/s = 9.76 Gbps` 逐项成立
（唯一措辞订正：187 拍里那 5 拍是**尾字**的，不是"额外开销"）。

### 2.2 9.76 够不够叫"10G"？—— **必须先把口径钉死，两个口径答案相反**

| 口径 | 数 | R1（9.76 Gbps）够不够 |
|---|---|---|
| **线上（10GBASE-R 载荷窗口）** | `10.3125 GBd × 64/66 = 10.000 Gbps`（XGMII: `64 bit × 156.25 MHz`） | 线上 10.000 就是 8 B/拍，**R1 的 8 路正好打满** ✅ |
| **TCP 线上的**载荷**（板→对端 TCP 段内容）** | 内容 `14+20+20+1460 = 1514 B`；线上 `8(前导/SFD) + 1514 + 4(FCS) + 12(IFG) = 1538 B` ⇒ `1460/1538 = 94.93% × 10.000 = **9.493 Gbps**`（= `7.594 B/拍`） | **9.76 > 9.493 ⇒ 够**（余量 `7.8075/7.594 = 1.0281 ⇒ **+2.8%**`）✅ |
| **"app 载荷 = 10.0 Gbps"** | 需要 8 B/拍**每一拍**（含尾字拍也要 8 字节） | **物理不可达**：TCP 帧头开销结构性地吃掉 5.07%，10G 线上送不出 10G 的 TCP 载荷 ❌ |

⇒ **答案**：**8 路就够**，条件是口径写成「**线上 10G / 载荷 ≤9.49 Gbps（最大段）**」。
**不要**把达标写成"app 载荷 10.0 Gbps" —— 那是算术上不可能的判据（等于用错尺子）。

**这条"够"对任意段长都成立（不只是最大段）** —— 一般式（逐项可复算）：

```
校验器拍数(R1, 段长 L) = ⌊L/8⌋ + (rem≠0 ? 1+rem : 0)      ≤ L/8 + 2
线上拍数(同段)         = (L + 78)/8 = L/8 + 9.75           （78 = 8 前导/SFD + 54 头(14+20+20) + 4 FCS + 12 IFG）
⇒ 校验器 ≤ L/8+2 < L/8+9.75 = 线上        ⇒ 任意 L（含 L=1..8 的极端短段）都恒成立
```
⇒ **R1 后 app 校验器永不是 10GBASE-R 的限速级**（真正要单独盯的是 `tcp_rx` 的 190 拍，见 §2.3）。

**若有人坚持 app 侧要 8 B/拍 无尾巴**：那需要尾字也一拍比完，即**变步长 LFSR 推进** `M^k (k=1..7)`
（7 套常量 XOR 网 + mux，≈ 7×891 = 6.2 k 项 XOR ⇒ **约 +1.5–3 k LUT**，与本设计全部其余增量同量级）。
⇒ **明确不推荐**：多花一倍面积只为换 `+2.8%`，而这 2.8% 在线上根本不存在。

### 2.3 ⚠️ 同批必须知道：RX 链上**还有一级更紧**（不然"RX 到 10G"会张冠李戴）

| RX 级 | 每 1460 B 段拍数 | 占线预算 `1538/8 = 192.25 拍` | 证据等级 |
|---|---|---|---|
| `mac_rx_10g` | 不反压线上（**结构 1 字/拍**） | — | 读 RTL |
| `rx_classify` v2 | 0 固定开销 | 1.000 字/拍实测（`P7B_RATE_DATAPATH.md` §2/Q4） | **仿真实测** |
| **`tcp_rx`（fast）** | **190**（`S_HDR 7 + 载荷 1 字/拍`） | ⭐ **98.8%（全链最紧）** | **读 RTL 推的，未实测**（`P7B_RATE_DATAPATH.md` §3/§5-item-4） |
| **app 校验器（R1 后）** | **187** | 97.3% | 本件推算（同 §2.1 算式） |

⇒ **R1 之后，app 校验器不再是 RX 方向的瓶颈；`tcp_rx` 的 190 拍（98.8%）才是。**
⇒ 设计判据必须写成"**RX 单路 10G = 全链 ≤192.25 拍/段**"，并要求**先把 `tcp_rx` 的 190 拍实测出来**
（`P7B_RATE_DATAPATH` 自己标的是"读 RTL 推的、边际风险项"）。**若那 2 拍余量不实，RX 方向卡在 `tcp_rx`，不卡在 app。**

## 3. Q3：TX 到 10G（本次主体）

### 3.1 现状定量（逐行 + 算式）

**① `app_pattern` TX = 0.8 B/拍**（`P7B_GAP9…` §1.1 + xsim 直测 `1828.000 拍/帧`）：

```
满字 = 8(填 bcnt) + 1(asm_full 装载 pw_*) + 1(pw_valid 消费)  = 10 拍 / 8 B
一帧 = 1(opener) + 182×10 + 6(4 B 尾字: 4 填 + 1 装载 + 1 消费) + 1(收帧) = 1828 拍 / 1460 B
     = 0.7987 B/拍 = 998.4 Mbps（app 单独天花板）
```
逐行落点：`:267-270` 每拍只产 1 字节；`:263-264` `asm_go` 含 **`!pw_valid`** ⇒ 呈交寄存器期间装配停摆；
`:500-508` 装载 1 拍；`:511-521` 消费 1 拍。

**② `tcp_tx_frame` = 整帧存转发、无乒乓 ⇒ 380 拍/帧 = 4.803 Gbps**（实测；`P7B_RATE_DATAPATH.md` TCP 表）：
`S_RECV 183 + S_WAIT 5 + S_HDR 6 + S_PAY 183 + S_TAIL 0 + S_DONE 1 + tx_arb 1 = 380`。
结构性证据 = `:473-477` `s_axis_tready` **只在 S_IDLE/S_RECV 有效** ⇒ 收（183 拍）与发（196 拍）**串行**。

**③ 端到端（现状）**：`P(c) ≈ 197 + 182·c`，`c=10 ⇒ 2017 拍`（板级实测 2003）⇒ **911 Mbps（板侧）/ 903.7 Mbps（socket）**。

### 3.2 改后算式（两处都改）

**改 ① `app_pattern` TX → A2（1 拍/字）**（Gap#9 §3.2）：把 `asm_go` 的门 `!pw_valid` 放宽为 `(!pw_valid || m_tready)`，
并把本字的 `need/left/pw_last` 用**前瞻量** `seg_sent + pw_n` 算。

```
app 单独：1(opener) + 182×1 + 6(尾字不变) + 1 = 190 拍/帧 ⇒ 1460/190 = 7.684 B/拍 = 9.605 Gbps
```

**改 ② `tcp_tx_frame` 乒乓（照 `UDP_TX_OVL` 的做法）**：RX 引擎（收帧 + 长度守卫 + 校验和收尾）与
TX 引擎（头/载荷/尾）拆开，载荷 FIFO 拆两个 256×73 bank 乒乓。

```
RX 引擎 = 184 拍(184 个 beat: 1 opener + 183 载荷字) + 5 拍(csum 收尾 S_WAIT) = 189 拍
TX 引擎 = 6(T_HDR) + 183(T_PAY) + 1(T_DONE) = 190 拍
MAC     = 193 拍（实测，1514 B 内容帧；`P7B_RATE_DATAPATH.md` §2）
帧周期  = max(189, 190, 193) = 193 拍
```

**⇒ 端到端 = `1460/193 = 7.5648 B/拍 × 156.25 MHz = 1,182 MB/s = 9,456 Mbps = 9.456 Gbps`**
（= TCP 线上载荷天花板 9.493 Gbps 的 **99.6%**；未改动的 `mac_tx_10g` 是**新的限速级**，与 UDP 轮结论一致）。

### 3.3 哪一处是瓶颈（三问三答，都要算式）

| 配置 | 帧周期 | 速率 | 瓶颈级 |
|---|---|---|---|
| 现状 | 2003–2017 拍 | **911 Mbps**（板侧） | app（1828/2017 = 90.6%） |
| **只改 ①**（A2，帧器不动） | `P = 197 + 182×1 = 379 拍` | **4.803 Gbps**（`1460/379`） | **帧器**（收/发串行） |
| **只改 ②**（乒乓，app 不动） | `max(1828 app, 190 TX, 193 MAC) = 1828 拍` | **998 Mbps**（`1460/1828`） | **app**（只比现状 +9.5%） |
| A1（2 拍/字）+ ② | `max(372, 193) = 372 拍` | **4.906 Gbps** | 仍 app |
| **① + ② （A2 + 乒乓）** | **193 拍** | ⭐ **9.456 Gbps** | **MAC** |

⇒ **两处是乘法关系，不是加法**：单独任一半都到不了 10G（①=4.80 / ②=0.998），**只有同批才有 9.456 Gbps**。
⇒ 这也回答"TX 想办法让单路达到该能力"：**该能力（10G 线上）= 9.456 Gbps 载荷**，改完正好撞到物理天花板。

### 3.4 `tcp_tx_frame` 与 `udp_tx_frame` 同构吗？乒乓能照抄吗？—— **不同构，不能照抄**

**同构的部分（可逐字照抄）**：载荷 FIFO `fifo_sync #(.W(73),.D(256),.AW(8))`（两者逐字相同）；长度守卫 `len_bad/flush_pend`；
"S_RECV 里 1 拍 1 字推 FIFO + 校验和同拍过"；头字装配/尾字优先级/欠载防御/统计口径的**代码骨架**；
`bank_rdy` 归还语义；`s_axis_tready && !bank_rdy[rx_bank]` 这条结构性约束。

**不能照抄的地方（逐条，附出处）**：

| # | 差异 | 出处 | 为什么乒乓改法要跟着变 |
|---|---|---|---|
| **a** | **帧源不是一个，是三个**：`ackq`（ACK/SYN/FIN/RST 控制帧，32 深，`:257-275/:710-715`）、`retx_ram` 重放帧（`S_RING`，`:1114-1124`）、活数据帧 | `tcp_tx_frame.v:277-301` 的仲裁链 `ack > retx svc > ring > RTO scan > 活数据` | UDP 版**只有活数据一个源**，所以它的 TX 引擎"等 `bank_rdy` 就发"是完备的。TCP 的控制帧**无载荷、不占 bank**（`plen_r=0`）却要一整份帧头上下文（见 c）⇒ TX 引擎需要**第三个上下文槽**（或把控制帧串行化 —— 会破坏现有"ACK 优先、对端时延敏感"的语义，`P7B_RATE_FRAMER` 同款取舍不适用） |
| **b** | **seq 账本被单 FSM 串行保护**：`w_tap_seq = start_data ? rb_snd_nxt : tap_seq`（`:551`，ring 写游标取**帧首拍的 TCB snd_nxt**）而 TCB 的 `snd_nxt` 写在**帧末**（`:453-458` `upd_wr` 在 `S_DONE` 末字消费拍） | `:453-458` / `:551` | ⭐ **这是最硬的一条**。乒乓后帧 N+1 的帧首**落在帧 N 的发送期内** ⇒ 那一拍 `rb_snd_nxt` **还是帧 N 的起点**（TCB 未更新）⇒ ring 写游标会**从帧 N 的基址重写** ⇒ 重传数据整体错位（重传=对端拿到别人的字节）。**修法必须落地**：把 ring 写游标**本地化**（每 bank 维护 `next_seq`），并在 **rewind 会话结束 / 引擎全空**这两个同步点从 `rb_snd_nxt` 重新锚定 |
| **c** | **每 bank 帧上下文大 3.35×**：TCP = `cur_id4 + is_*4 + seq32 + ack32 + wnd16 + doff16 + dmac48 + dip32 + sport16 + dport16 + id_cap16 + plen_r12 + tcp_len16 + total_len16 + ip_csum16 + tcp_csum16 = **308 bit**`；UDP = `plen12+udp_len16+total_len16+ip_csum16+udp_csum16+id_cap16 = **92 bit**` | 逐行数（`tcp_tx_frame.v:204-234` vs `udp_tx_frame.v:137-150`） | UDP 轮第二份上下文只 +92 FF；TCP 第二份 **+308 FF**（+ 控制帧槽）。**FF 代价不是同量级** |
| **d** | **校验和收尾 5 拍**（`S_WAIT`：`wait_cnt 0` 算 ip_csum + 3 拍 `aen` 补 9 个半字 + `fin` + 锁存，`:1024-1033`），UDP 是 3 拍 | `tcp_tx_frame.v:624-632` | 搬到 RX 引擎后 `RX_FIN = 5` ⇒ RX 引擎 189 拍（UDP 是 187）。仍 < 190 ⇒ 不改变结论，但**拍数账必须按 5 算** |
| **e** | **窗口门控的陈旧度会变大**：`win_open` 由 tcb 注册输出（`:346`），其输入是 TCB 的 `snd_nxt`；乒乓后帧 N+1 的帧首读到的在飞量**少算一帧** | `tcb.v:142-148` + `tcp_tx_frame.v:184` 的 RING_CAP 注 | 好消息：**既有 margin 已按此设计**（「可误开 1 拍…每次最多多放 1 帧；最坏在飞 = (0xBFFE-1)+4095 = 53244 < 65536」）⇒ 乒乓把这个"偶发"变成"结构性"⇒ **必须重述这条论证**，不能当没发生 |
| **f** | **`upd_wr/upd_val` 要按 bank 取值**（`seq_r + plen_r` → `seq_r[tx_bank] + plen_r[tx_bank]`） | `:453-458` | 机械改，但它是 TCB 唯一写口 ⇒ 错一处就是 seq 漂移 |
| **g** | **`o_busy` 不存在**（UDP 版有，给 `udp_tx_cfg` 冻结 cfg 用） | `udp_tx_frame.v:414`，`tcp_tx_frame.v` 端口表**无此口** | 这条是"**少了**"而不是"要改"：TCP 的 `cfg_src_mac/cfg_src_ip` 是常量，peer 信息走 CAM 且**帧首一次性锁存**（`:973-976`）⇒ **UDP 轮那个"改 peer 多冻 15 拍"的代价在 TCP 侧不存在** |
| **h** | **`S_RING` 重放会占住 RX 引擎**：`ring_wr` 是"RX 侧写源"的第二个来源（`fdin = ring_wr ? fdin_ring : {s_axis_tlast,s_axis_tkeep,s_axis_tdata}`） | `:588-590` | 乒乓后重放期间**不能同时收活数据**（与今天同）⇒ 重放帧也要向 RX 引擎申请 bank（`!bank_rdy[rx_bank]`），且 `ring_d_r` 2 级读流水（`:246`/`:562-575`）必须原样保留 |
| **i** | **`rb_id` 复用与"旁路拍"口径**：`rb_id = svc?svc_id : ring_eval?retx_id_r : scan_now?scan_id : (state==S_IDLE)?start_id : cur_id`（`:428-429`），且注释明写"本门**只准**出现在 S_IDLE 子句里（`S_RECV` 拍 `rb_id=cur_id≠start_id`）" | `:389-397`/`:420-429` | 拆引擎后这条不变式的**前提变了**（`cur_id` 变 per-bank、"S_IDLE"变成"RX 引擎空闲拍"）⇒ 必须重新逐条论证（否则会出现"用 scan_id 的 state 去门 start_id 的帧"这类错） |
| **j** | 帧头字节布局 / `ljust6` / `rm_mask` / `prio_lo` / `ip_csum_calc` 这些**纯函数与常量** | `:488-542`/`:593-606` | ✅ 可逐字照抄（同 UDP 轮"头 5 字一字未改"的做法） |

> **一句话**：UDP 的乒乓是"**纯流水切分**"（单帧源 + cfg 冻结 + 92 bit 上下文）；TCP 的乒乓是"**带账本的流水切分**"
> （三帧源 + seq 游标 + 308 bit 上下文 + 校验和 5 拍）。**可以照抄骨架，不能照抄结论** —— 尤其是 (b)，它是唯一一条
> "**照抄就静默损坏重传数据**"的项。

## 4. Q4：窗口 / BDP 硬约束（**可能被忽略、且数据面解决不了**）

### 4.1 表：10 Gbps 单路需要多少窗口

`10 Gbps = 1.25 GB/s`；板侧两个独立帽：**收**（`WIN_POOL`，对端在飞上界）**49,152 B** / **发**（`RING_CAP`，本板在飞上界）**49,150 B**。

| RTT | BDP = 1.25 GB/s × RTT | vs 49,152 B | 该 RTT 下 `W=49,152 B` 能到的单路速率 |
|---|---|---|---|
| **10 µs** | **12,500 B** | 0.25× ⇒ **够**（余 3.93×） | 4.92 GB/s = 39.3 Gbps（不成帽） |
| **50 µs** | **62,500 B** | 1.27× ⇒ **不够** | 983 MB/s = **7.86 Gbps** |
| **100 µs** | **125,000 B** | 2.54× ⇒ **不够** | 492 MB/s = **3.93 Gbps** |
| **1 ms** | **1,250,000 B** | 25.4× ⇒ **不够** | 49.2 MB/s = **393 Mbps** |

**扳点 RTT**：`49,152 B ÷ 1.25 GB/s = 39.32 µs`（发侧 `49,150/1.25e9 = 39.32 µs`，同一数）
⇒ **本板当前窗口在 `RTT > 39.3 µs` 时就不够**（这一格**与数据面无关**，是"窗口 ÷ 链路往返"的算术）。

### 4.2 实测候选（**必须带口径**）

原始 `ss` 读数（对端，连的是板子 `192.168.100.2:8080` = **同一条 10G 业务路径**；`p7b_wu_loop/fix/ss_WU_FIX_P0_R*.log`）：

```
rtt:0.016/0.01 … rto:201 … notsent:280336 minrtt:0.008      （单位 = ms；同行 rto:201 = 201 ms、ato:40 = 40 ms 自证）
minrtt 取值域 = 0.006–0.008 ⇒ 6–8 µs ；srtt = 0.016–0.027 ⇒ 16–27 µs
```
⇒ **BDP(minrtt 8 µs) = 10.0 KB**；**BDP(srtt 27 µs) = 33.8 KB** ⇒ 两者都 **< 49,152 B ⇒ 不成帽**（余量 1.45–4.9×）。
⚠️ 但 **`minrtt` 是"史上最小"、稳态要按 `srtt` 读**；且这两个数**没有在"单路 10G 满速"工况下现取过**（那些日志全是
`rwnd_limited:100%` 的 `wu` 缺陷态）⇒ **判据必须每一次都现取 `ss -ti`**（全局 #48：没核过的不许写成事实）。

### 4.3 顺带核：`WIN_POOL` 能不能改大？上限被什么约束？

| 帽 | 出处（逐字） | 值 | 上限由什么定 | 能加多少 |
|---|---|---|---|---|
| 收（对端在飞） | `rtl/app_ctrl.v:222` `parameter [15:0] WIN_POOL = 16'hC000`（+ `:242` `WIN_Q_MAX = 16'hC000` = `0x0C` 寄存器复位值） | 49,152 B | **app RX 缓冲 = `frame_fifo #(.W(73), .D(8192), .AW(13))`**（`rtl/tcp_echo.v:93`）= `8192×8 = 65,536 B`，且必须满足（`board/wrapper_p4.v:1127,1133` 逐字）`N×ACC_MARGIN + Σwinq + Δ(2816) + U(1518) + SEG_MAX(1500) ≤ 65536` | 取 `ACC_MARGIN=4096`（N≤2 档，`:1158`）⇒ `WIN_POOL ≤ 65536−4096−5834 = 55,606 B`（**+6.4 KB / +13%**）；代价：`wrapper_p4.v:1133` 的常量 **10550** 要重算（`:1158-1160` 的查表 4096/3516/3328 全跟着动） |
| 发（本板在飞） | `rtl/tcp_tx_frame.v:184` `parameter [15:0] RING_CAP = 16'hBFFE` + `rtl/tcb.v:13` `WIN_CAP = 16'hBFFE`（**两处必须同值**） | 49,150 B | **`retx_ram` 每连接 64 KB 环**（13 位 ring 字 idx）；结构性界（`:173-183` 逐字）`最坏在飞 = (RING_CAP−1) + plen_max 4095 < 65536` | `RING_CAP < 61,442` ⇒ **≤ 60 KB（+22%）**，然后把 `retx_ram` 的余量论证重做 |
| 序列号空间 | `tcb` 全 32 位（`tcb.v:142` 32 位回绕正确减法） | 4 GB | **不是约束** | — |
| 窗口缩放 | `wscale` = **对端**的 scale（`tcb.v:5-7`：`tcp_rx` drain `snd_wnd` 时按它缩放），本板自己不因此获得更大缓冲 | — | **没用**：物理缓冲只有 64 KB，scale 只改字段表示 | — |

⇒ **结论**：两个方向都**不能**把窗口提到"任意 RTT 都够"的量级（极限 ~55.6 KB 收 / ~60 KB 发 ⇒ 扳点 RTT 从 39.3 µs
挪到 **44.5 / 48.0 µs**）。要再往上就是 **每连接缓冲容量（BRAM/资源级）的决定**，不是数据面能救的。
⇒ **设计判据里必须**写：「单路 10G 的成立条件 = **RTT ≤ 39.3 µs**（现状窗口）」，并**在板级现取 `ss -ti` 的 `minrtt/srtt` 作为该判据的见证量**。

### 5.1 面积（**估计**；锚 = UDP 版同类改动的实测增量 + 本件逐行数的位宽）

### 5.2 时序：新逻辑会不会落进当前最差族？

**当前最差族（逐字，`P7B_WU_TIMING_DELTA.md` §1.1/§1.3）**：DP 域 `g_hw.clk_out0`（6.400 ns）**就是全局最差**
`WNS +0.147 = 2.30%`；拓扑 = `u_app_udp/u_txf/dout_reg[68]/C → u_udp_tx/ip_csum_r_reg[*]/D`，
**20 级逻辑 / route 55.5%**，DP 前 10 里有 **6 条同源**（0.147–0.229）⇒ **是一个簇，不是孤点**。

**逐条判**：

| 新逻辑 | 落点 | 会进最差族吗 | 理由 |
|---|---|---|---|
| R1 的 RX 比较锥 | `rx_lfsr → xs_word8 → 8×比较 → pop8 → stat_mismatch(D)`；源端是 `tcp_echo.frame_fifo` 的 BRAM/LUTRAM 输出 | **不直接** | ① 与那条族的**源/宿模块都不同**（`app_pattern` vs `app_udp_pattern`；`tcp_echo` vs `udp_tx_frame`），除共享时钟外**无共享逻辑**；② 深度 ≤8 级 vs 20 级 |
| A2 的 TX 装载锥 | `tx_lfsr → xs_word8 → pw_data(D)`（≤5–6 级） | **不直接** | 同上（不同实例、深度差 3–4×） |
| **A2 的 `asm_go` 新项 `m_tready`** | ⚠️ **跨模块新路径**：`tcp_tx_frame` 的 `s_axis_tready` ⇒ `axis_pipe.s_ready = m_ready \|\| !m_valid`（`rtl/axis_pipe.v:14`）⇒ `app_pattern.asm_go` ⇒ `pw_valid/pw_data(D)` | ⚠️ **是一条新族**（不进旧族，但值得点名） | 稳态分支浅（`state==S_RECV && !pay_full` ≈ 2–3 级）；`S_IDLE` 深分支（`wnd_open`/`tx_blk_sid`/`stk_ok`/`start_id` 16:1 mux）**只在帧首拍活**。合计估 8–12 级 ⇒ **比 20 级浅**，但**跨三模块**，布局不好就吃掉 2.3% 余量 |
| 乒乓的 73 位 2:1 mux | `tcp_tx_frame` 的 TX 载荷输出 | **不直接** | 同款构件在 UDP 轮**实测变好**（数据面域 WNS `+0.128 → +0.295`，RATE 轮）；且它挂在 `m_axis` 载荷路上，不是 `ip_csum` 锥 |
| 乒乓的第二份上下文/第二份 FIFO | `tcp_tx_frame` 区域新增 ~0.4 k FF | ⚠️ **布局压力** | `tcp_tx_frame` 自己的历史最差是**纯布线型**（基线 DP 组最差 `0.192`：`u_tcp_tx/u_retx/ra_o_r_reg → mem_o_reg_7_bram_6/ADDRBWRADDR[5]`，Logic Levels **0** / 98.3% 布线）⇒ 塞进同区域的新 FF/FIFO 会挤它的**布局/布线**，方向不可预判 |

**必须说清的三条**：
1. **结构性排除"同族"只能说"不直接"**：本流程的**重排幅度 ±0.4–1.3 ns**（会同一条物理路径在两轮之间移动 `−0.591…+1.302 ns`，
   `P7B_WU_TIMING_DELTA.md` §4.1；同输入 ⇒ 读数逐字复现 §4.4 —— ⛔ 2026-10-09 已升级为**位级**（`P7B_WU_TIMING_DELTA.md` §8：R0/R1 `cmp -l` 5 字节头差、C1/r6-fix `SW_CRC=da663843` 一致 ⇒ **同输入重跑方差 0**））⇒ **分析值不能替代构建读数**。
2. **本改动不碰快照窗**（`stat_wu`/`rx_occ_bytes` 是另一路 agent 的活）⇒ **不叠加**那两条已知薄处
   （`async_default` pcie 0.496 / DP 0.743）。
3. **hold 侧**：`WHS +0.010` 本来就薄；本改动**不新增时钟域、不新增跨域路径** ⇒ 不新增 hold 风险源。

**收口判据（必须由一次构建给，本工程口径）**：三类失败端点 **0/0/0** + **WNS > 0** + **新增的 `u_app*`/`u_tcp_tx` 锥
不在数据面域前 10**；并归档 `board/p7b_ku5p_timing.rpt` + `p7b_ku5p_util.rpt`（格式照 `P7B_WU_BUILD.md` §0 的表）。

## 6. Q6：实施顺序建议

**两批构建（不额外切批），每批由一次构建收口。**

| 批次 | 内容 | 预期收益 | 为什么这样切 |
|---|---|---|---|
| **构建 1** | **RX：R1（`app_pattern` 8 路 RX）** | TCP 上行 **1.111 → 9.76 Gbps**（结构值） | ① **最便宜**：0 新 FF / ≈80–120 LUT（+ 共用 XOR 网）；② **是判据的堵点**：`J6-ladder`（`P7B_BIZ_PLAN.md` §4.1b）上界现在就是 1.111 Gbps，不抬它 `wu` 修复的效果**永远在 >1.11 Gbps 上读不出来**；③ 纯组合、不动任何帧边界算账 ⇒ **风险面最小**，单独落地不会把后面 TX 的问题糊在一起 |
| **构建 2** | **TX：A2（`app_pattern` 1 拍/字）+ `tcp_tx_frame` 乒乓** | TCP 下行 **911 Mbps → 4.80（只①）→ 9.456 Gbps（①+②）** | ① **必须同批**：① 单独只到 4.80（撞帧器），② 单独只 +9.5%（撞 app）—— 分开做等于**两次都看不到 10G**；② 两者共用"帧周期"这一个读数（193 拍），同批才能一次证明；③ 风险都在这批（A2 改帧边界算账 + 乒乓改 seq 账本）⇒ **同批 = 风险同批收口**，且 §3.4(b) 那条必须在同一批里被专门论证 |

**不建议**：
- ❌ 把 RX 与 TX 合成一批：两个方向的风险面完全不同（RX 纯组合 / TX 动帧边界 + seq 账本），合批会把
  "哪一半引入的问题"糊在一起（本工程有"修复会曝光既有隐患"的先例，坑 20）。**但也不用为 RX 单独开第三次构建** —— R1 与 TX 改的是同一文件的两半，构建 1 顺带把共用函数块落盘，构建 2 只加 TX 分支。
- ❌ 只做 A1（2 拍/字）：它比现状好转 5×（911 Mbps → 3.25 Gbps），但**再抬就得回头改 A2**（多一次对 `seg_sent` 基准的扰动）= 多一次风险，且达不到目标。

**每批必须带的门（不可省，逐条有判别力）**：
