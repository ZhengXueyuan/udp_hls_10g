## 0. 结论（先给要点）

1. ⛔ **旧件 §0.3 / §5-边界-2 的那条"TX 收益被帧器锁死、天花板 4.803 Gbps"作废** —— `TCP_TX_OVL`
   已于同日落地（`rtl/tcp_tx_frame.v:236` 起，乒乓双 bank），帧器 **TX 引擎实测 191 拍/帧**
   （本单独立复现：`tx1460 min=191`，与仓内留存 `sim/p7b_stagec_tx/gate_ovl_r6.txt:503` 逐字一致）。
2. **【实测】现役 TCP app 的生产节奏 = `190` 拍/帧（单独、下游恒 ready）**；
   放进 wrapper 忠实链（app → `axis_pipe` → 帧器）后，**帧器 RX 引擎占用 = `193` 拍/帧**
   （= app 帧内跨度 188 + 5 拍 RX_FIN）—— **恰等于 XGMII 线上几何 193**（UDP 侧实测
   `ΔW43/ΔW20 = 192.99998`）⇒ **余量 = 0**。UDP app 同一口径 = `186` 拍/帧 ⇒ **余量 = 7**。
3. ⭐ **答案是"必要但不充分"，且"不是那 6.7 拍的数"**：【实测】app 的**节奏本身**相对线几何只值
   **0–1 拍/帧**（它是"恰好持平"，不是"超出"）；它的真正作用是**把余量压到 0** ——
   零余量 ⇒ 板级/对端侧任何抖动（窗口/ACK/仲裁）都**无法被吸收**，直接变成线上空洞。
   这解释"为什么同一帧器、同一条线，UDP 能打满 193.00000 而 TCP 只能 199.7"。
4. ⭐ **尾字（4 拍）是唯一的可压大头，且已量化并已用原型实测**：仓外原型（carry 跨帧，**逐字节等价**）
   把 app 从 **190 → 186 拍/帧**；链上 **RX 占用 194→190（无 pipe）/ 193→189（有 pipe）**；
   **TX 帧周期 193 → 191（逐帧）**。【实测】+【逐字节判据通过（`REDS payload=0`）】。
5. ⛔ **纸上算不出的那一格（§D）**：`P` 在 **195.9–401** 之间随对端 ACK 时序摆动
   （唯一变量曾是对端网卡 RX 中断合并），纸面预算里**没有对端模型** ⇒ 改法上线后
   **`P` 从 ~199.7 落到 193 还是只落到 ~197，本单不能判**（需要 §D 的三个计数器）。

### B.2 ⭐ 尾字刀：具体改法 + **原型实测**

**现役实现（逐字引用）**——尾字走逐字节路：
- `rtl/app_pattern.v:395`　`wire [3:0] need = (left >= 12'd8) ? 4'd8 : left[3:0];`
- `:468`　`wire a2_ldw = asm_go && (need_a == 4'd8) && !a2_hold;`　⇒ **`need_a<8` 时整字路不命中**
- `:737-744`　`end else if (bcnt < need_a) begin bcnt <= bcnt + 4'd1; stg <= stg_n;
  if (!bad_frm) tx_lfsr <= xs_next(tx_lfsr); end`　⇒ **1 字节/拍**
- `:772-780`　`if (asm_full && !pw_valid) begin pw_data <= ljust8(stg, need); …`（凑齐才装载）

**参考件（UDP 版）的 8 字节/拍写法**（**数据宽度/合同不同，不许直接抄**）：
- `rtl/app_udp_pattern.v:559`　`wire [63:0] tx_lfsr_8 = xs_next8(tx_lfsr);`
- `:560-561`　`wire [63:0] gen_word = pay_ok ? xs_word8(tx_lfsr) : 64'hA5A5A5A5A5A5A5A5;`
- `:563`　`wire wide_ok = gen_ok && (left >= 12'd8);`　⇒ **只在 `left>=8` 用宽路，尾字仍回落逐字节**
- `:566`　`wire frm_close = (push_now || wide_ok) ? last_b : nul_push;`

⭐ **两处结构性差异**（这就是"不许直接抄"的理由）：
1. UDP 是「字节 → `stg` → **同拍推 FIFO**」（`push_now`，零气泡）；TCP 是「载荷 → **呈交寄存器 `pw_valid`** → 下一拍消费」（`:410-413` 的前瞻 + `:800` 的写回）⇒ TCP 多一层 1 深 skid。
2. UDP 的 `left>=8` 门**天然把尾字踢回逐字节**；TCP 的 `need_a==8` 门同理 —— **两边都"忘了"尾字也本可以宽出**。
3. 更根本的一条：`xs_next8` 是 **+8 步**（`M^8`），尾字要的是 **+k 步**（k = 尾字字节数）⇒
   **直接用 `xs_word8` 会多推进 (8−k) 步 ⇒ 跨帧图案流错位**（这正是本单原型第一版踩到的坑，见 §F-3）。

**改法（carry 跨帧，本单已实现并实测）**：把"多推进的字节"`存起来`而不是丢掉 ——
尾字用**整字网**出，未用的 (8−k) 字节存进 `wc_buf/wc_n`，**下一帧用它们补开头**；
于是 LFSR **永远按 8 步走**（不需要 `M^k` 网），且**跨帧字节流逐字节连续**。核心网：

```verilog
// [PROTO] 仅示意；完整件 = %TEMP%\gap9_tx_recalc\m4\app_pattern.v（sha256 见 §F）
wire [3:0]  wc_gap  = need_a - wc_n;                       // case B 需新字节数 (1..8)
wire [63:0] wc_new  = bad_frm ? 64'hA5A5A5A5A5A5A5A5 : xs_word8(tx_lfsr);
wire [63:0] wc_spl  = wc_buf | (wc_new >> {wc_n, 3'b000}); // carry 在前, 新字接在后
wire        wc_b    = (wc_n < need_a);
wire [63:0] wc_emit = wc_b ? wc_spl : wc_buf;              // case A: 只用 carry, LFSR 不动
wire [63:0] wc_nxt  = wc_b ? (wc_new << {wc_gap, 3'b000})
                           : (wc_buf << {need_a, 3'b000});
wire [3:0]  wc_nnxt = wc_b ? (4'd8 - wc_gap) : (wc_n - need_a);
wire [63:0] wc_pw   = wc_emit & bmask64(need_a);           // 未用字节清零(与 ljust8 同约定)
wire        wc_go   = asm_go && (need != 4'd0) && (need_a != 4'd0) && !a2_hold;
```
装配块把**整字路与逐字节路合并成一条**（`:722` 的 `a2_ldw` 分支 + `:737` 的逐字节分支
→ 单一 `else if (wc_go)`），`tx_lfsr <= wc_b ? xs_next8(tx_lfsr) : tx_lfsr`（case A 不动 LFSR）。
`ev_up` 清 `wc_n`（新会话新流）；坏帧收尾清 `wc_n`（0xA5 残余不得跨帧）。

**原型【实测】结果（同一 TB、同一帧器、判据全绿）**：

| 指标 | 基线 | 原型 | 差 |
|---|---|---|---|
| app 单独周期 | 190 | **186** | −4 |
| 链上 app 跨度 | 188 | **184** | −4 |
| RX 占用（有 pipe, wrapper 忠实） | 193 | **189** | −4 |
| 链上 RX 占用（无 pipe） | 194 | **190** | −4 |
| TX 帧周期众数 | 193 | **191** | −2（被帧器自身 191 收口） |
| **载荷逐字节（TB J3）+ 守恒（J5）** | OK | **OK（`REDS payload=0 / cons=0`）** | 0 |
| TB 总数 | `REDS 全 0` | `REDS 全 0` | — |

⇒ **这一刀把 app 从"恰好压线（193=193）"变成"有余量（189/191 < 193）"**，
且**字节流逐字节不变**（该 TB 的 J3 是逐字节 oracle）⇒ 是**可交付的**改法，不是纸面推演。

### B.3 `axis_pipe`（1 深、无旁路）—— 是否把 app 的节奏**直接锁给帧器**？

- 【实测】**不锁**：`axis_pipe.v:16` 的 `s_ready = m_ready || !m_valid` 让 app 在 pipe 空时可**提前一手**；
  但 app 自己的周期与 pipe 无关（**190 两档逐字相同**，`m_tready≡1`）⇒ pipe 只做弹性 + 1 拍延迟。
- 【实测】pipe 的净效果 = 在**帧边界**吸收 **1 拍**（RX 占用 194 → 193），其余不变。
- **加深缓冲有没有用？没有 —— 且理由是双层的**：
  1. **平均值已不落后**：app 平均 190 < 线 193（UDP 侧同类量 186）；瓶颈在**帧器 RX 的 193**，
     不是缓冲深度。**平均值相等 ⇒ 永远追不出富余**（本单已先给出 A.1/A.4 的结论才谈缓冲）；
  2. **真正约束是"信用"不是"缓冲"**：板级 `app_tx_ready`（在飞<帽）与帧器 `wnd_open`
     （`rtl/tcp_tx_frame.v:1230`）是**窗口信用**门，窗口关时**再多缓冲也发不出去**
     （ping-pong 只有 2 bank ⇒ 先天最多领先 1 帧）。
  ⇒ **加深 `axis_pipe` 与提高 app 节奏是两件不同的事；前者对本缺陷 0 收益**（属【纸面推演】，但前提 1、2 都是【实测】）。

## D. ⛔ 纸上算不出来的那一格：**必要**还是**充分**？

**结论：必要（且是本单唯一被实测确认的"结构性前提"），但不充分。**

**为什么"必要"**【实测+纸面推演】：
- 同一条线（193）、同一个帧器（TX 191 / RX 下限 189）、同一个 arb：UDP app（186，余量 7）
  ⇒ 实测 `P = 192.99998`（**该构型下帧率已贴几何上限**——⛔ **2026-10-10 订正（口径）**：原写"零死拍"；
  `W43` 每拍无条件 +1（`mac_tx_10g.v:330`）⇒ `P ≡ 156.25e6/fps`，`P` 只能证明"帧率 = 几何帧率"，
  **不能**证明"线上无空拍"（板侧**没有**线占空计数器））；
- TCP app（193，**余量 0**）⇒ 实测 `P ≈ 199.7`（**等效帧周期差 ≈6.7**；⛔ 2026-10-10 订正：原写"6.7 死拍"——
  同上，该差值 = `(1/fps − 1/fps_max)×clock`，**不是**"测到线上 6.7 拍空转"）；
- 改法把 TCP app 拉到 186/189（余量 4）⇒ **结构上不再是 pacer**（实测链下限 191 < 193）。
⇒ **app 的零余量是"6.7 能出现"的前提**：余量 0 时，任何 ≤ 板级抖动的负偏移**都不再被吸收**。

**为什么"不充分"**【推断 + 未测】：
- 纸面预算里**没有对端模型**：`P` 的摆动（195.9–401；双向构型下 401）由**对端 ACK 时序**主导
  （唯一变量曾是对端网卡 RX 中断合并；`rx-usecs 60` 关掉后 6.5–8.4 → 9.1–9.3 Gbps）。
- **信用停顿不是抖动**：`app_tx_ready`（在飞<帽）/ 帧器 `wnd_open` 一关，**再快也没用**
  ⇒ 4 拍余量**吸不掉**这类停顿（只有 ping-pong 的 2 bank = 最多领先 1 帧）。
⇒ 4 拍余量能吸掉的是"**≤4 拍的板级抖动**"（RX_FIN/arb/bank handoff/ACK 突发）；
   **超出部分（窗口/对端侧）必须另外补足**。

**下一步该用什么补足（本条只登记，不实施）**：
1. **构建 B-1 三计数器**（`win_open==0` 拍数 / `frm_wait` 拍数 / `txcdc 空拍`）——
   与 `ΔW43/ΔW20` 同窗采样，即可把"6.7 里 app 占几拍、信用占几拍、链路占几拍"**分离**；
2. 同窗取 `ss -ti`（对端）与 NIC `rx-usecs` 当**对端配置见证**（全局 #62 的"见证"纪律同款）；
3. 三计数器落地前，**不许**把任何 P 变化写成"这一刀生效"/"没生效"。

3. **尾字直接用 `xs_word8` 而不带 carry 会推进 8 步 ⇒ 跨帧图案流错位**（本单第一版即"timing-only"
   思路会被 TB 的 J3 判红）；carry 方案才同时拿到"1 拍"与"逐字节等价"。
4. `rtl/tcp_tx_frame.v` 是 **CRLF**（2040 CR）⇒ 任何 `\n` 锚点脚本在它上面 0 命中（本单已避开，
   只读不写）；`rtl/app_pattern.v` 是 LF（本单 patch 脚本按 LF 锚点，正常）。
```

### G.2 ⛔ **对 §B.2 原型片段的一处订正（坏帧）**

§B.2 的示意代码与仓外原型 M4 里有一行 `ev_up` 之外的另一处清理：

```verilog
// [原型 M4 原文] 收帧拍:
if (bad_frm) wc_n <= 4'd0;      // ← ⛔ 这条是错的
```

**为什么错**：坏帧期间原型**照样更新** `wc_buf`（`wc_new` 取 0xA5 台填）⇒ 坏帧稳态下
`wc_buf` 里留下 `{0xA5 × wc_n}`；只清 `wc_n` **不遮住**它们，而合并式是 `wc_buf | (新字 >> …)`
⇒ **下一个好帧的首 `wc_n` 个字节变成 0xA5**（图案流从此错位）。正确做法 = **坏帧期间整体 hold**
（`wc_buf`/`wc_n`/LFSR 都不动）+ emit 直接取常数 0xA5 —— 这才让"坏帧对图案流不可见"这条
语义**同时覆盖 carry**。本轮实现即按此，并留了变异件 `mut_bad_upd.v`（把 hold 改成无条件更新）
⇒ 门在 `idx=1`（注入帧臂）给出 `[FAIL] G1 pattern mismatch`。

### G.3 实现的两个语义决定（判据读法必须有这两条）

1. **carry 的会话边界清除点 = 唯一一处** = `ev_up` 块里与 `tx_lfsr <= SEED` **同拍同条件**的那两行
   ⇒ "清了 carry" ⟺ "换了流"。`ev_down`（拆连）/坏帧 / `frm_wait` **都不清**（前两者之后
   唯有 `ev_up` 能让 app 再发 ⇒ 结构性安全；后者的流本来就要跨帧连续）。
2. **坏帧发射内容 = 纯 0xA5**（`wc_pwv = bad_frm ? 64'hA5A5… : …`）—— 与逐字节路的
   `gen_byte` 常填**逐字节同款** ⇒ 两臂的注入帧内容可比（本轮的 B-vs-C 门覆盖到它）。

### G.4 【实测】顺带观测到的一条既存口径（**与尾字刀无关**，登记）
