| 2 | **HLS `udp_echo`** | `hls/.../udp_echo*.v` | `RAMB36E2`×6 + `RAMB18E2`×62 | 20 实例 | 6 | 62 | **37** |

| 5–7 | 3× `frame_fifo` | `slow_rx_adp.v:94` / `slow_tx_adp.v:80` / `udp_split.v:464` | 手写 `RAMB36E2` | 512×73 | 3 | 0 | **3** |
| | **合计** | | | | **317** | **62** | **348** ✓ |

### 1.2 对账方法（**不是估的**，三条独立链）
- 综合期（XDMA 是黑盒）= 281 R36 + 62 R18 = **312**
- 实现期（XDMA 已链接）= 317 + 62 = **348**，Δ = **+36 R36 = XDMA**
- ⭐ 用 `_proj_pcie/pcie_min_util.rpt`（**同器件 + 逐字相同 XDMA CONFIG**）实测 **36** 钉死
⇒ **差 0。** A4 路当时留的"差 2"尾巴可删。

### 1.3 通路归属
- `retx_ram` = **TX 快路径**，但是**旁路**：首发时与载荷同拍旁写，**只在 `S_RING` 重传会话被读**
- `u_tcp_echo.u_fifo` = **RX 快路径**，**必经**（存转发）
- 3× `frame_fifo` = RX/TX 快路径，**必经**，但各只 1 tile
- HLS 37 + XDMA 36 = **旁路**（慢路径 / 观测面）
- ⭐ **其余全部手写 RTL = 0 tile**（Vivado 把手写 FIFO 全推断成分布式 RAM）；**`pcs64` 也是 0**

## 2. 在哪、对时序与延迟什么影响（A2）

### 2.1 ⭐ 位置测绘
RX 链 `PCS→mac_rx_10g→u_rxcdc→vlan_strip→rx_classify→{tcp_rx→tcp_echo | udp_split→slow_rx_adp→HLS}`、
TX 链 `app→udp_tx_cfg→udp_tx_frame/tcp_tx_frame→tx_arb→mac_tx_10g→PCS` 上，
**必经（该类流量每帧都过）的 BRAM 只有 5 块小件**（合计约 20 tile）。
**最大的 `retx_ram`（256 tile = 已用的 73.6%）是旁路。**

### 2.2 ⭐ 延迟：**实测流水里 BRAM 贡献 = 0 拍**
`P7B_LATENCY.md` 实测的 **95.98 ns** 流水：
- `(a)→(b)` 走 `mac_rx_10g` 的 16 深 fifo
- `(b)→(c)` 走 `u_rxcdc`（**FWFT 组合读 ⇒ 结构性 LUTRAM**）+ 16 深路由队列 + `vlan_strip`（零存储）
- `(c)→(e)` 走 `udp_split` 的 16 深预取 + 32 深 LUTRAM

⇒ **全程一块 BRAM 都没有。** 这正解释了那个「跨帧长只差 **0.05 ns**」的读数。

### 2.3 ⭐ 真正的延迟大头**不在 BRAM**
`(e)→HLS` 收完 ≈ **189 拍 ≈ 1209 ns**（158 B 帧），其中：
- **BRAM 只占 ~23 拍（128 ns）**
- **主项 = 「1 字节/拍」字节播放器的 166 拍 = 1062 ns**

⇒ **把播放器加宽到 1 字/拍 = −145 拍 = −928 ns** —— **比任何 BRAM 改动都大一个量级**。

### 2.4 关键机理：**深度不是延迟**
`DOA_REG`/`DOB_REG` 被**故意关掉**（`rtl/frame_fifo.v:153/:190` 显式 `.DOA_REG(0), .DOB_REG(0)`，
为了让 1 拍读延迟与 LUTRAM 边存对齐）⇒ **稳态读滞后恒 1 拍，深度只在被填满时才兑现**。

### 2.5 ⭐ 时序判词：**BRAM 是「面积 + 扇出」项，不是瓶颈**
判别性证据（不是泛泛之谈）：
1. **setup 200 条里只有 2 条含 BRAM**，且这 2 条**逻辑级数 = 0**、延迟 **100% 是布线**（5.5–5.6 ns）⇒ **扇出/布局问题**
2. **hold 307 条 / recovery 246 条里，BRAM 走数据通路的 = 0 条**
3. 全局 **WNS 落在 PCIe 复位网络**（`u_pcie_xdma` → `u_snap_dp`，逻辑级数 0、97.4% 布线），**与 BRAM 无关**
4. 唯一「BRAM 主导」的桶是 **XDMA 的 hold**（400 条里 73 条，71 条在 `pcie_axi_aclk`），slack **0.010 = 全局 WHS**

⚠️ **但 `retx_ram` 那条地址网没死透**：它是 `dp_clk` 组**第 3 差（0.289，距最差仅 0.010 ns）**，
自述「FSM → 256 片 RAMB36 地址脚，route 6.30 vs logic 1.53」。

⚠️ **一处历史低估的订正**：`P7B_LATENCY_GAPS.md` §2.1 的「固定开销 13~15 拍**外加 N 字**」若被读成**末字**延迟，
会**低估 N 拍** —— 存转发让末字是 **2N**。

## 3. 能否换 URAM（A3）

### 3.1 三条**最容易误判**的硬约束（都由 unisim 原语 + XPM DRC **源码**支撑）

| # | 约束 | 出处 |
|---|---|---|
| **1** | **KU5P 的 `URAM288` 没有 `INIT`** ⇒ **任何 ROM / 有初值的表一律硬否决**。⚠️ 能查到的 `INIT_*`/`INIT_FILE` 是 **Versal 的 `URAM288E5_BASE.sv`**；KU5P 的 `URAM288.v:25-66` 参数表里**一个 INIT 都没有**。**拿 Versal 推断 KU5P = 必错** | `URAM288.v:25-66`；`kintexuplus.lib` 只有 `URAM288`/`URAM288_BASE` |
| **2** | **URAM 只有一个 `CLK`**（端口表里连 `IS_CLK_INVERTED` 都只有共用那一个）⇒ **所有跨时钟 FIFO 一次性排除** | `URAM288.v:117`；`xpm_fifo.sv:322` 直接 `$error` |
| **3** | **没有 `WRITE_MODE` 三选一**：原语层 `grep` 零命中；XPM 层对 URAM **TDP 必须 `no_change`、SDP 只能 read-first/write-first，且 write-first 要读延迟 ≥3** | `xpm_memory.sv:614-645` |

⭐ **一条此前没人查的设备事实**：**KU5P 的 64 个 URAM288 全在 X2 这一列时钟区域（每区 16）**，
X0/X1/X3 **一个都没有**；而 **X2Y1 现在 Block RAM 是 72/72 满的**。

### 3.2 ⭐ 换得了的：**只有一块**

| 块 | 当前 | 迁移后 | 代价 |
|---|---|---|---|
| **`retx_ram`**（`rtl/retx_ram.v:119-120`，TCP 重传环 8.39 Mbit） | **256 tile** | ⭐ **348 → 92 tile（72.50% → 19.17%）** | **29–32 / 64 URAM** + 读流水 **2→3 级** |

⭐ **"能不能"不是猜的**：**Vivado 自己已经试过把 `retx_ram` 映到 URAM 并拒绝了**，
`Synth 8-6793` 原文给的理由是 **`Available pipeline stages = 0, Minimum required pipeline stages = 3`**
（`board/p7b_ku5p_stdout.txt:1473-1516`）。它的 **64 位宽 / 字节写使能 / 单时钟**全都匹配 URAM288
（`BWE_A[8:0]` 已对 unisim 源核过）。

### 3.3 换不了的（**说透，避免以后有人白试**）
| 块 | tile | 一句话理由 |
|---|---|---|
| `frame_fifo` 主存 ×5 | 23 | 是**手写 `RAMB36E2` 原语**（属性改不动），且**依赖 `WRITE_FIRST` 同址写读碰撞**（`rtl/frame_fifo.v:44-48`），URAM 无此语义 |
| `fifo_sync` 全部 | ~14 | **太浅太窄**：最大 2048×9 = 18,432 b，而 URAM 是 **4096 深 × 72 位整块** ⇒ **一个 tile 都省不掉**，纯负收益 |
| `fifo_async`（`u_rxcdc`/`u_txcdc`） | 0 | **双时钟 = 硬否决**；且它们组合读 ⇒ **本来就不吃 BRAM**。换它是双输 |
| HLS `udp_echo` 的 `RAM_2P_BRAM_*` | ~15 | 用 36 KB 存 96 bit；要改得回 HLS 源码加 `bind_storage` 重生成核。纯负收益 |
| `xdma_0` | 36 | 官方 IP 的 OOC 网表，不可改 |
| 任何 ROM / 有初值的表 | — | 见 §3.1-1，硬否决 |

### 3.4 ⭐ 迁移代价里**最贵的不是延迟**
**是 `tcp_tx_frame` 的 `S_RING` 拍表重算 + 全链回归。**
`rtl/tcp_tx_frame.v:558-570` 那张表是**逐拍对齐**的 —— `ring_end = nbeats+2` 的 **`+2` 就是现在的 2 拍读延迟**；
延迟一变要牵动写序列、`rm_mask` 相位与 `ring_fin`。
延迟本身反而便宜：**+1~3 拍（上界 +19.2 ns @156.25 MHz）**，且**只落在重传读路径**。

### 3.5 ⚠️ 施工前必须先修**推断形态**
**不能只加一行 `ram_style="ultra"`**：Vivado 已把 `retx_ram` 拆成 **8 字节 lane × 16 深度片**（`Synth 8-6841`），
直接套 `ultra` 会让**每 lane 独占 16 个 URAM** ⇒ **128 URAM/阵列 = 2 倍全器件**。
必须先加 `ram_decomp="power"` 或改写 `rtl/retx_ram.v:126-135`。

## 4. 能否减少（A4）

### 4.1 深度过剩（每条上界都有推导）

| # | 块 | 声明 | 结构上界（出处） | 比值 |
|---|---|---|---|---|
| 1 | **`retx_ram` 全 16 连接** | 16 × 64 KB = **1 MB** | `N_biz × 50,649 B` | **16 / N_biz** ⭐ |
| 2 | `retx_ram` 每连接 | 8192 字 = 64 KB | **6,332 字 = 50,649 B**（`RING_CAP 0xBFFE−1 + PLEN_MAX 1500`） | 1.29 |
| 3 | `tcp_echo.u_fifo` | 8192 字 = 64 KB | **6,873 字**（wrapper 的物理界等式 `Σwinq+N·ACC_MARGIN+Δ+U+SEG ≤ 65536`） | 1.19（**按构造取整 ⇒ 0 过剩**） |
| 5 | **HLS 的 62 片 RAMB18** | 1,116 Kb | 实装 **≈68 Kb** | ⭐ **利用率 6.2%**（`ip_rx_process_hdr` 每片 **0.44%**） |

### 4.2 三条可施工的减法

| 方案 | 省 | 代价 |
|---|---|---|
| **`retx_ram` N: 16 → 4** | ⭐ **192 tile（348 → 156，−55%）** | **只是产品并发上限**（16 是设计值非需求值）+ 跨 7 模块 conn id 参数化；**不碰时序** |
| **`WIN_CAP` 48 KB → 24 KB**（`wrapper_p4.v:222` **一处 localparam**） | **136 tile** | 每连接在飞 24 KB ⇒ RTT 50 µs→3.9 Gbps、1 ms→196 Mbps、10 ms→20 Mbps；⭐ **同时把 RX 排队延迟砍半**（**与低延时目标同向**） |
| 两者叠加 | ⭐ **232 tile（348 → 116，−67%）** | — |

### 4.3 LUTRAM 候选
| 方案 | 省 | 吃 LUT | 时序风险 |
|---|---|---|---|
| HLS 全部 62 片 RAMB18 → LUTRAM | **31 tile** | ~1,500–2,500 | 中 |
| ⭐ **只挑 ≤1 Kb 的那 ≈50 片**（hdr 14、arp_bytes 10、tcp_conn_* 13…） | **≈25 tile** | **~400–700** | **低** ← 首选起步 |
| `frame_fifo` ×3 → LUTRAM | 3 tile | ~2,200 | **高**（156 MHz 主通路 + P6a「边存改 RAMB18 丢 tlast」前科）⇒ **不做** |

⚠️ **换算校正**：1 片 RAMB36 = 36,864 位 = 576 个 RAM64X1 **是对的**，但**实测率是 41–56 位/LUTRAM**
⇒ 工程上 **1 tile ≈ 700–820 个 LUT**，深存再加等量读 mux。

### 4.4 减不动的
3 个 512 深 `frame_fifo` 是 `NB=D/512` 的**硬粒度**损失（换 RAMB18 也是同 1 tile）；
`retx_ram` 单 bank 化会让 7/8 的拍掉一半吞吐；
28 片当量的宽度浪费（64/72）是 2^16 环 + 字节写使能的固有代价。
⚠️ **`UDP_TX_OVL` 乒乓不能砍**：它是 378→191 拍/帧、4.84→9.53 Gbps 的来源，且**吃 LUTRAM 不吃 tile**（收益 0）。

### 4.5 顺手抓到的**文档缺陷**
`retx_ram.v:6` / `tcp_tx_frame.v:180` / `tcb.v:141` 三处仍写「`plen_max` **4095** = 53244」，
而 `PLEN_MAX` 现为 **1500** ⇒ 真上界 **50,649**（偏保守 2,595 B）。**结论不变，但引注释会算错 5%。**

## 5. 施工建议（**排序 = 收益/代价/风险**）

> ⚠️ **本节是建议，本轮一行未实施。**

### 5.1 ⭐ 第一优先：**`retx_ram` → URAM**（−256 tile，**−73.6%**）
- **收益**：348 → **92 tile**，同时**消掉 `dp_clk` 组第 3 差的那条 256 片地址网**（§2.5）
- **代价**：29–32 / 64 URAM（**全空**）+ 读流水 2→3 级 ⇒ **重传路径 +1~3 拍（上界 +19.2 ns）**
- **前置**：必须先修**推断形态**（§3.5），否则会炸成 128 URAM/阵列
- **真正的工作量**：`tcp_tx_frame` 的 `S_RING` 拍表重算 + 全链回归（§3.4）
- ⚠️ **必须专门造"重传"用例**：常规回显通路**走不到** `retx_ram` —— **这正是它能沉默这么久的原因**

### 5.2 第二优先：**`WIN_CAP` 48 → 24 KB**（−136 tile，**且与低延时同向**）
- **好处是双份的**：省 tile **+** RX 排队延迟砍半
- **代价是产品参数**：每连接在飞变 24 KB ⇒ 需按**目标 RTT** 定（直连低延时场景 RTT ≈50 µs ⇒ 仍有 3.9 Gbps）
- ⚠️ `WIN_CAP` 有 **≥6 处硬编码副本 + 门脚本的文本解析点** ⇒ 改动面要核全

### 5.3 第三优先：**HLS 小片 → LUTRAM**（≈25 tile，低风险）
- 只挑 **≤1 Kb 的那 ≈50 片**，吃 **400–700 LUT**（LUTRAM 余量 93%）
- **风险最低、最容易独立验证**，适合当"第一刀"练手

### 5.4 ⚠️ **一条必须写进纪律的**：窗口扩字会吃时序
本轮 **WNS `+0.136 → +0.077` 的 −0.059 已归因到快照阵列复位网**（51→61 字，**+320 FF**）：
全局最差 = `u_pcie_xdma/…/user_reset_reg/C → u_pcie_regs/snap_words_r_reg[174]/CLR`，
**逻辑级数 0、97.2% 只是布线**；且**上轮全局最差就是同一族** ⇒ 是"同一族内换了最差那一位"，不是新缺陷族。
⇒ **每 +10 字 ≈ +320 FF**，**再加字会继续吃这条**。三个候选（按代价排序，**未实施**）：
(a) 该复位在 `pcie_axi_aclk` 域内打 2 拍 `ASYNC_REG` 再驱动阵列 CLR；(b) `max_fanout`；(c) 接受现状。

### 5.5 ⭐ 一条**不该做的**：**别为了减 BRAM 去动 `UDP_TX_OVL` 或 `frame_fifo`**
前者收益 0（吃 LUTRAM 不吃 tile），后者有「丢 tlast」前科。

U3 ⭐ **`N_biz` 与目标 RTT 是产品输入**（决定 `retx_ram` N 与 `WIN_CAP` 的力度，**需要用户拍板**）·
U4 `WIN_CAP` 硬编码副本面 · U5 连接池化的时序代价（动的是**全工程最差地址网**，历史 −0.848/912 端点 ⇒ 风险高）。

**来自 A3 的**：`retx_ram` 换 URAM 后**时序能否收敛**（未验证）；`29 个 URAM` 是**上界估计（±3）**。

## 7. 未结与风险（如实列全）

| # | 事项 | 说明 |
|---|---|---|
| 1 | **本轮零实验** | 全部结论都是**静态分析**（报告 + RTL + unisim/XPM 源码）；**换 URAM 后 WNS 能否收敛、真实 URAM 数、LUTRAM 真实代价，全都没测** |
| 2 | **本机 Vivado 2025.2 没装任何 PDF 文档**（`Vivado/doc` PDF 计数 **0**） | UG573 **无法离线复核** ⇒ A3 的硬约束**全部改由 unisim 原语 + XPM DRC 源码支撑**（⚠️ 这比 PDF 更硬，但要写明出处形态变了） |
| 3 | A1 的不确定 | `retx_ram = 256` **不是本轮读数**（本轮无分层报告），来自 P6a+P6 两份分层报告 + RTL 注释 + 容量反算**三方同值**；XDMA OOC 38 vs in-context 36 的 **2 片去向未定位**；LUTRAM 求和 ≈3,665 vs 实测 ≈4,836，**~1,170 未逐条对账**；HLS 有 **12 片 RAMB18 在 depth-3 节点未逐片定位** |
| 4 | A2 的不确定 | `u_ofifo`(2048×9) **是否真落 BRAM 未核**；末字 `2N+2` 与 `(e)→HLS 1.21 µs` 是**推算**；`report_timing_summary` 每时钟对只采样 ~10–20 条最差，**240450 个端点绝大多数未被采样** |
| 5 | ⚠️ **A2 踩到的陷阱（值得记）** | `rtl/udp_echo.v` 的 4 片 RAMB36 **不在本轮构建里** —— 构建用的是 **HLS 生成的同名文件**。⇒ **同名文件有两份时，引用必须带路径** |
| 6 | **`retx_ram` 的 dp_clk 时序"没死透"** | 第 3 差（0.289，距最差 0.010 ns），0 逻辑级、98.3% 布线 ⇒ 但**换 URAM 会把这条网整个换掉**，是收益也是风险 |
| 7 | 产品输入缺口 | **`N_biz`（并发 TCP 连接数）与目标 RTT 未知** ⇒ 5.1/5.2 的力度**定不了**，**建议用户拍板** |
